## 1. 数据分级与处置策略【框架有效，L0 定义与存储位置已按 V0 改写】

> **V0 的关键变化**：原文说 L0「**仅端侧**」，那是"端侧为权威/本地优先"时代的口径。
> **V0 服务端 SQLite 是唯一权威**（PRD 08 §2.1），所以 L0 的含义改为
> "**仅存于你自己的机器 / 你的账户下**"——依然不上传第三方、不部署公网、不出家门。

| 数据级 | 内容 | V0 存储位置 | 默认行为 |
| ---- | ---- | ---- | ---- |
| L0 用户内容 | 物品明细、备注、开封状态、校准样本、（V1 起：照片、语音文本） | **仅存于你自己的机器 / 你的账户下**：本机 `localhost` 的 **SQLite 文件**，按 `user_id` 隔离 | **不出本机、不上传任何第三方**；V0 无照片（拍照属 V1） |
| L1 必要业务数据 | ~~订阅提醒计划（itemId + 品类名 + 到期日 + 文案键）~~ | 🚫 **【已作废】V0 无此数据面** | V0 不做提醒 → 服务端**不存在** `remind_plans`；提醒字段只作为 `Item` 的普通列存在 L0 内 |
| L2 匿名统计 | 埋点事件、错误码、校准方向 | 端侧队列 → 服务端 events 表（**同一台机器**） | 匿名化后写入；V0 不做对外上报 |
| L3 产品配置 | 50 类知识库、文案、开关 | 服务端持有（JSON），前端拉取 | 服务端为源；前端可缓存 |

### 2.5 【V0 新增】服务端安全要求（原文没有，必须实现）

> 📎 **编号说明**：本节沿用原章内部预留的空号段，直接从 §2.1 跳到 §2.5，**不是漏节**
> ——中间号段属于已作废的订阅消息设计，不再占用。

> 🎯 **这是 V0 唯一的新增必做安全节。** V0 有了账户与本地服务端，安全问题第一次真实存在——
> 尽管跑在 `localhost`，也**必须**做到下面 6 条：① 一旦以后部署公网（V1）不必返工；
> ② 越权是**逻辑缺陷**，与是否公网无关，本机同样会因 bug 串号。

| # | 要求 | V0 具体做法 | 反面（禁止） |
| ---- | ---- | ---- | ---- |
| **1** | **密码必须哈希加盐** | 用 **argon2id**（首选；Node 端 `argon2` 或 `@node-rs/argon2`）；参数按库默认（如 m=19456, t=2, p=1）；每个用户独立 salt；比对本用恒定时间比较 | 🚫 **禁止明文存储**；🚫 **禁止 MD5 / SHA1 / SHA256 裸哈希**；🚫 禁止自研"加盐算法"；bcrypt 可作次选（cost ≥ 10） |
| **2** | **会话 token 可吊销** | 二选一：① **httpOnly + Secure + SameSite=Lax Cookie**（前端拿不到 token，天然防 XSS 窃取）；② **Bearer token**（`Authorization: Bearer <token>`，PRD 08 §2.4 的 API 约定）。两者都要：token **高熵随机**（≥ 128 bit）、服务端存哈希、有 `expires_at`、**支持登出即吊销**（删除/置失效会话行） | 🚫 不签发永不过期的 token；🚫 不把 token 放 localStorage 后当"登录态"的唯一凭据（Bearer 场景须接受此权衡并限制有效期）；🚫 不在 URL query 里带 token |
| **3** | ⭐ **所有写接口必须校验资源归属**（**V0 头号安全问题**） | 每一条读写 SQL 都带 `WHERE id = ? AND user_id = ?`；`user_id` **只能取自会话**，**绝不接受请求体里的 user_id**；更新/删除影响行数为 0 → 返回 **404/403**（不要区分"不存在"与"别人的"，避免探测）；列表/统计/搜索一律先按 `user_id` 过滤 | 🚫 `SELECT * FROM items WHERE id = ?`；🚫 只在前端隐藏按钮而服务端不校验；🚫 用自增 ID 且不校验归属（可枚举别人的数据）；**建议 itemId 用随机 ID**（同 PRD 08 §2.4 口径） |
| **4** | **限流与防撞库** | 登录失败按**用户名 + IP** 计数 → 指数退避（如 5 次后锁定 15 分钟）；注册接口限流；响应时间恒定（避免用户名字典探测）；**注册必须防重复用户名**（DB 层 `UNIQUE` 约束 + 捕获唯一键冲突 → 友好提示，不能只靠"先查再插"） | 🚫 无限尝试；🚫 把"用户名已存在"做成可批量探测的接口而不限流；🚫 只在应用层查重（并发下会插入两条） |
| **5** | **密钥与数据文件绝不进仓库** | `.gitignore` 必须包含：`.env`、`.env.*`（保留 `.env.example`）、`*.sqlite`、`*.sqlite3`、`*.db`、`data/`、`backup/`、`*.log`；`.env.example` 只放**占位符**（如 `SESSION_SECRET=change-me`）；提交前用 `git status` 自查 | 🚫 把 `.env` 或 SQLite 文件 commit 进仓库；🚫 在代码里硬编码密钥/口令；🚫 把真实密钥写进文档、测试或截图 |
| **6** | **日志不得泄露敏感信息** | 日志白名单：请求方法/路径/状态码/耗时/`user_id`/`itemId`；**明确禁打**：密码与密码哈希、token 与会话 cookie、完整个人信息（备注等自由文本按需截断或不打）；错误响应不回显 SQL/堆栈给客户端 | 🚫 `console.log(req.body)` 打整包请求体（登录接口必然泄露密码）；🚫 打印 token；🚫 把 SQL 原文与参数打进响应体 |

**V0 附加底线（低成本但值得做）**：

- 密码强度最低要求（长度 ≥ 8，不做复杂度强制）；注册/登录请求体大小限制；
- 依赖最小化：不引入"认证全家桶"，V0 的会话与哈希足以自持；
- **参数化 SQL**：一律使用 `better-sqlite3` 的 prepared statement / 占位符，禁止字符串拼接 SQL（防注入）。

## 7. 隐私事故应急（11 §9 对策落地）【已改写】

> ⚠️ **原文第 1 条"事故面天然最小（明细不上云）"的因果已变**：
> V0 的事故面小的原因**不是"不上云"**，而是 **"数据只在你自己的机器上、且不出本机"**。
> 一旦 V1 上公网，这条结论**立即失效**，风险等级需重新评估。

1. **V0 事故面**：本机 SQLite 文件 + 本机进程；主要风险是**误删/文件损坏**（→ 备份，见 10 §6）
   与**账户越权逻辑缺陷**（→ §2.5 第 3 条），**不是外泄**；
2. **V1 起**，若发生服务端数据异常：
   - 立即关停服务/回滚版本（分钟级）；
   - 强制吊销全部会话（`sessions` 表全清 → 所有 token 失效）；
   - 通知用户并说明补救；
   - 复盘并更新本架构文档（活文档原则）。

## 8. 验收清单（V0 版）

### 8.1 V0 必过

- [ ] **越权测试**：注册 A、B 两个账号各录 3 件；用 A 的 token 请求 B 的物资 → **403**；
  连 A 的 token 猜 B 的 id 做 PUT/DELETE → **同样 403/404**；数据库直查确认 `user_id` 分属不同账户
  （对应 PRD 08 §2.5 第 2 条）；
- [ ] **密码存储**：直查 SQLite 的 `users` 表 → 字段是 argon2id 哈希串（`$argon2id$v=19$...`），
  **无明文、无 MD5/SHA1 形态**；
- [ ] **会话可吊销**：登出后旧 token 立即失效（再次请求 → 401）；
- [ ] **限流**：连续 5 次错误密码 → 被退避/锁定，且提示不区分"用户不存在/密码错误"；
- [ ] **注册防重复**：并发注册同一用户名 → 只有一条成功，另一条得到友好错误而非 500；
