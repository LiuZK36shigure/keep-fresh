## 1. 语音解析器 `core/parser`（F-01，规则版）——【V1 起实现，V0 不做】

> 🚫 **V0 状态：不实现。** V0 的录入方式是**手动表单**（PRD 08 §2.2「记录」行），
> 语音录入与 ASR 明确排除在 V0 之外（PRD 08 §2.3）。
> V0 只需在 `packages/core/parser/` 放**空目录 + 接口签名**（`parse(text: string): ParsedRecord`），
> 保证移动端/V1 接入时不改协议；**本节以下全部内容按 V1 阅读**。
> V0 唯一继承本条的是"品类匹配词典"（`aliases`）——它同时也是 V0 表单"品类搜索 / 热门品类候选"的数据源。

> 📌 **V0 与 §5 的关系**：本节（parser）与 §3（reminder）的验收项收在 **§5.2（V1 起）**，
> 不要放进 V0 的完成定义里。

> 设计约束（11 §6 R5）：V1 用**规则解析**，不用开放大模型——可预期、可纠错、零成本、可单测。

### 1.1 处理流水线

```
识别文本（V1：浏览器录音 → 云 ASR 代理；原 WechatSI 已作废）
  → ① 归一化：全角→半角、繁体→简体、"几"→数字、"昨天/前天/上周X"→日期
  → ② 品类匹配：词典最大匹配（aliases 同义词 → categoryId）
       · 未命中 → 返回"未识别" + 热门品类候选（GWT-01 兜底话术）
  → ③ 实体抽取：数量（"三盒/一箱/3 个"）、开封（"开封了/打开了"）、日期（"今天/昨天/上周二"）
  → ④ 冲突处理：数量>1 → qty；多个日期 → 取最近；口误日期在未来 → 拦截（04 §6）
  → 输出 ParsedRecord { categoryId, qty, buyDate, openedAt, storageLocation?, confidence }
```

### 1.2 词典与规则数据（随知识库远程更新）

```jsonc
{
  "numWords": { "一": 1, "两": 2, "三": 3, "几": 3 },
  "unitWords": { "盒": 1, "箱": 12, "袋": 1, "瓶": 1, "个": 1 },
  "dateWords": { "今天": 0, "昨天": -1, "前天": -2, "上周二": "lastTuesday" },
  "openWords": ["开封", "打开了", "拆了", "开盖"],

```

### 1.3 二次语音纠错（GWT-02）

- 确认页进入"纠错模式"：`parseCorrection("不对，是昨天买的")` → 只更新指定字段；
- 实现：解析器输出字段级 diff，仅替换用户指出的字段，其余保持。

## 2. 推算引擎 `core/engine`（F-05，04 章三层规则）——【V0 核心，本章唯一必做模块】

> ⭐ **V0 最有价值的资产，就是这一个模块。** 理由：
> 1. V0 的业务假设是"**东西记得住吗？算得准吗？**"（PRD 08 §3），"算得准"全靠它；
> 2. 它是**纯计算**（零 IO、零平台 API）→ 可 100% 单测，`core/` 覆盖率 ≥ 80% 的门槛主要靠它达成；
> 3. 它同时被**前后端共用**（TechDesign 03 的 REST 接口与前端预览都调用它）→ 同一份算法不会出现两套实现；
> 4. 它**不依赖提醒、不依赖语音、不依赖账号**——所以 V0 砍掉那些功能后，它一点没缩水，
>    而 V1/V2 的移动端可以直接原样复用。**V0 期间对它的投入是唯一不会浪费的投入。**

### 2.1 日期驱动品类（model: 'date'）

```
输入：categoryRule + openedAt + storageLocation + climate(settings) + ruleVersion
  T0 = rule.T0[location] ?? rule.T0[default]       // ① 品类基线（按存储位置分档）
  T1 = rule.T1[location] ?? rule.T1[default]       // 开封后期限
  base = openedAt ? T1 : T0                        // ② 状态修正（04 §3）
  若 storageLocation ≠ 规则要求 → × storage_mismatch(0.5) + 提示文案
  k = 气候系数组合（04 §4.1，按 sensitivity 分级生效：high 全量 / mid 仅湿度+梅雨 / low 仅高温0.9）
  T = roundDown(base × k, 保守原则取更短期限)        // ③ 气候因子
  expireAt = (openedAt ?? buyDate) + T 天
  confidence = 打分（04 §5.1：品类命中40 + 开封20 + 存储15 + 日期15 + 气候10）
```

**输出**：`{ expireAt, windowEndAt, confidence, reasonText, climateFactors, ruleVersion }`
（reasonText 例："未开封冷藏 7 天 × 夏季高温潮湿 0.64 ≈ 4 天"——**可解释性**是信任的来源，01 §3.1）

### 2.2 状态驱动品类（model: 'state'，04 §7 最小版）

- 不推算精确日期：输出 `window = [buyDate + window[0], buyDate + window[1]]`；
- 提醒由 `checkRhythm` 驱动（检查提醒，见 §3.3）；
- 反直觉规则（香蕉勿冷藏）在确认页展示 tips 一行小字（04 §7.4）；
- 置信度固定 `mid`，详情页明示"状态类物品不承诺精确期限"。

### 2.3 边界情况（04 §6 全表实现要点）

| 情况 | 实现 |
| ---- | ---- |
| 品类不在知识库 | 走自定义模板：用户填期限 → `custom:` 条目，T0=用户值，sensitivity=mid |
| 无网络 | 用本地缓存 KnowledgeBundle（标注 ruleVersion='offline:xxx'）——V0 为服务端权威，浏览器侧以此条为降级兜底 |
| 药品/婴幼儿 | `conservative: true` → 区间展示按下限 + 强提示文案 |
| 冷冻→解冻 | 用户标记后创建"解冻后 24h"倒计时（复用 opened 计时器模型） |
| 补录过期 | 不阻断保存，status 直接置 `expired`，横幅提示检查实物 |

### 2.4 修改反馈回路（F-06，校准样本）——【V0 只记录，V1 才上报】

```
用户修改到期日 + 选原因 → 记录 CalibrationSample {
  categoryId, climateFactors, direction: 'shorter|longer', reason, ruleVersion
} → V0：随物资一起存入服务端 SQLite（**只存不分析**，供后续人工调参）
  → V1：匿名上报 calibration 集合 → 每周人工审核调参（04 §5.3）
```

> **V0 口径**：校准样本是"详情页手动修改推算"的副产物，V0 必须落库（否则调参无据可依），
> 但 V0 **不做**聚合分析、不做自动调参、不做上报通道。原表述中的"端侧暂存 + P1 匿名上报"
> 改为 **V1**（P1 编号已废弃，统一称 V1）。

## 4. 模块依赖与纯 TS 约束——【V0 有效，且是前后端共用 `core/` 的前提】

```
core/
├── parser/       ← 【V0 空占位，V1 实现】只依赖词典数据（JSON）
├── engine/       ← 【V0 ✓】依赖 knowledge(规则) + types
├── reminder/     ← 【V0 空占位，V1 实现】依赖 items + knowledge + types
├── knowledge/    ← 【V0 ✓】依赖注入的存储/规则读取接口（见下）
└── types/        ← 【V0 ✓】纯类型 + Zod/手写校验器（手写足够，不引入校验库）
```

> **V0 现实**：`core/` 里**只有 engine / knowledge / types 有实现**；
> `parser/` 与 `reminder/` 是**空目录 + 接口签名**，用来锁住未来协议（PRD 08 §2.4）。

**纯 TS 约束（架构铁律 3，V0 语境重述）**：

> ⚠️ **原表述"禁止 `import wx` / `getApp()`"是小程序时代的写法，已不适用**——
> V0 没有小程序 API 可禁止。V0 的真实约束更强也更清晰：

- 🚫 **`core/` 内禁止任何 IO**：
  - 禁止 `fetch` / `XMLHttpRequest` / `WebSocket`（**不得发网络请求**）；
  - 禁止 `node:*`（`node:fs` / `node:path` / `node:crypto` 等）；
  - 禁止 `fs` / `better-sqlite3` / 任何数据库或 ORM 调用；
  - 禁止 `process.env` 读取配置、禁止 `console` 之外的宿主全局；
  - 禁止 `localStorage` / `IndexedDB`（浏览器存储同样是 IO）；
  - **一句话：`core/` 必须是纯函数式的计算层，同样的输入必得同样的输出。**
- ✅ **存储与外部依赖一律通过接口注入**：

  ```ts
  // 形状示意：core 只认接口，不认实现
  interface KVStore { get<T>(k: string): T | undefined; set<T>(k: string, v: T): void }
  interface RuleSource { load(): KnowledgeBundle }   // 后端读 SQLite/文件；测试读内存对象
  interface Clock { today(): string }                // 不读系统时间，日期由注入的时钟提供
  ```

  - 后端把 SQLite 查询结果包成 `RuleSource` 实现；测试端用内存实现；
    未来移动端（RN）用同一份接口、换一个实现——**这就是可测试性与可复用性的共同来源**；
- **这条约束正是"V0 前后端共用 `core/`"的前提**：同一个 `engine/`，
  既被后端 REST 接口调用（权威推算并落库），也被前端调用（表单实时预览），
  因为它是纯计算，放在哪边跑都一样，**不会出现两套算法漂移**（见 [10 §6 TR-5 类风险](./10-技术演进与风险.md)）；
- `core/` 的 package.json 独立，vitest 直接运行（08 §5）；CI 建议加一条静态检查：
  `core/` 目录内不得出现上述禁词（可 grep 实现）。

## 5. 核心模块验收清单

> 按 **V0 / V1** 分列。**V0 全绿的判定标准见 [PRD 08 §2.5](../PRD/08-MVP范围与版本规划.md)。**

### 5.1 V0 必做（`core/engine` + `core/knowledge` + `core/types`）

- [ ] engine：04 §2 示例品类 × 各气候档的组合用例（含保底 0.5、敏感度分级、保守取整）；开封日期缺省默认今天；
- [ ] engine：状态驱动品类输出**窗口**而非单点，且 tips 生效；
- [ ] engine：`reasonText` 与 `expireAt` 逐位一致（PRD 08 §2.5 第 4 条，"可解释性"是 V0 的信任来源）；
- [ ] knowledge：50 类 `shelf_rules.json` + `copywriting.json` 校验通过，每类带依据来源（食品安全红线）；
- [ ] types：`Item` 模型**含提醒字段**（`remindPolicy` / `windowStart` / `windowEndAt`）但 V0 不消费它们；
