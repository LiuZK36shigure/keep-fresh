## 1. 语音解析器 `core/parser`（F-01，规则版）

> 设计约束（11 §6 R5）：V1 用**规则解析**，不用开放大模型——可预期、可纠错、零成本、可单测。

### 1.1 处理流水线

```
识别文本（WechatSI 结果）
  → ① 归一化：全角→半角、繁体→简体、"几"→数字、"昨天/前天/上周X"→日期
  → ② 品类匹配：词典最大匹配（aliases 同义词 → categoryId）
       · 未命中 → 返回"未识别" + 热门品类候选（GWT-01 兜底话术）
  → ③ 实体抽取：数量（"三盒/一箱/3 个"）、开封（"开封了/打开了"）、日期（"今天/昨天/上周二"）
  → ④ 冲突处理：数量>1 → qty；多个日期 → 取最近；口误日期在未来 → 拦截（04 §6）
  → 输出 ParsedRecord { categoryId, qty, buyDate, openedAt, storageLocation?, confidence }
```

### 1.2 词典与规则数据（随知识库远程更新）

```jsonc
// shelf_rules.json 内嵌 aliases；数量/日期词表放 parser 内置 + 可远程覆盖：
{
  "numWords": { "一": 1, "两": 2, "三": 3, "几": 3 },
  "unitWords": { "盒": 1, "箱": 12, "袋": 1, "瓶": 1, "个": 1 },
  "dateWords": { "今天": 0, "昨天": -1, "前天": -2, "上周二": "lastTuesday" },
  "openWords": ["开封", "打开了", "拆了", "开盖"],
  "locationWords": { "冷藏": "fridge", "冷冻": "freezer", "冰箱": "fridge" }
}
```

### 1.3 二次语音纠错（GWT-02）

- 确认页进入"纠错模式"：`parseCorrection("不对，是昨天买的")` → 只更新指定字段；
- 实现：解析器输出字段级 diff，仅替换用户指出的字段，其余保持。

### 1.4 验收映射

| GWT | 实现保障 |
| ---- | ---- |
| GWT-01（3 秒出确认页，无需修改可保存） | 流水线全同步执行；命中 aliases + 默认日期=今天 |
| GWT-03（只说"牛奶"→ 默认今天并标注） | 日期缺省 → buyDate = 今天 + 标注位 |
| GWT-04（识别失败 → 手动表单） | 调用方 catch 后跳 F-02 表单 |
| 准确率 ≥ 85%（常用 50 类） | 词典随知识库迭代；单测覆盖 50 类 × 常见句式（08 §5） |

## 2. 推算引擎 `core/engine`（F-05，04 章三层规则）

### 2.1 日期驱动品类（model: 'date'）

```
输入：categoryRule + openedAt + storageLocation + climate(settings) + ruleVersion
  T0 = rule.T0[location] ?? rule.T0[default]       // ① 品类基线（按存储位置分档）
  T1 = rule.T1[location] ?? rule.T1[default]       // 开封后期限
  base = openedAt ? T1 : T0                        // ② 状态修正（04 §3）
  若 storageLocation ≠ 规则要求 → × storage_mismatch(0.5) + 提示文案
  k = 气候系数组合（04 §4.1，按 sensitivity 分级生效：high 全量 / mid 仅湿度+梅雨 / low 仅高温0.9）
  T = roundDown(base × k, 保守原则取更短期限)        // ③ 气候因子
  expireAt = (openedAt ?? buyDate) + T 天
  confidence = 打分（04 §5.1：品类命中40 + 开封20 + 存储15 + 日期15 + 气候10）
```

**输出**：`{ expireAt, windowEndAt, confidence, reasonText, climateFactors, ruleVersion }`
（reasonText 例："未开封冷藏 7 天 × 夏季高温潮湿 0.64 ≈ 4 天"——**可解释性**是信任的来源，01 §3.1）

### 2.2 状态驱动品类（model: 'state'，04 §7 最小版）

- 不推算精确日期：输出 `window = [buyDate + window[0], buyDate + window[1]]`；
- 提醒由 `checkRhythm` 驱动（检查提醒，见 §3.3）；
- 反直觉规则（香蕉勿冷藏）在确认页展示 tips 一行小字（04 §7.4）；
- 置信度固定 `mid`，详情页明示"状态类物品不承诺精确期限"。

### 2.3 边界情况（04 §6 全表实现要点）

| 情况 | 实现 |
| ---- | ---- |
| 品类不在知识库 | 走自定义模板：用户填期限 → `custom:` 条目，T0=用户值，sensitivity=mid |
| 无网络 | 用本地缓存 KnowledgeBundle（标注 ruleVersion='offline:xxx'） |
| 药品/婴幼儿 | `conservative: true` → 区间展示按下限 + 强提示文案 |
| 冷冻→解冻 | 用户标记后创建"解冻后 24h"倒计时（复用 opened 计时器模型） |
| 补录过期 | 不阻断保存，status 直接置 `expired`，横幅提示检查实物 |

### 2.4 修改反馈回路（F-06，校准样本）

```
用户修改到期日 + 选原因 → 端侧记录 CalibrationSample {
  categoryId, climateFactors, direction: 'shorter|longer', reason, ruleVersion
} → 本地暂存 → P1 匿名上报 calibration 集合 → 每周人工审核调参（04 §5.3）
```

## 3. 提醒生成器 `core/reminder`（F-07，05 章时机矩阵）

### 3.1 端侧每日计算（App 内横幅，通道 B）

```
输入：items（本地）+ settings.remind + 今天日期
1. 对每个非 disposed 物品，按状态机计算「今天该不该提醒」：
   - 日期驱动：距 expireAt 进入分档窗口（05 §1.2）→ expiring；
     超过 expireAt → expired；openedAt 存在 → opened 计时节点（T1×50% / 到期前6h）
   - 状态驱动：checkRhythm 命中今天 → check
2. 去重：同物品同类型今天已提醒过（Item.reminders）→ 跳过
3. 合并：同用户当天 ≥3 条 → 生成 1 条汇总（05 §1.3）；限频：单发 ≤3 条（05 §3）
4. 输出今日横幅数据 → reminderStore → 首页渲染
5. 触达后写入 Item.reminders（sentVia: 'banner'）→ 下次不重复
```

### 3.2 订阅消息计划上报（通道 A 的数据源）

- 触发点：记录成功页授权（05 §2 黄金时机）+ 设置页手动订阅；
- 上报内容（脱敏，01 §3）：`itemId + name + expireAt + remindType + windowStart + copyKey`；
- 端侧同步状态标记 `kf_remind_synced`，失败静默重试（≤3 次），不阻塞记录；
- 物品处置/删除/延后 → 同步更新/取消云端 remind_plan（03 §4 幂等配合）。

### 3.3 检查提醒（状态驱动，V1 第四种提醒，05 §1.1）

- 触发节奏来自 `rule.checkRhythm`（如草莓 `[2]`：第 2 天看一眼）；
- 文案用 `copyKey: 'check.fruit'`（"草莓第 2 天啦，看一眼有没有发霉～"）；
- 不承诺精确期限 → 该品类**不进入**"修改推算比例 ≤ 20%"统计（08 §2.3 注，实现时埋点打标排除）。

### 3.4 防轰炸与沉默策略（05 §3）

| 策略 | 实现 |
| ---- | ---- |
| 同物品不重复 | Item.reminders 去重 + 升级节点（临期→过期）才再提醒 |
| 日限频 | 端侧横幅 + 云端订阅消息**双端各自限频**（3 单发 + 1 汇总） |
| 免打扰 | 横幅渲染与云函数发送都跳过 quietHours（云端以用户 settings 为准） |
| 沉默降频 | 连续 3 次未点击某类型 → 该类型降频为 7 天一次（端侧记 interaction 计数） |
| 延后 3 天 | 重排提醒窗口；postponeLeft 减一，≤2 次（05 §5） |

## 4. 模块依赖与纯 TS 约束

```
core/
├── parser/       ← 只依赖词典数据（JSON）
├── engine/       ← 依赖 knowledge(规则) + types
├── reminder/     ← 依赖 items + knowledge + types
├── knowledge/    ← 依赖 storage 抽象接口（见下）
└── types/        ← 纯类型 + Zod/手写校验器（V1 手写足够）
```

**纯 TS 约束（架构铁律 3）**：

- 禁止 `import wx` / `getApp()` / 任何小程序 API 进入 `core/`；
- 本地存储通过**接口注入**：`interface KVStore { get(k): T; set(k, v): void }`，
  小程序端用 StorageService 实现，测试端用内存实现——这就是可测试性的来源；
- `core/` 的 package.json 独立，vitest 直接运行（08 §5）。
