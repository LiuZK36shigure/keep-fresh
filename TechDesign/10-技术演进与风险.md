| 版本 | 技术验证目标（PRD 08 §3 退出标准的技术版） | 关键技术增量 |

## 2. V0 技术交付清单（对齐 PRD 08 §2.2 的 P0 功能）

| P0 功能 | 技术交付 |

| 一条命令起前后端 | monorepo（pnpm workspace）+ `pnpm dev` 并行起 `apps/web`(:5173) 与 `apps/server`(:3000) |

| 推算（三层引擎 + 依据展示） | `core/engine`（双模型：`date` / `state`）+ `shelf_rules.json`（50 类）+ `reasonText` / 置信度输出；**前后端共用同一份 core** |
| 完整管理视图（分组/排序/筛选/搜索） | 前端列表：分组（冷藏/冷冻/储物柜/药箱/化妆台/其他）+ 排序（到期日/购买日）+ 筛选（临期/过期/已开封）+ 搜索；服务端分页查询（按 `user_id` 过滤） |
| 详情 + 手动修改推算 | 详情页（全字段 + 推算依据）+ 修改到期日并落 `calibration_samples`（V0 只记不分析，[05 §2.4](./05-核心模块设计.md)） |
| 处置 + 5 秒撤销 | 状态机（`used` / `discarded` / `gifted`）+ 软删除 + 撤销窗口 |
| 极简统计（在库 / 本月处置 / 避免浪费件数） | 服务端聚合查询（`COUNT` by `user_id`），**不做图表** |
| 知识库（50 类 JSON） | `shelf_rules.json` + `copywriting.json` 服务端持有 + 启动时 schema 校验 + 版本号 |
| 设置子集（气候档 / 默认存储位置 / 修改密码） | `settings` 表 + 前端设置页；**无提醒窗、无推送开关**（V1） |

| 工程与质量 | `pnpm typecheck` + `pnpm test`（vitest，`core/` 覆盖率 ≥ 80%）+ `core/` 零 IO 静态检查 |

**V0 明确不做（技术侧）**：语音录入与 ASR（`core/parser` 空占位）、提醒生成器与一切推送通道
（`core/reminder` 空占位，`NoopNotifier`）、定时任务/Cron、天气 API、PWA/Service Worker、
拍照/OCR、家庭共享、金额统计、公网部署/域名/备案、云函数与任何云开发服务
——与 [PRD 08 §2.3](../PRD/08-MVP范围与版本规划.md) 严格一致，避免技术提前堆砌。

> ⚠️ 与原文的关键差异：原文的 V1.0 清单以**语音录入 + 四类提醒 + 云函数**为骨架；
> V0 把它们**全部移出**，换成**账户 + 同步 + 管理视图 + 服务端权威**——
> 净效果是"**少了一整套通知链路，多了一整套持久化与账户链路**"。

## 3. 各阶段关键技术设计要点

### 3.1 家庭共享（F-12）——【V2】最大的架构增量

> ⚠️ 原文标注 V1.1 并称"共享物品以**云端为权威**（多写者），与本地优先的'端侧为权威'相反"。
> **这半句已作废**：V0 起**服务端 SQLite 就已经是唯一权威**，"端侧为权威"的前提不存在了——
> 因此家庭共享在技术上**比原文更简单**（不必再设计"端权威 ↔ 云权威"的双向切换）。

- 共享物品与个人物品**同一张表**，用 `space_id`（或 `family_id`）区分；个人物品的 `space_id` 为空；
- 多写者冲突：同字段同时编辑 → 后保存者覆盖 + 合并备注；离线编辑 → 本地队列 + 联网合并（乐观锁 `updatedAt`）；
- 数据集合：`families`（空间）+ `memberships`（成员 + 角色）+ 物品归属改由 `space_id` 表达；
- 权限：服务端校验**成员关系**（与 V0 的 `user_id` 归属校验同源，见 [09 §2.5](./09-安全与隐私架构.md)）；邀请码 24h 过期；成员可退出；
- 提醒分发：家庭成员各自配置自己的提醒策略（V1 已有提醒链路，V2 按成员拆分）；
- **免费/付费墙**：家庭共享 = 付费卖点 → V2 内测验证后与支付一并开闸。

### 3.2 自动气候（F-13 自动档）——【V1】

- 天气 API：和风天气**免费版**（QPS 限额内）；服务端定时（如每 6 小时）拉取城市天气并落库
  （⚠️ 不再有"端侧定时拉取"——V0 起服务端为权威，且 V1 有了常开的提醒链路；
  另注：原文"和风天气免费版"的表述已过时，需在 V1 实现时重新核实，见 [12 §5](./12-Web优先方案（平台迁移决策）.md)）；
- **降级链**：API 失败/超时/未授权定位 → 回退**手动气候档**（04 §4.3，绝不因 API 故障影响记录）；
- 城市来源：用户自填城市 → 可选地理定位（拒绝则维持手动）；
- 实现位置：`core/engine` **不接受网络输入**——气候档以参数传入（`climate`），
  取数由服务端 adapter 负责注入，这正是 V0 的"零 IO 约束"带来的红利。

### 3.3 OCR（F-14 试点）——【V2】

- 识别包装日期文字 → 候选日期填入表单（人工确认后生效）；V0/V1 均不做拍照，故本项后置；
- 定位：**辅助录入**，不自动信任识别结果（食品安全红线 R1 不破）；
- 依赖：拍照记录（V1）先上线；实现位置改为**服务端**（V0 起服务端为权威，客户端不再持有照片权威副本）。

### 3.4 订阅支付——【V2；V0/V1 明确不涉及支付】

> 🚫 **V0 与 V1 都不涉及任何支付能力**：V0 是自用工具，V1 是"提醒闭环"验证版，
> 二者的退出标准都只看功能与行为指标（PRD 08 §3），**没有付费转化目标**（付费是 V2 的退出标准）。

- 前置决策：主体资质（个体工商户/企业）——**V0/V1 不注册任何主体**，此决策点推迟到 **V2 启动时**；
- 技术形态（V2 再定）：因已离开微信生态，**微信支付 `cloudPay` 云函数方案已作废**；
  V2 的候选是 Web 侧第三方支付（Stripe / 支付宝当面付等）或应用商店内购（若那时已有 RN App），
  具体方案在 V2 启动时单独立章决策；
- 订阅状态：服务端为权威（`subscriptions` 表），前端只读；
- ~~⚠️ 主体硬约束：`cloudPay` 需要微信支付商户号，个人主体小程序不可开通~~ 🚫 随小程序方案作废。

### 3.5 ~~服务号订阅通知~~——🚫【整节作废】

> ❌ **本节整体作废。** 放弃小程序后，"服务号订阅通知"这条渠道**不存在**：
> 它依赖微信生态（服务号注册认证 + 与小程序绑定 + 模板消息），而 V0/V1 路线是
> **Web（PC → PWA）→ React Native**，不再经过任何微信渠道。
>
> 同时作废的还有：
> - "小程序订阅消息"（一次性配额机制）——[12 章 §1](./12-Web优先方案（平台迁移决策）.md) 已说明它正是放弃小程序的主因；
> - 与之绑定的"企业/个体工商户主体 + 300 元/年认证"前置决策（V0/V1 不注册主体）；
> - `service_msg` 云函数、模板字段约束、跳回小程序的链路设计。
>
> **V1 的提醒渠道**改为：**Web Push（VAPID）+ 页内提醒**，可选第三方通道（Bark / ntfy）兜底
> —— 见 [12 章 §3](./12-Web优先方案（平台迁移决策）.md) 与 [PRD 05 提醒策略](../PRD/05-提醒策略.md)。

## 4. V2 候选：React Native / Expo 原生 App（替代原文的 Flutter）

> 🛑 **原文标题"V2 候选：Flutter 原生 App"的结论是错的，已重写。**
> 原表把 `core/` 标为"✅ 直接复用 —— 纯 TS → Dart 翻译成本低"——**这不成立**：
> **Flutter 用 Dart，TypeScript 不能直接复用**，所谓"翻译成本低"其实是**逐行重写一整层算法**。
> [12 章 §2](./12-Web优先方案（平台迁移决策）.md) 已把演进目标纠正为 **React Native / Expo**：
> 它跑 JS/TS 运行时，`core/` 是**原样引入依赖**而不是"翻译"，这才是真实的复用链。

**触发条件**：数据与访谈证实"移动端记录/提醒体验是留存瓶颈"（对应 PRD 08 §3 的 V2 退出标准）。

| 迁移项 | 复用/重写 | 说明 |
| ---- | ---- | ---- |
| `core/`（engine / knowledge / types；V1 起含 parser / reminder） | ✅ **原样复用（真正的直接复用）** | 纯 TS，RN 与 Node 同一语言、同一包管理；`core/` 零 IO 约束（[05 §4](./05-核心模块设计.md)）保证它不依赖任何宿主 —— 换实现只需换注入的 adapter |
| 知识库 / 文案 JSON | ✅ 直接复用 | 与平台无关 |
| 数据模型（`Item` 等）与校验器 | ✅ 直接复用 | 同一份 TS 类型 + 校验器，双端不会解析出两份 schema |
| REST 接口 `/api/v1/*` | ✅ **直接复用，零改动** | V0 就已冻结契约（§4.1），移动端换 HTTP 客户端即可指向同一后端 |
| 服务端 | ✅ 基本不变 | 换的是推送发送实现（APNs/FCM/Expo Push），不是协议 |
| UI 层 | ❌ 重写 | 这是换平台的必然成本（用 RN 组件重做；样式可从 Web 的设计令牌迁移色值/圆角/间距） |
| 语音识别 | ⚠️ 换 adapter | V1 的 `VoiceInput` 接口不变，实现换为系统 ASR（iOS Speech / Android 系统） |
| 账号体系 | ✅ 直接复用 | ⚠️ **这是 Web 路线的一个意外红利**：V0 起就是自建用户名 + 密码（argon2id）+ Bearer token，**不存在"离开小程序生态要重建账号"的代价**（原文 §4 的"需自建账号"一行随之作废） |
| 端云调用 | ✅ **REST，无需新增接入层** | ⚠️ 原文写"小程序走 `wx.cloud.callFunction`；App/多端改走 REST"——**V0 起就没有云函数了，REST 是一开始就定好的主线**，不存在"未来加 HTTP 接入层"这项迁移工作（见 §4.1） |

**技术前置准备（V0 期间零成本，迁移时才兑现收益）**：
`core/` 保持纯净（[05 §4](./05-核心模块设计.md) 零 IO 约束）就是为这一天准备的；
知识库 schema 稳定（04 §3）避免未来双端解析两份 schema；
**REST 契约在 V0 就冻结**（`/api/v1/*`，见 §4.1）——这条是 V0 留下的最有价值的接口遗产。

### 4.1 更远的多端：Web/桌面/鸿蒙/移动端

> 核心逻辑是纯 TS（[05 §4](./05-核心模块设计.md)）+ 配置是 JSON（06）→ 这两个资产与平台无关，
> 多端迁移 = "**重写 UI + 替换平台能力（语音/推送/支付）**"。
>
> ⭐ **之所以这里不再需要"增加 HTTP 接入层"这一步，是因为 V0 一开始就把接口定成了 REST**：
> **V0 就冻结 `/api/v1/*` 契约（JSON + `Authorization: Bearer <token>`，见 TechDesign 03）**，
> 前端与后端之间从来就是 HTTP。这是"V0 保留接口"策略最直接的回报——
> 原文的多端表里"端云调用改 HTTP（云开发 HTTP API 服务或 `@cloudbase/js-sdk`）"一行**整体作废**，
> 替换为"**REST API 直接复用（契约 V0 已定）**"。

| 目标端 | 核心逻辑复用 | 主要工作 |
| ---- | ---- | ---- |
| **移动端（RN / Expo，V2 主候选）** | `core/` 纯 TS **原样打包复用** | UI 重写（RN 组件）；**REST API 直接复用（契约 V0 已定，见 TechDesign 03）**；语音换系统 ASR；推送换 APNs/FCM/Expo Push |
| Web（已是 V0/V1 主形态） | `core/` 纯 TS 直接打包复用 | —（V0 已完成；V1 只加 PWA 与推送） |
| 桌面（Windows/macOS/Linux） | `core/` 纯 TS 直接复用（Electron/Tauri 或 Node 包装） | UI 重写；推送换系统通知；语音换系统 ASR；**REST API 直接复用** |
| 鸿蒙（HarmonyOS） | `core/` 与 ArkTS（TS 超集）兼容性高 | UI 重写（ArkUI）；推送换华为推送；支付换华为支付；**REST API 直接复用** |

**现在就做、零成本的三件事**（迁移时才兑现收益）：

1. **REST 契约冻结**：V0 即定 `/api/v1/*` + `Bearer token`，**版本前缀不可省**；
   前端所有 HTTP 调用收口到 `apps/web/src/api/` 一处（未来换客户端只改这一层）；
2. **`core/` 纯净约束不放水**（[05 §4](./05-核心模块设计.md)）：这是多端复用的根基；
3. **知识库/文案 schema 冻结**：稳定后不做破坏性变更，只做兼容性新增（04 §6 迁移纪律）。

## 5. 备选方案（触发条件明确，不提前行动）

> ⚠️ 原文备选表 4 条中有 3 条是**小程序时代条目**，已删除并替换为 V0/V1 真正可能发生的备选。
> 删除条目：~~后端迁出云开发~~（V0 就没有云开发）、~~引入跨端框架 Taro~~（V0 是纯 Web，无多端诉求）、
> ~~自建 ASR（WechatSI 额度不足）~~（WechatSI 已作废，ASR 属 V1 事项）。

| 备选 | 触发条件 | 方案 |
| ---- | ---- | ---- |
| **SQLite → Postgres**（服务端数据库升级） | V1 上公网多用户后并发写冲突明显 / 需要多实例部署 | 因 V0 已有 `schema_version` + 顺序迁移脚本，切换成本可控；`core/` 与 REST 契约不受影响 |
| **前端状态管理升级**（Zustand → TanStack Query / Redux） | 服务端为权威后，缓存失效与并发刷新逻辑开始重复手写 | 引入数据请求缓存层；`core/` 不动，只换 `apps/web` 的数据获取方式 |
| **UI 组件库引入** | 自研组件数量超过 ~15 个、无障碍与键盘操作开始出错 | 引入轻量无样式库（headless，如 Radix 原语）+ 保留设计令牌——**但 V0 明确不引入**（02 §5 生活化基调） |
| **后端框架替换**（Hono → Fastify/Express） | Hono 的中间件或 SQLite 集成成为瓶颈 | 路由层薄，替换只影响 `apps/server`；`core/` 与 REST 契约不变 |
| **自建推送通道** | V1 的 Web Push 在 iOS 送达不可靠 | 第三方通道聚合（Bark / ntfy）或自建 APNs/FCM（V2 有 RN App 后） |
| **备份方案升级**（手动复制 SQLite → 定时快照） | 出现一次真实的误删/损坏事故 | 用系统任务计划做每日文件快照（**仍不引入 Cron 服务**，V0 期不引入常开进程） |

## 6. 关键技术风险与对策

### 6.1 V0 技术风险（**新增，V0 期间每周必看**）

| # | 风险 | 概率/影响 | 对策 | 监控信号 |
| ---- | ---- | ---- | ---- | ---- |
| **TR-V0-1** | **账户安全：越权与撞库**（V0 头号安全问题） | 中/**高** | 所有写接口 `WHERE id=? AND user_id=?`，`user_id` **只取自会话**；itemId 用随机 ID；密码 argon2id；登录失败指数退避 + 注册用户名 DB 级唯一约束；`.env` 与 SQLite 文件进 `.gitignore`；日志不打密码/token。**完整清单见 [09 §2.5](./09-安全与隐私架构.md)** | PRD 08 §2.5 第 2 条的**越权测试必须绿**；`.gitignore` 自查；日志抽样 |
| **TR-V0-2** | **SQLite 并发与备份**：写冲突（`SQLITE_BUSY`）、数据文件损坏、误删 | 中/中 | `better-sqlite3` + **WAL 模式** + `busy_timeout`；单进程单写入者（V0 本机场景足够）；写操作包事务；**每日快照备份**（复制文件到本机另一目录，不进仓库）；崩溃后能从备份恢复 | 出现 `SQLITE_BUSY` 的次数；备份文件日期是否连续；`pnpm test` 中迁移脚本的前后兼容用例 |
| **TR-V0-3** | **`core/` 与前端逻辑漂移**：前端图省事自己算了一遍到期日，或绕过接口直接改 UI 状态 | 中/中 | `core/` 零 IO 约束（[05 §4](./05-核心模块设计.md)）→ 前后端**唯一算法来源**；CI 静态检查 `core/` 内禁词；前端一律走 `/api/v1/*`，不复制推算公式；**同一份用例同时跑前后端** | 代码 review 中前端出现"天数 × 系数"类算式即告警；`core/` 覆盖率是否下滑 |
| **TR-V0-4** | **单人开发中断**（考试/生病/工作忙）：V0 工期 3~4 周，中断即断档 | **高**/中 | 全文档化（本套文档 + 代码注释）；**每阶段完成定义明确**（[11 §3](./11-开工指引与命令.md)），半成品不留半截；范围锁死（PRD 08 §2.2/§2.3），中断后不重新规划只继续；Git 全量备份 + 每日推送；`docs/tech-debt.md` 显式登记 | 连续 7 天无提交即触发"降范围"预案（不是加班）；`pnpm test` 在中断后仍能全绿 |
| **TR-V0-5** | 知识库 50 类的**依据质量**（编码错误 → 推算误导） | 中/高 | 保守原则（取更短期限）+ 置信度表达（04 §5）；每类必带依据来源（食品安全红线）；`reasonText` 让人能复查；详情页允许手动修改并落校准样本 | 该品类被手动修改的比例；`reasonText` 与实际不符的举报 |
