## 一、当前技术决策（速览）

> **平台决策（用户暂定）**：V1 使用**微信小程序**（PRD 09 §3.1），V2 视数据决定是否转 Flutter 原生 App。

| # | 决策点 | 结论 | 关键理由 | PRD 依据 |
| ---- | ---- | ---- | ---- | ---- |
| T-01 | 客户端框架 | **微信小程序原生 + TypeScript**（不用 Taro/uni-app） | 平台原生能力（订阅消息、语音插件）零损耗；核心逻辑抽成**框架无关纯 TS 模块**，V2 转 Flutter 时可复用 | 09 §3.1 |
| T-02 | 状态管理 | `mobx-miniprogram`（轻量、TS 友好） | 数据流简单（本地为主），不需要重型框架 | — |
| T-03 | 语音识别 | **微信同声传译插件（WechatSI）**，端侧优先 | 免费额度内、免自建 ASR；失败降级手动表单 | 09 §3.2 |
| T-04 | 后端 | **微信云开发 Serverless**（云函数 + 云数据库 + 云存储 + 定时触发器） | 零运维、月成本 ≈ 0、天然微信身份（openid）、定时推送链路完整 | 09 §3.4 / 07 §5 |
| T-05 | 数据架构 | **本地优先（Local-First）**：物品明细、照片默认只存端侧 | 隐私是信任资产（差异化卖点）；离线可用（07 §3）；服务器事故面最小 | 07 §1 / 11 §9 |
| T-06 | 推算引擎 | **端侧纯 TS 规则引擎**（三层规则 + 日期/状态双模型），规则放远程 JSON | 必须离线可用（07 §3）；规则可远程更新不发版（07 §5）；可单元测试 | 04 / 07 §5 |
| T-07 | 提醒渠道 | 端侧**App 内横幅兜底** + 云函数**定时发订阅消息** | 订阅消息一次性授权受限，横幅保证打开必见；云函数每日定时计算（07 §2） | 05 §2 / 07 §2 |
| T-08 | 气候数据 | V1 手动气候档；V1.2 接**和风天气免费版**（失败自动回退手动） | 冷启动不依赖第三方 API，避免单点故障 | 04 §4 / 09 §3.3 |
| T-09 | 埋点 | 自建极简匿名事件上报（本地队列批量）+ 小程序自带数据分析 | 一人公司也要数据（03 §4），但不做复杂画像系统 | 03 §4 |
| T-10 | 工程化 | monorepo（miniprogram / cloudfunctions / shared / config）+ `miniprogram-ci` 自动上传 + vitest 单测 | 纯 TS 共享层可脱离小程序运行时测试，是质量的保险丝 | 09 §4 |
| T-11 | 支付/订阅 | V1 不做；V1.2 用**微信支付云函数**实现订阅 | 先验证价值再验证付费（10 §1） | 10 §1.1 |

## 二、架构一图流

```
┌───────────────────────────────────────────────────────────────┐
│ 客户端：微信小程序（本地优先，可离线）                            │
│                                                                │
│  ┌───────────┐  ┌───────────┐  ┌───────────────────────────┐  │
│  │ UI 层      │  │ 状态层     │  │ 核心逻辑层（纯 TS，可单测） │  │
│  │ WXML/WXSS │→ │ mobx store│→ │ 语音解析器 / 推算引擎       │  │
│  │ 自定义组件 │  │           │  │ 提醒生成器 / 知识库管理      │  │
│  └───────────┘  └───────────┘  └───────────────────────────┘  │
│                                                                │
│  本地存储：物品记录 / 照片(文件系统) / 知识库缓存 / 埋点队列       │
└──────────────┬────────────────────────────────────────────────┘
               │ wx.cloud.callFunction（仅必要数据，不传物品明细）
┌──────────────▼────────────────────────────────────────────────┐
│ 微信云开发（Serverless，零运维）                                 │
│                                                                │
│  云函数：reminder(定时) / subscribe / knowledge / analytics     │
│          family(P1) / export(P1) / pay(V1.2)                   │
│  云数据库：users / remind_plans / families(P1) / events         │
│            calibration(P1) / configs / knowledge_versions      │
│  云存储：shelf_rules.json / copywriting.json / 可选备份(P1)      │
│  定时触发器：每日提醒计算（全部用户 ≤ 1 分钟，07 §2）              │
└────────────────────────────────────────────────────────────────┘
```

**一句话架构**：客户端是数据的"家"，服务器是"配置分发 + 消息通道 + 匿名统计"，二者职责边界清晰。

## 四、三条设计铁律（源自 PRD，贯穿全部文档）

1. **本地优先，云端最小**：能放端侧的数据绝不上云；上云的数据必须可脱敏、可删除、可解释（07 §1）。
2. **配置大于开发**：规则、文案、开关全部远程可更新，一个人来不及发版救火（07 §5、09 铁律 3）。
3. **逻辑与平台解耦**：核心逻辑层必须是"不依赖小程序运行时"的纯 TS 模块——
   既为了单元测试，也为了 V2 转 Flutter 时能直接复用（T-01）。
