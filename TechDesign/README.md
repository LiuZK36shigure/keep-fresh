### 1.1 V0 技术决策表

| # | 决策点 | 结论 | 关键理由 | PRD 依据 |
| ---- | ---- | ---- | ---- | ---- |
| T-01 | **前端** | **Vite + React + TypeScript**，仅 **PC 桌面浏览器** | V0 定位是"客户辅助端"；仍按响应式写，避免 V1 重写 | 08 §2.1 |
| T-02 | **后端** | **本地 Node + Hono + SQLite**（`better-sqlite3`） | 零部署、零第三方账号、零备案；`sqlite3` 直接看数据；`pnpm dev` 一条命令起 | 08 §2.1 |
| T-03 | **数据权威** | **服务端 SQLite 为唯一权威**：账户下的物资通过服务端同步 | 有账户就必然有同步；单端使用不存在冲突，复杂度最低 | 08 §2.4 |
| T-04 | **账户与鉴权** | **用户名 + 密码**（argon2id）；不透明 token + `sessions` 表；所有查询带 `user_id` | 不依赖邮件/短信服务；越权是 V0 头号安全问题 | TechDesign 03 §4 |
| T-05 | **推算引擎** | **`packages/core` 纯 TS**，**由服务端唯一计算**，前端只展示 `reasonText` | 一份代码、一处计算、可单测；避免前后端双算法漂移 | PRD 04 |
| T-06 | **API 契约** | **REST `/api/v1/*`** + JSON + Bearer token；Zod schema 为唯一真源 | **V1 的移动端直接复用同一套接口**（"保留接口"的落地） | 08 §2.4 |
| T-07 | **状态管理** | 轻量（Zustand 或 React Context） | 数据以服务端集合为主，前端不需要重型框架 | — |
| T-08 | **知识库** | `config/shelf_rules.json`（50 类）+ 启动时 Zod 校验；改规则重启即生效 | 逻辑与数据分离；坏规则宁可起不来 | 07 §5 / TechDesign 06 |
| T-09 | **气候数据** | **V0 手动三档**（夏季/潮湿/梅雨）+ 未设置时 `k = 0.9` 保守值 | 不依赖任何第三方 API | PRD 04 §4.2 |
| T-10 | **工程化** | monorepo（`packages/core` + `apps/web` + `apps/server` + `config/`）+ vitest + GitHub Actions（**仅 CI**） | 纯 TS 共享层可脱离运行时测试，是质量的保险丝 | TechDesign 08 |
| T-11 | **埋点** | **V0 只写服务端结构化日志**，不做上报系统与仪表盘 | V0 的用户就是你自己，看日志比看仪表盘快 | TechDesign 04 §5 |
| T-12 | **备份** | 拷贝 `data/keepfresh.db`（SQLite 单文件） | 零成本、零工具 | TechDesign 04 §6 |

## 二、架构一图流（V0）

```
┌───────────────────────────────────────────────────────────────┐
│  前端：apps/web（Vite + React + TS，PC 桌面浏览器）              │
│    pages/ 登录 · 物资列表 · 详情 · 新增编辑 · 统计 · 设置          │
│    api/   唯一的网络出口（REST 客户端）                           │
│    ⚠️ 不算到期日、不判断状态、不持有权威数据                        │
└───────────────────────┬───────────────────────────────────────┘
                        │  REST /api/v1（JSON + Bearer token）
                        │  ← V1 的手机端走同一套契约，不改协议
┌───────────────────────▼───────────────────────────────────────┐
│  后端：apps/server（Node + Hono + SQLite）—— 本地运行，无需部署   │
│    routes/ auth · items · categories · settings · stats         │
│    middleware/ auth（注入 userId）· validate（Zod）· error        │
│    services/ 业务逻辑，签名第一参数恒为 userId（防越权）            │
│    db/       better-sqlite3 + migrations（顺序 SQL）             │
└───────────────────────┬───────────────────────────────────────┘
                        │
┌───────────────────────▼───────────────────────────────────────┐
│  packages/core（纯 TS，前后端共用 —— V0 最有价值的资产）           │
│    engine/  三层推算引擎（日期/状态双模型）                        │
│    rules/   知识库加载与校验                                     │
│    schemas/ Zod：领域类型 + API 契约（唯一真源）                   │
│    parser/ 【V1 预留】reminder/ 【V1 预留】                       │
│    ⚠️ 无 fetch / 无 node:* / 无 IO —— 所以未来 React Native 能直接复用 │
└───────────────────────────────────────────────────────────────┘
```

**一句话架构**：**服务端 SQLite 是数据的家；前端是可替换的壳。**

## 四、三条设计铁律（贯穿全部文档）

1. **服务端为权威，逻辑只有一份**
   物资数据只存服务端 SQLite；推算只在 `packages/core/engine` 算一次，前端只展示结果。
   *（2026-08 修正：原表述为"本地优先，云端最小"。V0 有账户与同步，端侧权威会立刻带来冲突合并问题——那是 V2 才需要的。）*

2. **配置大于开发**
   品类规则、文案是 JSON，改规则不发版；但**必须启动时校验**，坏规则宁可起不来。

3. **逻辑与平台解耦**
   `packages/core` 必须是纯计算（无 `fetch` / 无 `node:*` / 无 IO / 不读系统时钟）。
   这既为了可单测，也为了 **V1 做移动端时能直接复用**——
   换 UI 是必然成本，但换 UI 时不用重写业务逻辑，这个差别决定 V1 是"重写一遍"还是"接一块屏"。
   *（2026-08 修正：原表述称"转 Flutter 可直接复用"是错的，Flutter 用 Dart；正确目标是 React Native / Expo。）*
