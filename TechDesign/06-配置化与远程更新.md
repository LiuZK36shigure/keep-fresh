# 06 · 配置化与远程更新（V0：本地文件 + 启动时校验）

> 📌 **V0 生效范围（2026-08 范围收缩后重写关键部分）**：
> **机制有效，但分发方式变了**——V0 的服务端就在本机，
> 所以"远程更新"退化为**"改本地 JSON 文件 + 重启服务端"**（前端刷新即生效），
> **不需要云存储、不需要版本比对接口、不需要灰度发布**。
>
> 仍然有效的设计：**配置资产清单（§1）、schema 校验先行、版本号与 `ruleVersion` 可追溯、禁止词扫描**。
> **推迟到 V1**：远程拉取链路（§2 的云端版本比较）、灰度与回滚（§3）。
>
> 一人公司的生命线（09 铁律 2："可配置 > 可开发"）：规则、文案全部外置为 JSON，
> **改一个 JSON 能解决的事，绝不改代码**。
>
> **版本号**：**V0**（=P0，当前）/ **V1**（=P1）/ **V2**（=P2）。

---

## 1. 配置资产清单

| 配置 | 文件名 | 内容 | 更新频率 | V0 影响面 |
| ---- | ---- | ---- | ---- | ---- |
| **品类知识库** | `config/shelf_rules.json` | 品类基线 + 气候系数 + 词典（`aliases`） | 每周（审核后） | **推算（V0 核心）**、表单品类搜索 |
| **文案库** | `config/copywriting.json` | 生活化文案（空状态、确认提示、正向反馈、免责） | 按需 | 界面与反馈 |
| 品类图标映射 | `config/category_icons.json` | 品类 → 图标/emoji | 按需 | 展示 |
| 紧急公告 | `config/announcement.json` | 顶部公告（知识库更新日志、免责提醒） | 按需 | 展示 |
| ~~功能开关~~ | ~~`feature_flags.json`~~ | — | — | ⏸ **V0 不需要**（单人单端，改代码比配开关快）；V1 再引入 |

> 所有配置**必须带 `version` + `publishedAt`**。
> V0 的版本号用途**不是"比对增量"**，而是**写进每条记录的 `estimate.ruleVersion`**，
> 让"这条推算当时是按哪版规则算的"永远可查（见 [04 §6](./04-数据模型与存储.md)）。

## 2. 加载链路（V0：本地文件 + 启动时校验）

```
服务端启动
  → 读取 config/shelf_rules.json + config/copywriting.json
  → Zod schema 校验（id 唯一、T0/T1 非负、aliases 非空、T1 允许区间/null、禁止词扫描）
  → ✅ 通过 → 载入内存，版本号写入响应中
  → ❌ 失败 → 【启动失败】并打印具体错误行
```

**细节要求**：

1. **校验先行，宁可不启动**：V0 的"用户"就是你自己，
   与其带着一条坏规则算出一堆错误日期，**不如直接起不来**——这是 V0 特有的取舍
   （V1 有真实用户后，才需要"校验失败视为无更新、保留旧版本"的容错策略）；
2. **改规则流程**：编辑 JSON → `pnpm validate:config` → **重启服务端** → 前端刷新即生效；
   **不需要发版、不需要部署、不需要灰度**；
3. **历史记录不受影响**：已在库的 `estimate` 是**写入时的快照**，
   改规则**不会回溯修改**老记录；如需让老记录用新规则重算，走"改气候档触发的批量重算"这条路
   （见 [03 §4.3](./03-服务端技术栈.md)），或直接手动改单条的到期日；
4. **通知面**：知识库版本号在设置页展示，可查"当前用的是哪一版"。

> ⚠️ **与旧版的差别**：原设计是"小程序启动 → 比对云端版本 → 拉取 → 原子写 `wx.setStorageSync`"，
> 这套链路**已随小程序作废**。V0 没有"端侧缓存"这个概念——
> 配置在**服务端**加载，前端通过 `GET /api/v1/knowledge/rules` 读取（若需要展示）。

## 3. 发布流程（V0：改本地文件；V1：远程分发）

### V0 流程（当前）

```
编辑 config/shelf_rules.json（Git 管理，提交信息写清改了什么）
  → pnpm validate:config
      · Zod schema 校验 + 禁止词扫描（05 §4 惊吓词表）+ 版本号递增检查
  → ✅ 通过 → 重启服务端 → 前端刷新即生效
  → ❌ 失败 → 修 JSON，服务端本来就起不来
```

**回滚**：`git checkout config/shelf_rules.json` —— **Git 就是版本管理**，不需要"保留最近 5 个版本"那套机制。

### V1 流程（公网化后）

```
改 JSON → validate → 部署到静态托管 → 客户端拉取 → 灰度 → 监控 → 异常回滚
```

> ⏸ **V0 不实现灰度发布、不实现远程拉取、不实现自动回滚**——
> 那些机制的价值在于"一次改错会影响很多用户"，而 V0 只有你自己。

## 4. 功能开关（Feature Flag）—— ⏸ V0 不需要

> V0 **不引入 feature flag**。理由：单人单端，**改一行代码重启比配开关更快**，
> 而且开关本身要维护、要文档化、三个月后还会看不懂。
>
> 原 `feature_flags.json` 的内容已整体作废（含 `remind.channel.subscribe`、
> `remind.channel.service_account`、`voice.provider: "wechatsi"` 等小程序时代条目）。

**V1 引入时的规则**（先记下来，届时别再犯）：

- 规则：**新功能默认关 → 灰度开 → 全量开**；出问题先关开关，再慢慢修；
- 每个 flag **必须带注释用途与负责人**（就是自己），防止三个月后看不懂；
- **只给"出问题会影响用户"的功能加开关**，不要给每个功能都加。

## 5. 配置与代码的关系（边界约定 · V0 有效）

| 内容 | 放配置（JSON） | 放代码（TS） |
| ---- | ---- | ---- |
| 品类基线、气候系数、词典（`aliases`） | ✅ | ❌ |
| 文案模板 | ✅ | ❌ |
| 提醒时机分档表（05 §1.2） | ✅（V1 并入 `shelf_rules` 或独立 `timing.json`） | ❌ |
| 解析算法流程、引擎计算逻辑 | ❌ | ✅（`packages/core/parser`、`engine`） |
| 数据模型结构 | ❌（迁移函数必须代码化） | ✅ |
| 用户设置（气候档、默认存储位置） | ❌ | ✅（存数据库，不是配置文件） |

> 判定标准（11 §11 复杂度上限）：**新增一条规则必须能写进一行 JSON，否则重新设计**。
> 逻辑与数据分离后，修改规则 = 改一个文件 + 重启 = **0 代码、0 发版、1 分钟生效**。

## 6. 验收清单（V0）

- [ ] 修改 `shelf_rules.json` 里鲜牛奶的 `T0` → 重启服务端 → **新建**一条鲜牛奶记录，到期日按新值计算（不需改代码）；
- [ ] 已在库的历史记录**不受影响**（`estimate` 快照 + `ruleVersion` 可追溯）；
- [ ] 故意写一个 schema 非法的 JSON（如 `T0: -1`）→ **服务端启动失败并打印具体错误行**；
- [ ] 文案库里的惊吓词（"库存告急""请立即处理"）被 `pnpm validate:config` 拦下；
- [ ] 版本号未递增时 `pnpm validate:config` 报错；
- [ ] 设置页能显示当前知识库版本号。
