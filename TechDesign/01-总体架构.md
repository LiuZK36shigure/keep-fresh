# 01 · 总体架构（V0）

> 📌 **本章已按 2026-08 范围收缩整体重写**。原版本是"微信小程序客户端 + 微信云开发"的分层图与四条数据流，
> 随"放弃小程序"**已完全作废**。
>
> **V0 的一句话架构**：
> **服务端 SQLite 是数据的家；前端是可替换的壳。**
> 同一个账户下的物资只有一份数据，存在你自己的机器上，前端（今天的 PC 网页、明天的手机 App）
> 都只是它的视图。
>
> PRD 依据：[08 §2 范围](../PRD/08-MVP范围与版本规划.md)、[07 非功能需求](../PRD/07-非功能需求.md)。
> 后端与 API 契约见 [03 服务端技术栈](./03-服务端技术栈.md)；数据结构见 [04 数据模型与存储](./04-数据模型与存储.md)。

---

## 1. 架构原则（V0）

| 原则 | 含义 | 落地方式 |
| ---- | ---- | ---- |
| **服务端为唯一权威** | 物资数据只存一处（服务端 SQLite），**前端不持有权威副本** | 前端只做请求与渲染；刷新即与数据库一致 |
| **逻辑层与平台解耦** | 推算引擎是纯 TS，前后端共用同一份代码 | `packages/core`，**禁止 IO**（见 §5） |
| **接口先于实现** | V0 不做的能力（提醒/语音/推送），契约先冻结 | `/api/v1` 版本前缀 + V1 预留路由（03 §3.3） |
| **配置驱动** | 品类规则、文案是 JSON，改规则不发版 | `config/*.json` + 启动时校验（06 章） |
| **零外部依赖** | V0 不需要任何第三方账号、域名、部署 | 本地 Node + SQLite，`pnpm dev` 起 |
| **可替换的前端** | 电脑网页是"第一块屏"，不是唯一一块 | 同一套 REST 契约服务 PC / PWA / RN |

> **与旧架构最大的差别**：原文档的 ADR-01 是"推算引擎放端侧、端侧为权威、云端只做配置分发"。
> V0 **反转为"服务端为权威"**——因为账户与同步是 V0 的核心（PRD 08 §2.2），
> 而多端共享同一份数据时，"端侧为权威"会立刻带来冲突合并问题（那是 V2 家庭共享才需要面对的）。
> 这个选择让 V0 的复杂度**大幅下降**：没有本地队列、没有离线合并、没有端云去重。

## 2. 分层与职责边界

```
┌──────────────────────────────────────────────────────────────────────┐
│  前端：apps/web（Vite + React + TS，PC 桌面浏览器）                     │
│                                                                       │
│   pages/       登录 / 注册 / 物资列表 / 物资详情 / 新增编辑 / 统计 / 设置  │
│   components/  列表卡片 / 分组标签 / 筛选栏 / 表单控件 / 确认弹窗          │
│   api/         REST 客户端（唯一的网络出口，见 §5）                       │
│   store/       轻量状态（当前用户 / 列表查询条件 / 表单草稿）               │
│                                                                       │
│   ⚠️ 前端不做：到期日推算、状态判断、排序筛选的最终裁决、任何本地权威存储     │
└─────────────────────────────┬────────────────────────────────────────┘
                              │  REST /api/v1（JSON + Bearer token）
                              │  （V1 的手机端走同一套契约，不改协议）
┌─────────────────────────────▼────────────────────────────────────────┐
│  后端：apps/server（Node + Hono + SQLite）—— 本地运行，不需要部署          │
│                                                                       │
│   routes/       auth / items / categories / settings / stats           │
│   middleware/   auth（会话校验，注入 userId）/ validate（Zod）/ error     │
│   services/     业务逻辑，**签名第一参数恒为 userId**（防越权，03 §4.1）    │
│   db/           better-sqlite3 连接 + migrations（顺序 SQL + schema_version）│
│                                                                       │
│   服务端负责：鉴权、归属校验、**推算引擎调用**、状态推导、排序筛选搜索、统计  │
└─────────────────────────────┬────────────────────────────────────────┘
                              │
┌─────────────────────────────▼────────────────────────────────────────┐
│  packages/core（纯 TS，前后端共用 —— V0 最有价值的资产）                  │
│                                                                       │
│   engine/     三层推算引擎（日期驱动 + 状态驱动双模型）                    │
│   rules/      知识库加载 / 校验 / 版本比较                               │
│   schemas/    Zod：领域类型 + API 契约（唯一真源）                        │
│   parser/     【V1 预留】语音解析器，V0 不实现                             │
│   reminder/   【V1 预留】提醒生成器，V0 不实现                             │
│                                                                       │
│   ⚠️ 纯计算：无 fetch / 无 node:* / 无文件读写 / 无数据库                  │
│      —— 所以能被 server 用、能被 web 用、能被未来的 React Native 用        │
└──────────────────────────────────────────────────────────────────────┘
```

## 3. 服务端职责（V0 的"该谁做"清单）

| 能力 | 服务端 | 前端 | 理由 |
| ---- | ---- | ---- | ---- |
| 账户与鉴权 | ✅ 唯一实现 | ❌ 只存 token | 越权防线只能在服务端 |
| 物资 CRUD | ✅ 权威存储 | 发请求 | 服务端为权威 |
| **推算（到期日/置信度）** | ✅ **唯一计算点** | ❌ **只展示 reasonText** | 避免前后端两套算法漂移（§5） |
| 状态推导（临期/过期/已开封） | ✅ 查询时计算 | ❌ 不判断 | 前端时钟不可信，且列表筛选要下推 SQL |
| 排序/筛选/搜索 | ✅ SQL | 传参数 | 数据量增长后前端过滤不可持续 |
| 统计（3 个数字） | ✅ SQL 聚合 | 展示 | — |
| 知识库校验 | ✅ 启动时校验 | 拉取展示 | 坏规则宁可起不来 |
| 提醒生成 | ❌ V0 不做 | ❌ | V1 |
| 推送发送 | ❌ V0 不做 | ❌ | V1 |
| 语音识别 | ❌ V0 不做 | ❌ | V1 |

> **边界铁律**：
> ① 凡是**关于时间和规则的计算**，只在服务端做一次；
> ② 凡是**网络请求**，前端只允许出现在 `apps/web/src/api/` 一处；
> ③ 凡是**读写数据库**，只允许出现在 `apps/server/src/services/`，且必须带 `userId`。

## 4. 三条主数据流（V0）

### 4.1 写入流：录入一件物品

```
[前端] 填写表单（品类/数量/购买日/开封状态/存储位置/备注）
   → 前端生成 UUID 作为 id（幂等，重复提交不重复建）
   → POST /api/v1/items
[后端] auth 中间件校验 token → 注入 userId
   → Zod 校验载荷（非法即 400，不写库）
   → 调 packages/core/engine 推算 → 得到 expireAt / windowEndAt / confidence / reasonText / ruleVersion
   → INSERT INTO items (..., user_id, ..., estimate_*)
   → 返回完整 item（前端不需要自己算任何东西）
[前端] 用返回值渲染；列表插入或重取
```

**关键点**：**推算发生在服务端，写入时固化成 `estimate` 快照**。
这样历史记录的日期不会因为日后改规则而漂移，且 `ruleVersion` 保证了可追溯。

### 4.2 读取流：打开"我的物资"

```
[前端] GET /api/v1/items?status=active&storage=fridge&sort=expireAt&order=asc
[后端] 单条 SQL（WHERE user_id = ? AND ...）→ 附带按当前日期推导的 status
   → 返回 { items, total }
[前端] 渲染分组标签 / 筛选栏 / 列表；点击进入详情（GET /items/:id）
```

**关键点**：**筛选与排序全在 SQL 里**，前端只负责把查询条件拼进 URL 并记忆上次选择。
`expireAt` 上必须建索引（500 条列表 ≤ 300ms，见 03 §7）。

### 4.3 变更流：编辑 / 开封 / 处置 / 撤销

```
编辑字段 → PATCH /items/:id → 服务端重算 estimate → 返回新 item
标记开封 → PATCH /items/:id { openedAt: today } → 服务端切换到 T1 重新计时
处置    → POST /items/:id/dispose { type } → status=disposed + disposedAt
撤销    → POST /items/:id/restore（5 秒内 UI 提供入口）
改气候档 → PATCH /settings → **服务端批量重算该用户全部未处置物品**
```

**关键点**：**"改气候档要批量重算"是被原文档漏掉的一条**——
原设计是端侧实时算所以不存在这个问题；现在推算固化在库里，改设置就必须重算，
否则会出现"设置改了但到期日没变"的诡异现象。

## 5. 为什么 `packages/core` 必须是纯计算（本架构的支点）

V0 的架构里，`packages/core` 是**唯一同时被前端和后端引用**的代码。它一旦掺入 IO，整个架构就塌了：

| 若 `core` 里出现… | 后果 |
| ---- | ---- |
| `fetch` / `axios` | 前端 bundle 里混入网络层；RN 复用时要重写 |
| `node:fs` / `better-sqlite3` | **前端根本打不开**（Vite 会报错或需要 polyfill） |
| `process.env` | 前端拿不到，且泄露配置 |
| `Date.now()` 散布各处 | 无法写确定性单测（应把"今天"作为参数传入） |

**因此的硬约束**（写进 CI）：

- `packages/core` **不允许出现** `fetch` / `node:` / `fs` / `process` / `better-sqlite3` 字样；
- 所有时间相关函数**必须接受 `today: Date` 作为参数**，不在内部读系统时钟；
- 存储与网络通过**接口注入**（`interface KVStore`、`interface Clock`），V0 里由 server 侧提供实现。

> 这条约束是"以后做移动端"这个目标能兑现的**唯一保证**。
> 它同时也是本项目里**最值得守住的一条设计**：换 UI 是必然的成本，但换 UI 时不用重写业务逻辑，
> 这个差别决定了 V1 是"重写一遍"还是"接一块屏"。

## 6. V0 明确不做的架构能力（避免提前设计）

| 不做 | 为什么现在不做 | 什么时候做 |
| ---- | ---- | ---- |
| 离线队列与冲突合并 | 服务端为权威 + 单端使用，**不存在冲突** | V2 家庭共享 / 多设备 |
| 端侧加密存储 | 数据在你自己的机器上，威胁模型不成立 | V1 公网化时重新评估 |
| 推送与订阅管理 | V0 没有提醒 | V1 |
| 定时任务与常开进程 | 同上；**且"必须常开"是部署问题** | V1 |
| 多租户配额与限流 | V0 只有你自己的几个账号 | V1 |
| 缓存层（Redis 等） | SQLite + 索引已足够 | 数据说话 |
| 微服务拆分 | 一个人维护不了 | 不做 |
| 服务端渲染 | PC 端 SPA 足够 | 不做 |

## 7. 关键权衡记录（ADR 摘要，2026-08 重写）

| # | 权衡 | 结论 | 原因 | 若反转会怎样 |
| ---- | ---- | ---- | ---- | ---- |
| ADR-01 | 数据权威在哪 | **服务端 SQLite** | 账户 + 同步是 V0 核心；单端使用不存在冲突 | 改回端侧权威 → 立刻需要离线队列与冲突合并，V0 工期翻倍 |
| ADR-02 | 推算引擎放哪 | **`packages/core`，由服务端调用** | 一份代码、一处计算、可单测；前端只展示 | 各写一份 → 必然漂移（旧 TR-5 风险换个形式复活） |
| ADR-03 | 后端选型 | **本地 Node + Hono + SQLite** | 零部署、零账号、零备案；SQL 可直接看 | 选云 Serverless → 立刻要面对域名/备案/CPU 限额（V1 再面对） |
| ADR-04 | 要不要 ORM | **不用，直写 SQL** | 6 张表，SQL 更好读、更好复核 | 引入 ORM → V1 迁移时多一层黑盒 |
| ADR-05 | 鉴权方式 | **不透明 token + sessions 表** | 可吊销、实现最短、无需 JWT 的无状态复杂度 | 用 JWT → 吊销困难，V0 没有收益 |
| ADR-06 | 前端要不要本地缓存 | **不要（V0）** | 服务端为权威，加缓存就会引入一致性问题 | 加 IndexedDB → 又要处理"本地新还是远端新" |
| ADR-07 | 语音/提醒是否先搭架子 | **只冻结接口，不写实现** | 实现会被 V1 的真实约束推翻（音频格式、iOS 权限） | 提前实现 → 大概率白写 |

## 8. 本章验收（怎么算"架构落地了"）

- [ ] `pnpm dev` 一条命令起前后端；前端 `/api` 请求经 Vite proxy 到 :3000，**无 CORS 配置**；
- [ ] 数据库里**只存在一份**物资数据：删掉前端全部产物后重新构建，数据依旧完整；
- [ ] 前端代码中 `fetch` **只出现在** `apps/web/src/api/` 一处（grep 检查纳入 CI）；
- [ ] `packages/core` 内**无** `fetch` / `node:` / `fs` / `process` / `better-sqlite3`（grep 检查纳入 CI）；
- [ ] `packages/core` 的引擎单测**在纯 Node 下**全部跑通，且不依赖系统时钟（传入固定 `today`）；
- [ ] `apps/server/src/services/` 之外**不存在任何 SQL 语句**（grep 检查）；
- [ ] 修改气候档后，未处置物品的 `expireAt` 全部被重算（抽查与单测一致）；
- [ ] 用 A 的 token 访问 B 的物资返回 403/404（自动化用例）；
- [ ] 断开网络（或停掉后端）时，前端**明确报错且不显示陈旧数据**——V0 不做离线，不要假装可用。
