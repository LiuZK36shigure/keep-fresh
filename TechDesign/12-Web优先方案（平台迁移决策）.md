## 1. 决策

| 项 | 决策 | 说明 |
| ---- | ---- | ---- |
| 微信小程序 | **完全放弃** | 订阅消息一次性配额 + 长期订阅类目受限，无法承载"提醒"这一核心价值 |
| 移动端原生开发 | **后置（V2）** | 用户仅持 iPhone + Windows PC，无 macOS 与移动开发条件 |
| **V0 形态**（2026-08 收缩后） | **PC 网页（桌面浏览器）+ 本地 Node + SQLite**，跑 `localhost` | **不做提醒/推送/语音/PWA/部署**；V0 是"物资总管"（PRD 08 §2.1） |
| V1 形态 | 公网 PWA（Web Push）+ 移动端可用 + 语音录入 | 部署到 HTTPS，可给他人使用 |
| V2 形态 | 原生 App（Expo / React Native，复用 `packages/core`） | 待 V1 验证后评估 |
| **资产复用主线** | **同一套 REST 契约 + 纯 TS 逻辑层，服务多种前端** | V0 就把 `/api/v1/*` 冻结好，V1 加移动端时**不改协议**（PRD 08 §2.4） |

## 2. 为什么这个决策成立

1. **提醒可靠性**：小程序订阅消息"一次授权 = 一条配额"，长期订阅仅向公共服务类目开放；
   把产品的唯一主动触达手段押在"用户反复点头"上，产品会退化为"想起来才打开的工具"（PRD 09 §3.1）。
2. **零 Mac 依赖**：iOS 原生开发需 macOS（云 CI 可绕过，但非必要）；Web 路线在 Windows 上即可完成全部开发。
3. **资产保全且更优**：核心逻辑是纯 TS（`core/`）——Web 与未来的 Expo/React Native **共用同一套逻辑**。
   ⚠️ 原 TechDesign 中"纯 TS 可在 V2 转 Flutter 时直接复用"的判断**是错的**（Flutter 用 Dart，无法直接复用）；
   走 Web → React Native 路线，这条复用链才是真实成立的。

## 3. 技术前提：网页默认"不能提醒"（V1 起才需要补推送通道）

> ⏸ **V0 不实现本节**——V0 没有提醒功能（PRD 08 §2.3）。
> 本节在 **V1** 生效，是 V1 最重要的技术前提，**请务必在启动 V1 前重读**。

浏览器**没有可靠的本地定时通知**，页面关闭即失去提醒能力。三条补救通道：

| 通道 | 原理 | 可靠性 | 开发量 | 适用阶段 |
| ---- | ---- | ---- | ---- | ---- |
| 页内提醒 | 打开页面（或后台标签页）才可见 | ❌ 无主动触达 | 0 | 兜底，**始终保留**（V1 起） |
| **Web Push** | Service Worker + VAPID + 服务端推送 | ⚠️ iOS 需 16.4+ **且已"添加到主屏幕"** | 中 | **V1 主力** |
| **第三方推送通道**（Bark / ntfy / 飞书机器人） | 服务端 HTTP 调用 → 系统级通知（走 APNs/厂商通道） | ✅ 最可靠 | **低** | **V1 早期过渡**（先把闭环跑通，再换 Web Push） |

> **V1 决策（2026-08 收缩后修订）**：**先**用第三方推送通道把"到点 → 手机响 → 处置"的闭环跑通
> （一条 HTTP 请求即可推到 iPhone，零推送开发），**再**切换为 Web Push（不依赖第三方 App，可服务他人）。
> 页内横幅始终保留作兜底。
>
> ⚠️ **注意**：**V0 完全不做本节内容**——V0 没有提醒，也就没有任何推送通道。
> 本节整体属于 **V1**，V0 只需要把 `Notifier` 接口与 V1 预留路由（03 §3.3）留好。
>
> 📌 但有一条**现在就该知道**：**推送不能当作可靠承诺**。
> iOS 上权限一旦拒绝**无法程序化重新申请**，且订阅会**静默失效**（见 §7.3）。
> 因此产品的对外承诺应是"**打开时一定会看到**"，而不是"一定准时响"——
> 这也让 V1 的页内横幅从"兜底"升级为"主承诺"。

> iOS 现实约束（务必写进说明文档）：Web Push 要求 ① iOS 16.4+；② 已"添加到主屏幕"
> （**严格说"添加主屏幕"是"接收"推送的前提，"订阅"在 Safari 标签页内也能完成**）；
> ③ HTTPS；④ 用户在**用户手势**中授权通知。**未安装到主屏幕时完全没有推送。**
> 实操建议：把"添加主屏幕"与"请求通知权限"放在**同一个用户手势链**里一次完成。

> ⚠️ **本节的选型表是"Web 优先"当时的版本**（Cloudflare Pages/Workers + IndexedDB 本地优先）。
> **V0 范围收缩后，技术栈已改为 Vite+React + 本地 Node/Hono/SQLite**，
> 现行选型请见 **[TechDesign README §1.1](./README.md)** 与 **[03 服务端技术栈 §1](./03-服务端技术栈.md)**。
> 本节中**仍然有效**的部分：§5.1 的托管对比（V1 部署时要用）、**§5.2 / §5.3**（技术核实结论）。

| 层 | 选型 | 理由 |
| ---- | ---- | ---- |
| 语言 | **TypeScript**（前后端同语言） | 逻辑层可单测、可复用至未来 RN |
| 前端框架 | **Vite + React + TS** | 生态成熟、AI 辅助编码友好、构建快 |
| 样式 | CSS 变量设计令牌 + 轻量自研组件 | 保持"生活化"基调（PRD 01 §2.4），避开工具感组件库 |
| 状态 | Zustand 或 React Context（轻量） | 数据流以本地集合为主，无需重型框架 |
| 本地存储 | **IndexedDB（Dexie 封装）** | 容量远大于 localStorage，适合物品 + 照片元数据 |
| PWA | `vite-plugin-pwa`（manifest + Service Worker） | iPhone "添加到主屏幕" 的必要条件 |
| 语音 | **MediaRecorder 录音 → 服务端 ASR 代理** | iOS Safari 的 Web Speech API 不可靠（见 §6） |
| 服务端 | Node（Hono/Express）+ SQLite，或 Cloudflare Workers + D1/KV | 见 §5.1 托管对比 |
| 定时任务 | 平台 Cron（Cloudflare Cron Triggers / GitHub Actions schedule / node-cron） | **必须常开**，不能跑在会关机的 PC 上 |
| 推送 | V0：Bark / ntfy / 飞书机器人　V1：`web-push`（VAPID） | §3 |
| 部署 | Cloudflare Pages（前端）+ Workers（API/Cron）；或轻量云服务器 + Caddy | 见 §5.1 |
| 代码托管/CI | GitHub + GitHub Actions | 已有仓库（本 PRD 与 TechDesign 同仓） |

### 5.1 服务端托管三选一

| 方案 | 成本 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| **Cloudflare Pages + Workers + D1/KV + Cron** | **0 元** | 免费额度充足、自带 HTTPS、全球可达、零运维 | Workers 运行时限制（无完整 Node）；Web Push 实现需用 Web Crypto 自研 |
| **轻量云服务器 + Node + SQLite + Caddy** | 约 24~60 元/月 | 完整 Node 生态、`web-push`/`node-cron` 开箱即用、调试直观 | 需自己维护（更新/证书/备份） |
| **本地 Windows + Cloudflare Tunnel** | 0 元 | 开发零摩擦、数据不出家门 | ❌ **PC 关机即无提醒**，与核心价值冲突 → 仅适合开发期 |

> **推荐**：开发期用 `localhost`；自用期用 **Cloudflare 或轻量服务器**（保证定时任务常开）；
> 若嫌 Cloudflare 写 Web Push 麻烦，V1 直接上轻量服务器最省心。

### 5.2 ⚠️ 部署前必须知道的三个硬约束（2026-08 技术核实后补充）

> V0 **不部署**，所以下面这些都不阻塞 V0。但它们**直接决定 V1 的托管选型**，
> 而且其中第 1 条与**备案**正面冲突——**建议在 V0 期间就把方向想清楚，不要等到 V1 才碰**。

**1）自定义域名与备案互斥（最重要）**

Cloudflare 的 Custom Domain 要求域名处于你自己的 Cloudflare zone，
而免费/Pro 计划**只支持 Full setup**——Full setup 的定义就是**把 nameserver 改到 Cloudflare**。
也就是说：

- 想用自定义域名 → **必须迁 NS 到 Cloudflare** → 丢掉境内 CDN 与**备案接入资格**；
- 想用 `*.workers.dev` → 虽然**自带有效 HTTPS 证书、不需要任何域名**，
  但官方明确**不推荐用于生产**（该子域被视为 "Free website"，定位是
  "personal or hobby projects that aren't business-critical"），且**该域名在国内常被污染/不可直连**。

而 PWA 的三件事（安装到主屏、Service Worker、Web Push）**都必须走 HTTPS 且域名可达**——
这正好打在产品生命线上。**这是 V1 的第一件前置决策**，见 [PRD 11 R13](../PRD/11-风险与对策.md)。

**2）Workers 免费版有"双重硬墙"，不能用一轮跑完推送**

| 限额 | Workers Free | 说明 |
| ---- | ---- | ---- |
| **CPU 时间（含 Cron Trigger）** | **10 ms** | 50 条推送要做 VAPID JWT 签名 + AES-GCM 加密，预算 = 每条 0.2 ms，**连一次 ECDSA P-256 签名都不够** |
| **子请求 / 次调用** | **50** | 50 个 `fetch()` 就把配额用尽，之后连"写回发送结果"都做不了 |
| Cron Trigger 数量 | 5 个/账户 | — |

超限返回 **Error 1102**，调用**被硬杀、无重试、状态丢失**。

**因此必须**：① 改成分片 cron（`*/1 * * * *`，每次 ≤10 条推送），游标存 **D1**，幂等键保证可续跑；
② **提醒计划/推送订阅/发送日志全部放 D1——KV 不适用**（KV 免费写额度仅 **1,000/日**、
同 key **每秒 1 次**，几十个活跃用户就爆）；
③ 若不想受这些限制，**最便宜的正解是 Workers Paid $5/月（≈36 元），而不是 60 元 VPS**
（$5 把子请求提到 10,000、cron CPU 提到 30s~15min，且免运维、免证书续期）。

**3）定时任务的选型排雷**

| 方案 | 能用吗 | 原因 |
| ---- | ---- | ---- |
| Cloudflare Cron Triggers | ✅（需分片） | 见上 |
| `Deno.cron`（Deno Deploy Free） | ✅ | 无 10ms CPU 墙，1M 请求/**月** |
| VPS 常驻 `node-cron` | ✅ | 要自己扛可用性与证书续期 |
| **GitHub Actions `schedule`** | ❌ **不可用于提醒** | 官方承认高负载时延迟、**排队任务会被丢弃（dropped）**、公开仓库 60 天无活动自动禁用。**用于 CI 完全合适，用于业务定时任务不合适** |
| Vercel Cron（Hobby） | ❌ | 每天 1 次、精度 ±59 分钟 |
| Render Free | ❌ | 15 分钟无流量即休眠 |
| Fly.io | ❌ | 已无 free allowance |

### 5.3 Cloudflare 上做 Web Push 的现成方案（推翻旧的"需自研"结论）

原版本写"Web Push 实现需用 Web Crypto 自研"——**这个结论是错的**，会造成不必要的选型顾虑：

- `web-push` npm 确实是 Node 库（依赖 `crypto.createECDH` / `https`），在 Workers 上**不能开箱使用**；
- 但可选：① **Cloudflare Agents 官方就有 Web Push / push-notifications 通信通道文档**（最省事）；
  ② Web Crypto 系库：`@block65/webcrypto-web-push`、`webpush-webcrypto`、`pushforge`；
  ③ 调度侧另有 Cron Triggers（粗粒度）+ Queues + Durable Objects（精确到点）的现成组合。

> ⚠️ 选型风险：上述库中若干为个人项目，**引入前评估维护活跃度**。

## 6. 语音输入方案（V1 起实现；原 WechatSI 方案已作废）

> ⏸ **V0 不做语音**（PRD 08 §2.3）。但 **§6.1 的格式结论现在就要知道**——
> 它决定了 V1 的语音方案必须包含哪一层，属于"不知道就会返工"的那类事实。
> V0 需要做的只有一件事：把 `VoiceInput` 接口和 `core/parser/` 目录**留空占位**。

### 6.1 ⚠️ 音频格式：这是 V1 语音最大的坑（技术核实后确认）

**浏览器的 `MediaRecorder` 产出的格式，两家主流国内 ASR 都吃不下：**

| 浏览器产物 | 讯飞语音听写（仅支持 `pcm` / `wav` / `speex-wb`，16k/8k、16bit、单声道） | 腾讯云一句话识别（支持 `wav`/`pcm`/`ogg-opus`/`speex`/`silk`/`mp3`/`m4a`/`aac`/`amr`） |
| ---- | ---- | ---- |
| Chrome / Edge：`audio/webm;codecs=opus`（48 kHz） | ❌ **完全不支持**（opus 不在列） | ❌ **不支持 WebM 容器**——列表里的 `ogg-opus` 指 **Ogg 封装**的 Opus，**"webm" 在该文档中零命中** |
| Safari：`audio/mp4`（AAC） | ❌ 不支持 | ⚠️ 列表含 `m4a`/`aac`，**可试但文档未保证**该 MIME 被接受 |

**而"在服务端转码"这条路在 Workers 上是堵死的**：

- Workers 是 **V8 isolate，不是容器**——**没有子进程、没有文件系统、没有 shell**，`ffmpeg` 无法运行；
- **`ffmpeg.wasm` 也不行**：Workers 的 WebAssembly 运行时**只支持预编译模块、禁止运行时动态编译**。

**✅ 正确做法（必须写进 V1 方案）**：**把转码挪到前端，让云端零转码**——
浏览器里 `decodeAudioData()` 解码 Blob → 重采样到 **16 kHz 单声道** → 手写 **44 字节 WAV 头** → 上传 WAV。
15 秒 @16k/16bit/mono ≈ **480 KB**，远低于腾讯云 **3 MB / 60 秒**上限。
Worker 只做**纯透传**（只保管 API key，不做任何编解码）。

> 换言之：`TechDesign/12` 原版本"采集 → 服务端代理识别"是**不完整的方案**，
> 中间缺了"前端音频归一化"这一层。不补的后果是**上线后 Chrome 用户 100% 识别失败**。

### 6.2 方案表

| 环节 | 方案 |
| ---- | ---- |
| 采集 | 浏览器 `MediaRecorder` 录音 |
| **归一化** | **前端 `decodeAudioData` + 重采样 16k 单声道 + WAV 封装**（见 §6.1） |
| 识别 | **服务端代理**调用云 ASR（腾讯云一句话识别 / 讯飞），密钥仅存服务端 |
| 解析 | `packages/core/parser`（规则优先），与平台无关 |
| 降级 | 无网/失败/用户拒绝麦克风 → **手动表单**（V0 已有，天然降级路径 ✓） |
| 隐私 | 录音**识别后即弃**，服务端不留存音频；隐私说明中如实声明"音频会发送至 ASR 服务商" |
| 成本控制 | 按量计费 + 每日用量上限 + 失败重试上限。腾讯云一句话识别 **5,000 次/月免费**，之后 **3.20 元/千次**；讯飞默认 **500 次/日**免费，之后 **0.005 元/次**。**两家均需实名认证** |

> `services/voice` 的**可替换接口抽象**继续有效，仅更换 adapter 实现。

## 7. 数据与隐私：V0 的实际边界（2026-08 收缩后重写）

> 🔄 原版本写的是"V0 自用可存明细 / V1 收紧为最小提醒字段"的**阶段化条款**。
> 范围收缩后，**V0 的边界变了**：V0 有账户与同步，**服务端 SQLite 就是权威数据源**，
> 所以"服务端只存最小字段"在 V0 不成立、也不需要成立。以下为 V0 的实际边界。

### 7.1 V0 的数据边界

| 数据 | 存在哪 | 说明 |
| ---- | ---- | ---- |
| 物资明细（品类/数量/日期/开封/存储/备注） | **服务端 SQLite** | V0 的核心数据；就在你自己的机器上 |
| 账户与密码 | 服务端 SQLite | 密码只存 **argon2id 哈希**，绝不明文 |
| 会话 token | 服务端 `sessions`（存哈希）+ 客户端内存/Cookie | 登出即吊销 |
| 照片 | **V0 没有** | 拍照是 V1 功能 |
| 语音 | **V0 没有** | 语音是 V1 功能 |
| 知识库 JSON | `config/`（Git 管理）+ 服务端加载 | 不含任何用户数据 |
| 日志 | 服务端本地文件 | **禁止打印密码、token、备注全文** |

> **V0 的隐私论证很简单**：数据在你自己的机器上，网络不出 localhost。
> **但这是一条"V0 限定的"论证**——一旦 V1 部署到公网，这个论证立刻失效，
> 必须重新做一次边界设计（见 §7.3）。**不要把这个阶段性的舒适当成永久的隐私承诺。**

### 7.2 V0 真正的安全问题不是隐私，而是越权

旧文档的 §7 通篇在担心"云端泄露"。V0 的实际风险排序是：

1. **越权访问**（头号）：A 的 token 读/改/删 B 的物资——**必须靠"所有查询带 `user_id`"从根上防**，
   并有自动化测试覆盖（[TechDesign 03](./03-服务端技术栈.md) §4.1）；
2. **密码存储不当**：明文 / MD5 / 无盐哈希；
3. **密钥与数据文件误提交**：`.env`、`*.db` 进了 Git（`.gitignore` 已覆盖 ✓）；
4. **SQL 注入**：字符串拼接 SQL；
5. 隐私泄露：**V0 基本不涉及**（数据不出本机）。

> 完整的 V0 安全清单见 [TechDesign 09 安全与隐私架构](./09-安全与隐私架构.md)。

### 7.3 V1 部署时必须重新做的边界设计

| 问题 | 为什么 V1 必须重做 |
| ---- | ---- |
| 数据出境/出境合规 | 公网后要面对备案与个人信息保护要求 |
| 服务端存明细还是只存最小字段 | 提醒需要"服务端知道什么"，这个权衡在 V1 才真实存在 |
| 数据导出与彻底删除 | 从"拷个 db 文件"变成需要产品化功能 |
| 传输安全 | localhost → 必须全程 HTTPS |
| 备份与恢复 | 从"拷文件"变成需要自动化 |

> ⚠️ 附带一条**必须写进 V1 的发现**：iOS 上的 Web Push 订阅会**静默失效**
> （系统更新 / 长期未打开 / 存储回收 / 清理网站数据），且 `pushsubscriptionchange` 在 iOS 上**不可靠**。
> 服务端必须**每次打开都重新 upsert 订阅**，并对 **404/410 立即删除**，
> 否则会在"推送到达率"指标上看到**虚假的好数字**。
> 由此推论：**产品承诺应下调为"打开时一定会看到"，而不是"一定准时响"**。

## 10. 迁移后的风险与对策

> V0 的风险与 V1 的风险已经不是一回事。下表按版本分组。

### 10.1 V0 的风险（**当前要面对的**）

| 风险 | 对策 |
| ---- | ---- |
| **越权访问**（A 的 token 操作 B 的数据） | 所有查询带 `user_id`；`services/` 签名第一参数恒为 `userId`；**自动化测试覆盖 4 个动作**（03 §4.1） |
| 密码存储不当 | 强制 argon2id/bcrypt + 盐；禁止明文/MD5/SHA1 |
| 密钥与数据文件误提交 | `.gitignore` 覆盖 `*.db` / `.env` / `node_modules` / `dist`（**已完成** ✓） |
| SQLite 损坏 / 误删 | 每周拷贝 `data/keepfresh.db`（写进 09 章周节奏） |
| 前后端逻辑漂移 | 推算**只在 `packages/core/engine` 算一次**（01 ADR-02）；CI 检查 `core/` 内无 IO |
| 范围蔓延（想把提醒/语音提前做） | 本清单 §1.2 与 PRD 08 §2.3 是**明确的排除项**；接口留好即可 |
| 单人中断（考试/生病） | 全文档化 + 配置化 + Git；**V0 不要引入任何需要"持续运维"的东西**（这正是选本地 SQLite 的原因） |
| **工期误判** | 旧口径"2~4 周含 2 周 dogfooding"已被证明不现实；新口径 **3~4 周 @14h/周**，且在 PRD 08 §2.5 做了可勾选的验收表 |

### 10.2 V1 的风险（**现在不用解决，但要知道**）

| 风险 | 对策 |
| ---- | ---- |
| **公网发布的合规与域名可达性** | **PRD 11 R13**——自定义域名要求 NS 迁到 Cloudflare，与境内备案冲突（§5.2）；**这是 V1 的第一件前置决策** |
| Workers 免费版 CPU 10ms / 子请求 50 的硬墙 | 分片 cron（≤10 条/批）+ 游标存 D1；或直接用 Workers Paid $5/月（§5.2） |
| 网页关闭/后台限制 → 提醒失效 | 推送通道（系统级通知）+ 页内横幅双轨；绝不把提醒押在"页面开着"上 |
| iOS Web Push 前置条件苛刻（16.4+ / 主屏安装 / 权限不可重新申请） | "添加到主屏幕"引导与权限请求放在**同一手势链**；内置权限被拒的降级引导（§3） |
| **iOS 推送订阅静默失效** | 每次打开重新 upsert + 404/410 清理 + `last_seen_at` + 以"用户是否打开网页"做真实性校验（§7.3） |
| ASR 音频格式（Chrome 的 webm/opus 两家都不收） | **前端归一化为 16k 单声道 WAV**（§6.1） |
| ASR 成本失控 | 每日用量上限 + 失败重试上限 + 手动表单兜底 |
| 放弃小程序导致获客摩擦上升 | V1 产品化阶段面对（PRD 10 §2 冷启动路径：内容 → 网页直链） |
