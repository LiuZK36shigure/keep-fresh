# 02 · 客户端技术栈（微信小程序）

> 本章给出小程序端（客户端）的完整技术选型与理由，包括框架、状态管理、本地存储、
> 语音、UI 方案、分包策略与性能注意点。
> PRD 依据：06 信息架构（页面结构）、07 §4 兼容性、09 §3 平台决策。

---

## 1. 框架选型：原生小程序 + TypeScript（T-01）

### 1.1 为什么不用 Taro / uni-app 等跨端框架

| 维度 | 原生 + TS | Taro / uni-app | 结论 |
| ---- | ---- | ---- | ---- |
| 订阅消息 / 语音插件 / 云开发 | 直接调用，零损耗 | 需抽象层适配，偶发能力缺口 | 原生 ✅ |
| 学习与调试成本（一人公司） | 微信开发者工具原生调试最顺 | 多一层编译链，报错定位多一跳 | 原生 ✅ |
| V2 转 Flutter 时逻辑复用 | 纯 TS 模块直接复用 | 依赖框架运行时，复用价值低 | 原生 ✅ |
| 未来多端（H5/抖音） | 需重写 UI 层 | 一套代码多端 | Taro 胜（但 V1 不需要） |

> **关键判断**：PRD 09 §3.1 的演进方向是"小程序 → Flutter App"，而不是"小程序 → H5/多端小程序"。
> 跨端框架省的是 UI 层，而 UI 层恰恰是转 Flutter 时必须重写的部分；
> **逻辑层复用**才是真正的资产——这用"纯 TS 模块"（`core/`）就能实现，不需要跨端框架。
> 若未来出现"必须多端"的证据（V2+），再引入 Taro 也不迟（10 §4 备选）。

### 1.2 基础技术

| 项 | 选型 | 说明 |
| ---- | ---- | ---- |
| 语言 | **TypeScript** | 领域模型（Item/规则）有类型才有安全感；云函数同样 TS，端云共享类型 |
| 基础库 | ≥ 2.30（PRD 07 §4） | 云开发、同声传译插件的最低要求 |
| 构建 | 微信开发者工具内置 TS 编译 | 不引入额外打包器（保持简单） |
| 分包 | 主包（首页/语音/确认/设置）+ 分包（我的物品/详情，P1 统计页） | 主包 ≤ 2MB 红线，见 §6 |
| 最低机型 | iPhone 8+ / Android 8+（真机自测清单） | 兼容性自测表见 §7 |

## 2. 状态管理：mobx-miniprogram（T-02）

- 选型：`mobx-miniprogram` + `mobx-miniprogram-bindings`（官方维护，TS 友好，约 20KB）。
- 为什么不是 Redux/自研：数据流以"本地集合"为主（items / settings / knowledge / analytics queue），
  动作少而明确，mobx 的响应式绑定能让 WXML 直接 `useObservable`，代码量最小。
- Store 划分：

```
itemsStore     物品集合（CRUD、排序筛选缓存、撤销栈）
settingsStore  气候档案 / 提醒时间窗 / 推送开关 / 隐私开关
knowledgeStore 知识库版本与内容（shelf_rules + copywriting）
analyticsStore 埋点队列（阈值触发上报）
reminderStore  今日提醒横幅数据（端侧计算）
```

- 规则：**页面不直接写存储**，一律走 store action → 存储服务 →（异步）更新状态，保证可追踪。

## 3. 本地存储方案（本地优先的基石）

| 数据类型 | 存储介质 | 说明 |
| ---- | ---- | ---- |
| 物品记录（Item 数组） | `wx.setStorageSync`（key: `kf_items_v1`） | 500 条 JSON 约 200~400KB，可接受；写入节流（防抖 500ms） |
| 设置 / 气候档案 | `wx.setStorageSync`（key: `kf_settings_v1`） | 单对象 |
| 知识库缓存 | `wx.setStorageSync`（key: `kf_knowledge_v{ver}`） | 全量 JSON ≤ 200KB；旧版本清理 |
| 埋点队列 | `wx.setStorageSync`（key: `kf_events_queue`） | 上限 500 条，超出丢弃最旧（先本地统计，见 07） |
| 照片 | **文件系统** `wx.env.USER_DATA_PATH/photos/` | 路径存 Item 记录；删除物品时级联删除文件（GWT-10） |
| 撤销栈 | `wx.setStorageSync`（key: `kf_undo_stack`） | 5 秒撤销（03 §3），最多 20 条 |
| 提醒计划上报标记 | `wx.setStorageSync`（key: `kf_remind_synced`） | 记录 itemId → 云端 remind_plan 同步状态 |

**StorageService 封装要点**：

- 统一 `read<T>(key, fallback)` / `write(key, value, {ttl})`，内部 JSON 序列化 + 异常兜底；
- 写操作 try/catch：存储满（>10MB）时提示清理照片，绝不因存储异常崩溃；
- 版本化 key（`_v1` 后缀）：数据模型升级时写迁移函数（04 §6）。

## 4. 语音能力：微信同声传译插件（T-03）

- 插件：`WechatSI`（plugin://WechatSI），能力：`getRecordRecognitionManager()` 实时语音识别。
- 集成方式：`app.json` 声明插件 + 权限；识别结果回调 → `core/parser` 解析（05 §1）。
- **降级链路**（GWT-04）：无网络 / 插件失败 / 用户拒绝麦克风 → 直接进手动表单（F-02），不阻塞。
- 隐私：录音识别完成后**不留存音频**（07 §1.1）；识别文本仅用于解析，解析后不持久化原文。
- 免费额度监控：在管理后台记录插件用量，接近额度时提前评估（11 §6 R5 关联）。

## 5. UI 方案：自研轻量组件 + 设计令牌

- 基调：**生活化**（01 §2.4）：奶油白/橘/浅绿、圆角卡片、手绘风插画——商业组件库（Vant/TDesign）
  是"工具感"风格，与产品基调冲突，因此 **UI 以自研为主**。
- 自研范围：语音大按钮、物品卡片、提醒横幅、确认卡片、徽章、空状态插画位。
- 设计令牌：`app.wxss` 定义 CSS 变量（`--kf-bg`、`--kf-warm`、`--kf-radius`、`--kf-text-*`），
  全站统一；无障碍（07 §7）：字号跟随系统、对比度 WCAG AA、提醒不依赖单一红色。
- 图标/插画：AI 生成 + 本地压缩（WebP），放入 `assets/`；分享卡片模板（P1）用 canvas 绘制。

## 6. 包体积与性能策略

| 风险 | 对策 |
| ---- | ---- |
| 主包超 2MB | 分包：统计页（P1、echarts）→ `pages/stats/` 分包；插画压缩；字体不用大字体库 |
| echarts 体积大（P1） | 用 `echarts-for-weixin` 的按需引入（只注册柱状/环形图）；且只在分包 |
| 500 条列表渲染卡顿 | 分页加载（每页 50 条）+ 到达底部追加；卡片组件轻量化（避免复杂 wxs 表达式） |
| 冷启动慢 | 首页首屏不等待知识库拉取；知识库更新走后台；骨架屏占位 |
| 存储膨胀 | 照片定期清理引导；知识库只保留最新版 |

**性能自测清单**（对照 07 §2）：真机冷启动计时、列表 500 条滚动帧率、弱网（3G）记录流程。

## 7. 兼容性自测矩阵（07 §4）

| 维度 | 要求 |
| ---- | ---- |
| 系统 | iOS 12+ / Android 8+ 各 1 台真机跑通全流程 |
| 基础库 | ≥ 2.30；云开发环境线上版 |
| 屏幕 | 全面屏（刘海/挖孔）适配 `safe-area-inset-*`；iPad 小程序可跑通 |
| 深色模式 | V1 不主动适配，但颜色令牌需保证强制深色时仍可读 |
| 大字体 | 系统"大字体"下页面不破版（07 §7） |

## 8. 客户端依赖清单（V1）

| 依赖 | 用途 | 体积/成本 |
| ---- | ---- | ---- |
| TypeScript | 全站类型 | 0 |
| mobx-miniprogram + bindings | 状态管理 | ~20KB |
| WechatSI 插件 | 语音识别 | 免费额度 |
| dayjs（可选，或自写日期工具） | 日期计算（含农历可后置） | ~7KB |
| echarts-for-weixin（P1） | 统计图表 | 放分包 |
| miniprogram-ci（开发机） | CI 自动上传 | 0 |

> 原则：**依赖越少越好**。日期计算、防抖、节流等小工具优先自写，避免为省 100 行代码引入一个包。
