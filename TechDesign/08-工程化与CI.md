## 1. Monorepo 布局

> 与 [03 §2](./03-服务端技术栈.md) **严格一致**，改动必须同步两处。

```
keepfresh/
├─ packages/
│  └─ core/                       # ★ 纯 TS 逻辑层（前后端共用，未来 RN 复用）
│     ├─ src/
│     │  ├─ engine/               # 三层推算引擎（品类基线 × 开封状态 × 气候档）
│     │  ├─ rules/                # 知识库加载与校验
│     │  ├─ schemas/              # 领域类型 + Zod schema（契约唯一真源）
│     │  └─ index.ts
│     └─ package.json
├─ apps/
│  ├─ web/                        # Vite + React + TS（仅 PC 桌面浏览器）
│  │  ├─ src/
│  │  │  ├─ pages/                # 列表 / 详情 / 录入 / 统计 / 设置 / 登录
│  │  │  ├─ components/           # 物品卡片 / 分组 / 筛选栏 / 撤销条
│  │  │  ├─ api/                  # 仅调用 /api/v1/*，不重算任何日期
│  │  │  └─ main.tsx
│  │  └─ vite.config.ts           # ★ proxy: '/api' → http://localhost:3000
│  └─ server/                     # Hono + SQLite
│     ├─ src/
│     │  ├─ routes/               # auth.ts / items.ts / categories.ts / settings.ts / stats.ts / knowledge.ts
│     │  ├─ middleware/           # auth.ts（会话校验）/ error.ts / validate.ts
│     │  ├─ db/                   # index.ts（连接）/ migrations/*.sql / migrations.ts（执行器）
│     │  ├─ services/             # auth / items / stats（业务逻辑，可单测；首参恒为 userId）
│     │  └─ index.ts
│     └─ data/keepfresh.db        # ← 数据文件（.gitignore，绝不入库）
├─ config/                        # 知识库与配置资产源文件（Git 管理）
│  ├─ shelf_rules.json
│  ├─ copywriting.json
│  └─ feature_flags.json
├─ tools/                         # 本地脚本：mock 数据、知识库校验、周报草稿
├─ PRD/  TechDesign/  docs/       # ★ 文档与代码同仓库（见 §7）
├─ package.json                   # workspace 根（scripts 汇总）
└─ pnpm-workspace.yaml
```

**核心约定**（同 03 §5）：

1. `packages/core` 是**唯一一份**领域逻辑，**不允许在 `apps/web` 里再手写一份**——
   两份实现必然漂移，这是 01 ADR-03 明确禁止的；
2. `packages/core` **必须是纯计算**：不允许 `fetch`、不允许 `node:*`、不允许读文件；
   存储与网络一律通过接口注入。这样 ① 前后端都能用；② 可在纯 Node 下单测；③ 未来移动端直接复用；
3. **推算只在服务端发生**：前端只展示服务端返回的 `expireAt` / `reasonText` / 置信度，**不重算日期**。

## 3. 一条命令启动（V0 的硬验收项）

> PRD 08 §2.5 #1：**`pnpm dev` → 前端 `:5173` + 后端 `:3000` 同时可用**。
> **不要要求开发者开两个终端**——一人公司里"多开一个终端"就是"今天不写代码"的借口。

`pnpm-workspace.yaml`：

```yaml
packages:
  - 'packages/*'
  - 'apps/*'
```

根 `package.json`（scripts 部分）：

```json
{
  "name": "keepfresh",
  "private": true,
  "scripts": {
    "dev": "concurrently -n server,web -c cyan,magenta \"pnpm -F @keepfresh/server dev\" \"pnpm -F @keepfresh/web dev\"",
    "build": "pnpm -r build",
    "typecheck": "pnpm -r typecheck",
    "test": "vitest run --root .",
    "test:watch": "vitest",
    "coverage": "vitest run --coverage",
    "validate:config": "tsx tools/validate-config.ts",
    "lint": "eslint .",
    "mock": "tsx tools/mock.ts"
  },
  "devDependencies": {
    "concurrently": "^9.0.0",
    "tsx": "^4.0.0",
    "typescript": "^5.6.0",
    "vitest": "^2.0.0"
  }
}
```

`apps/web/vite.config.ts` 里的 **proxy 是"一条命令"能成立的关键**：

```ts
export default defineConfig({
  server: {
    port: 5173,
    proxy: { '/api': { target: 'http://localhost:3000', changeOrigin: false } },
  },
});
```

> 有了 proxy，**前后端在浏览器里就是同源**（都是 `localhost:5173`）——
> 因此 V0 **不需要开 CORS**、**不需要为 Cookie 配跨域策略**。
> 这是 03 §4.3 的结论，不要用"配 CORS 白名单"的方式绕过去。

**常用命令一览**：

```bash
pnpm install         # 安装依赖（workspace 全量）
pnpm dev             # ★ 并行启动：server :3000 + web :5173
pnpm typecheck       # 全仓 TS 类型检查
pnpm test            # vitest（core + server services + 集成测试）
pnpm validate:config # 知识库校验（见 §4）
pnpm lint            # 可选（见 §4）
```

## 4. CI / 本地检查流水线

```
提交 Git（main 分支保护：必须过检查）
  → 本地或 CI 执行：
      1. pnpm install --frozen-lockfile
      2. pnpm typecheck        # 全仓类型检查（core + web + server）
      3. pnpm test             # vitest：engine / API 集成（含越权）/ 组件
      4. pnpm validate:config  # 知识库：schema + 禁止词 + 版本号递增
      5. pnpm lint             # 可选（V0 保持轻，能跳过）
  → 通过后：
      合并到 main。**没有"发布"这一步**——V0 跑在 localhost，改完就能自测。
```

### 4.1 V0 用 GitHub Actions 做这三件事就够

```yaml
# .github/workflows/ci.yml
name: ci
on:
  push: { branches: [main] }
  pull_request:
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with: { version: 9 }
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: pnpm }
      - run: pnpm install --frozen-lockfile
      - run: pnpm typecheck
      - run: pnpm test
      - run: pnpm validate:config
```

> **V0 的 CI 只做"检查"，不做"部署"**：没有 npm publish、没有 Docker、没有云部署、没有小程序上传。
> 这是范围收缩后最省心的一点——**CI 从"发布流水线"退化成"质量门禁"**。
>
> 一人公司不追求 CD 全自动。**"AI 写完代码 + 本地一条命令跑起来 + CI 全绿"就是 V0 的全部工程链路。**

### 4.2 ⚠️ GitHub Actions 的 `schedule` 不可靠——用在 CI 合适，用在业务上不合适

| 用途 | 是否合适 | 说明 |
| ---- | ---- | ---- |
| **CI 检查**（push / PR 触发） | ✅ **完全合适** | 事件触发稳定、免费额度充足；**这是 V0 唯一的用法** |
| **`on: schedule` 定时任务** | ❌ **不可靠，禁止用于业务** | 官方明确说明：**高负载时定时任务的运行会被丢弃（dropped）、延迟（常见延迟几分钟到数小时，高峰期可延迟更久）**；且**仓库连续 60 天无活动会自动停用定时工作流** |

> **这条要写清楚，避免以后误用**：
>
> - **V0 根本不需要定时任务**——没有提醒就没有 Cron（PRD 08 §2.3）。所以这条纪律在 V0 是"提前立规矩"；
> - **V1 做提醒时必须注意**：提醒发送属于**业务链路**，**不能挂在 GitHub Actions 的 `schedule` 上**，
>   否则会出现"该发的提醒没发、晚发几小时"。V1 的常开服务端与定时器方案见 03 §8 与 12 §3；
> - 一句话：**GitHub Actions 是 CI 工具，不是定时任务平台。**

### 4.3 `pnpm validate:config` 具体校验什么

| 校验项 | 规则 | 失败后果 |
| ---- | ---- | ---- |
| schema | `shelf_rules.json` / `copywriting.json` 必须过 Zod schema | CI 红，**服务端启动直接失败**（宁可起不来，也不要带着坏规则跑） |
| `id` 唯一性 | 50 类品类 `id` 不重复 | CI 红 |
| 数值合法性 | `T0` / `T1` 非负、上限合理、`aliases` 非空 | CI 红 |
| 禁止词扫描 | 文案库不得出现"保证/一定/绝对/治愈/安全无毒"等承诺性表述（06 §3） | CI 红 |
| 版本号递增 | 规则文件改动必须**同时递增版本号 + 写非空变更说明** | CI 红 |

> **改规则的标准动作**：改 JSON → `pnpm validate:config` → 重启服务端 → **前端刷新即生效（不发版）**。
> 注意：**改规则必须同步改 engine 用例的预期值**——`validate:config` 会提示"版本号需递增"，
> 人工 review 时对照测试 diff（见 §5）。

> 写测试时不要另起一套"测试视角"的描述，**直接把 GWT 抄成 `it()` 的标题**。
> 这样"需求说要做"和"测试说做到了"永远是同一句话，不会漂移。

| **知识库校验** | node/tsx 脚本 | 04 §3 schema + 06 §3 禁止词 | ★ V0 必做（`validate:config`） |
| **前端组件测试** | vitest + @testing-library/react | [02-客户端技术栈](./02-客户端技术栈.md) 的 UI 交互 + PRD [03](../PRD/03-核心功能需求.md) 的 GWT | V0 选择性覆盖关键交互 |

| **reminder（提醒生成器）** | vitest | 05 §1.2 分档表 + GWT-16~19 | **V1 才有** |

### 5.1 API 集成测试：**越权用例是 V0 的头号必测项**

> 03 §4.1 写明："**自建鉴权后，越权是本项目 V0 最可能出的严重 bug**"。
> 因此这类用例**必须自动化**，不能只靠人工点。

```ts
// apps/server/src/routes/items.test.ts（示意）
it('用 A 的 token 读取 B 的物资 → 404，且不返回数据', async () => {
  const a = await register('alice');
  const b = await register('bob');
  const item = await createItem(b.token, { categoryId: 'milk_250ml' });

  const res = await app.request(`/api/v1/items/${item.id}`, {
    headers: { Authorization: `Bearer ${a.token}` },
  });

  expect([403, 404]).toContain(res.status);   // 不是 500，也绝不能返回数据
  expect(await res.text()).not.toContain(item.id);
});

// 同样的 4 个动作都要测：GET 详情 / PATCH 编辑 / DELETE 删除 / POST dispose
```

| 必测的越权动作 | 期望 |
| ---- | ---- |
| `GET /items/:id`（读 B 的） | **403 / 404** |
| `PATCH /items/:id`（改 B 的） | **403 / 404**，且 B 的数据**未被修改** |
| `DELETE /items/:id`（删 B 的） | **403 / 404**，且 B 的数据**仍存在** |
| `POST /items/:id/dispose`（处置 B 的） | **403 / 404** |
| 列表接口 | 只返回本账户数据（A 的列表里**不出现** B 的任何 id） |
| 登出后复用旧 token | **401** |

> **实现保障**（03 §4.1）：所有查询只走 `services/` 层，且 **`services/` 函数首参恒为 `userId`**——
> 让"忘记传 userId"在**类型层面**就报错，而不是靠 review 抓。

### 5.2 测试纪律（食品安全红线 R1 的工程保障）

1. **改规则必须改测试**：任何 `shelf_rules` 系数调整，必须同步更新 engine 用例的预期值；
2. **纯逻辑测试不依赖服务端与浏览器**：这是 `packages/core` 纯 TS 约束的回报；
3. **覆盖率目标**：`packages/core` 语句覆盖 **≥ 80%**（engine 是重点）；`apps/server` 不设硬指标，但**越权用例必须 100% 覆盖**；
4. **`core/` 内无 `fetch` / 无 `node:*`**——用 grep 检查纳入 CI（这是"纯计算"约束的自动化保障）；
5. 涉及**日期**的用例一律**注入固定"今天"**，禁止在测试里读 `new Date()`（否则用例会随时间漂移变红）。

## 6. 数据库迁移纪律

> V0 用 SQLite 单文件 + 手写 SQL 迁移（03 §1.1：**不引入 ORM 迁移框架**）。

```
apps/server/src/db/
├─ index.ts               # better-sqlite3 连接（单例）
├─ migrations/
│  ├─ 001_init.sql        # users / sessions / items / settings
│  ├─ 002_login_attempts.sql
│  └─ 003_....sql
└─ migrations.ts          # 执行器：按文件名顺序执行未应用的迁移，写入 schema_version
```

`schema_version` 表（**执行器的唯一台账**）：

```sql
CREATE TABLE IF NOT EXISTS schema_version (
  version     INTEGER PRIMARY KEY,   -- 对应迁移文件的前缀序号
  name        TEXT    NOT NULL,      -- 文件名
  applied_at  TEXT    NOT NULL       -- ISO 8601
);
```

**四条铁律**：

| # | 纪律 | 理由 |
| ---- | ---- | ---- |
| 1 | **顺序执行、一次性**：启动时按文件名升序执行所有 `version > 当前最大 version` 的脚本，整个批次包在一个事务里 | 半途失败会留下坏库，V0 只有自己用，**宁可启动失败也不要半个 schema** |
| 2 | **只增不改**：**已应用的迁移文件永不修改**（哪怕只改一个注释） | 改了就会与别人（或三个月后的自己）的库产生分叉，且无法察觉 |
| 3 | **破坏性变更走双字段并行过渡**：先加新字段并双写 → 数据回填 → 代码切读新字段 → 下一个版本再删旧字段 | 一步到位的 `DROP/RENAME` 会让旧数据文件直接不可用 |
| 4 | **迁移脚本必须能在"空库"和"当前库"两种情况下都跑通**：本地验证方式 = 删掉 `data/keepfresh.db` 重启一次 + 用旧库文件重启一次 | 这是唯一能低成本发现迁移错误的办法 |

> - **V0 不回滚迁移**（SQLite 上成本高于收益）：出错的正确做法是**从备份的 `.db` 文件恢复**；
> - **备份就是拷贝 `apps/server/data/keepfresh.db`**，建议每周一次（写进 09 章周节奏）；
> - V1 迁 Postgres / 云 DB 时，这套 `schema_version` + 顺序脚本的台账**直接有据可依**（PRD 08 §2.4）。

## 7. Git 工作流（一个人也要规范）

```
main（可运行状态：pnpm dev 起得来、CI 全绿）
 └── feat/xxx   每周主题分支（PRD 08 §4：每周只做一件事）
      ├── 提交粒度：一个逻辑变更一个 commit（PRD/TechDesign 文档变更也进仓库！）
      └── merge 前：pnpm typecheck + pnpm test + pnpm validate:config 全绿
```

- **`feat/` 分支命名跟主题走**：`feat/auth`、`feat/engine-climate`、`feat/manage-view`、
  `feat/dispose-undo`、`feat/knowledge-50`（对应 PRD 08 §2.2 的模块清单）；
- **PRD / TechDesign 文档与代码同仓库**：中断 1 个月后，靠 **README + 文档**恢复上下文（PRD 11 §8）；
  **文档修改与代码修改在同一个分支里提交**，避免"代码改了文档没改"；
- 提交信息模板：`feat(engine): 气候档改为三档并补用例`（conventional commits，轻量即可）；
- 紧急热修：`hotfix/*` 分支直接修直接进 main，事后补测试；
- **main 分支保护**：必须过 CI 才能合并（GitHub 免费版支持）。

### 7.1 `.gitignore` 是安全线，不是可选项

> ✅ **2026-08 已补齐**：仓库根 `.gitignore` 原先只有系统文件三项（`Thumbs.db` / `.DS_Store` / `*.log`），
> **缺少数据文件与密钥的排除项**——那正是"密码哈希 + 会话 token 被提交进仓库"的红线。

## 8. 开发效率工具（一人公司加成）

| 工具 | 用途 |
| ---- | ---- |
| **AI 辅助编码**（Cursor / Claude Code） | 大部分样板代码由 AI 起草；**Prompt 直接喂 PRD [03](../PRD/03-核心功能需求.md) 的 GWT 验收标准**，让 AI 输出"能过验收"的实现，而不是"看起来对"的实现 |
| **`tools/mock.ts`** | 生成 **200 条（可加到 500）假物资数据**，测列表渲染性能（PRD 08 §2.5 #5：500 条 ≤ 1 秒）与分组/筛选/搜索组合 |
| **`tools/validate-config.ts`** | `pnpm validate:config` 的实现（§4.3），CI 与本地共用同一支脚本 |
| **`tools/weekly.ts`** | 从库中导出周报草稿（在库件数 / 本周处置 / 本周新增），供 PRD 08 §4 周日复盘 |
| **知识库初稿生成** | 让 AI 按 04 §3 schema 起草 50 类，**人工逐条审核**（[PRD 08 §4 迭代节奏](../PRD/08-MVP范围与版本规划.md)、[PRD 09 §4 研发工作流](../PRD/09-一人公司工作流.md) 第 2 条，**食品安全红线，不可跳过**） |
| **备份脚本** | 一条命令拷贝 `data/keepfresh.db` 到带日期的副本（§6） |

> **AI 边界（写进纪律，不是建议）**：
> ① AI **可以**起草表单、路由、SQL、迁移脚本、测试骨架；
> ② AI **不可以**决定任何期限数值——**推算数值只能来自 `config/shelf_rules.json`，且必须人工逐条审核**；
> ③ 用 AI 起的每一个 PR，**merge 前都要问一句"这段代码会不会让某件东西的到期日算错"**。

## 9. V1 起才需要的工程化项（**明确不在 V0**）

> 列出这一节是为了让"以后要做什么"有明确落点，**避免 V0 期间被这些事干扰**（PRD 08 §2.3）。
> 完整方案见 [12-Web优先方案](./12-Web优先方案（平台迁移决策）.md) 与 [03 §8](./03-服务端技术栈.md)。

| 能力 | V1 形态 | V0 状态 |
| ---- | ---- | ---- |
| **公网部署** | 域名 + HTTPS + **备案决策**（PRD 11 R13，V1 第一件前置事） | ❌ 不做，跑 `localhost` |
| **常开服务端** | 必须常开，否则提醒失效；注意 Workers 免费版 CPU 10ms / 子请求 50 的硬墙 | ❌ 不做 |
| **定时任务 / Cron** | 提醒调度；**禁用 GitHub Actions `schedule`**（见 §4.2） | ❌ 不做，无提醒即无定时 |
| **推送发送** | Web Push（VAPID）等通道；订阅生命周期管理（404/410 清理） | ❌ 不做 |
| **移动端构建** | PWA「添加到主屏幕」或 RN/Expo（**复用 `packages/core`**）；弱网批量补传 `/items/batch` | ❌ 不做，但**接口已在 V0 留好** |
| **ASR 集成** | 浏览器端归一化为 16k 单声道 WAV + 云 ASR 代理 | ❌ 不做 |
| **CD / 自动化发布** | GitHub Actions 做部署（若届时用云服务） | ❌ 不做，V0 无"发布"环节 |
| **数据库迁移到 Postgres/云 DB** | 复用 §6 的 `schema_version` 台账 | ❌ 不做，V0 就是 SQLite 单文件 |
