# 08 · 工程化与 CI

> 一人公司的工程化目标不是"最佳实践大全"，而是三件事：
> **① 中断一个月能无缝续接（R7）；② 核心逻辑有测试兜底（食品安全红线 R1 不允许"拍脑袋改"）；
> ③ 发版/发布配置 5 分钟内完成。**
> PRD 依据：09 §4 研发工作流、11 §8 单人开发风险、07 §5 可维护性。

---

## 1. Monorepo 布局（code/ 目录）

```
code/
├── miniprogram/                  # 小程序工程（微信开发者工具打开此目录）
│   ├── miniprogram/              # 页面/组件/资源
│   │   ├── pages/                # 首页 / 语音页 / 确认页 / 设置...
│   │   ├── components/           # 语音大按钮 / 物品卡片 / 横幅...
│   │   ├── store/                # mobx stores（02 §2）
│   │   ├── services/             # 平台能力封装（voice/storage/cloud/subscribe）
│   │   ├── core/                 # ★ 纯 TS 逻辑层（05）——与 shared 同源
│   │   ├── assets/               # 图标插画（压缩后）
│   │   └── app.ts / app.json / app.wxss
│   ├── typings/                  # 小程序官方类型
│   └── project.config.json
├── cloudfunctions/               # 云函数（每个目录一个函数，含独立 package.json）
│   ├── reminder/  subscribe/  analytics/  knowledge/  user/
│   └── family/  export/  pay/   # (P1/V1.2)
├── shared/                       # 端云共享的纯 TS 包（npm workspace）
│   ├── types/                    # Item / CategoryRule / Events（04）
│   ├── schemas/                  # JSON Schema 定义（知识库/文案/埋点）
│   └── validate/                 # 校验器实现（供端侧与发布脚本复用）
├── config/                       # 配置资产源文件（06，Git 管理）
│   ├── shelf_rules.json
│   ├── copywriting.json
│   ├── feature_flags.json
│   └── scripts/                  # validate.js / publish.js / icons.js
├── tools/                        # 本地脚本：知识库校验、模拟数据生成、周报导出
├── docs/                         # 开发笔记、决策记录（ADR）
└── package.json                  # workspace 根（vitest / lint / scripts）
```

> **核心约定**：`miniprogram/miniprogram/core/` 与 `shared/` 保持**同一份代码**——
> 实现方式二选一：① npm workspace + 小程序构建 npm（推荐）；② 构建脚本同步复制（V1 可先用，
> 简单直接）。**不允许两份手写副本**（那是漂移与 bug 的来源，01 ADR-03）。

## 3. 环境与发布通道

| 环境 | 云开发环境 | 用途 |
| ---- | ---- | ---- |
| dev | `keepfresh-dev` | 开发自测、定时触发器调试 |
| prod | `keepfresh-prod` | 线上体验版/正式版 |

- 小程序侧用 `wx.cloud.init({ env: ... })` 按构建环境切换（envList 配置）；
- **测试账号隔离**：dev 环境的用户数据与 prod 完全隔离（防止内测数据污染线上统计）；
- 内测发布：体验版（微信群二维码）→ 稳定后提交审核 → 正式版。

## 4. CI 流水线（miniprogram-ci，本地脚本即可起步）

```
提交 Git（main 分支保护：必须过本地检查）
  → 本地/CI 执行：
      1. pnpm install && pnpm typecheck        # TS 类型检查（miniprogram + cloudfunctions + shared）
      2. pnpm test                             # vitest：parser / engine / reminder / 云函数纯逻辑
      3. pnpm validate:config                  # config/ 校验：schema + 禁止词 + 版本号递增（06 §3）
      4. pnpm lint                             # 代码规范（可选，V1 可跳过，保持轻）
  → 通过后：
      手动：微信开发者工具上传（或 miniprogram-ci 命令行上传体验版，自动填版本号+备注）
      配置发布：pnpm publish:config            # 上传云存储 + 写 knowledge_versions 台账（06 §3）
```

> V1 用 **GitHub Actions（免费额度）+ miniprogram-ci** 即可；一人公司不追求 CD 全自动，
> "一键上传体验版"是性价比最高的自动化（每周五发版场景，09 §4）。

## 5. 测试策略（验收标准即测试用例——03 章 GWT 就是用例清单）

| 测试对象 | 工具 | 用例来源 |
| ---- | ---- | ---- |
| parser（语音解析） | vitest | 03 F-01 的 GWT-01~04 + 50 类 × 句式矩阵（05 §1.4） |
| engine（推算引擎） | vitest | 04 §2 示例表逐品类用例 + 气候组合矩阵 + 边界（04 §6） |
| reminder（提醒生成器） | vitest | 05 §1.2 分档表 + GWT-16~19 + 合并/限频/沉默策略 |
| 知识库校验 | node 脚本 | 04 §3 schema + 05 §4 禁止词（文案库） |
| 云函数（纯逻辑部分） | vitest（mock 云 SDK） | 幂等（重复触发不重发）、越权拒绝、字段白名单 |
| 端到端（真机） | 手动清单 | 02 §7 兼容矩阵 + 断网流程（01 §8 验收） |

**测试纪律**（食品安全红线 R1 的工程保障）：

1. **改规则必须改测试**：任何 shelf_rules 系数调整，必须同步更新 engine 用例预期值——发布脚本
   `validate.js` 会检查"版本号递增 + 变更说明非空"，人工 review 时对照测试 diff；
2. **纯逻辑测试不依赖小程序**：这是 `core/` 纯 TS 约束的回报（05 §4）；
3. 覆盖率目标：`core/` 语句覆盖 ≥ 80%（parser/engine/reminder 三个模块重点）。

## 6. Git 工作流（一个人也要规范）

```
main（可发布状态）
 └── feat/xxx  每周主题分支（08 §4 每周只做一件事）
      ├── 提交粒度：一个逻辑变更一个 commit（PRD 文档变更也进仓库！09 §4 第 4 条）
      └── merge 前：typecheck + test + validate:config 全绿
```

- **PRD/TechDesign 文档与代码同仓库**：中断 1 个月，靠 README + 文档恢复上下文（11 §8）；
- 提交信息模板：`feat(parser): 支持"上周X"日期解析`（conventional commits，轻量即可）；
- 紧急热修：`hotfix/*` 分支直接修直接发，事后补测试。

## 8. 验收清单

- [ ] 新克隆仓库 → `pnpm install && pnpm typecheck && pnpm test && pnpm validate:config` 全绿（新人 10 分钟上手）；
- [ ] 修改 shelf_rules 一个系数 → validate 脚本报"需要更新测试"提醒（或测试红）；
- [ ] 一键命令完成"上传体验版"与"发布配置"（各 1 条命令）；
- [ ] `core/` 内无 `wx.*` 引用（grep 检查纳入 CI）。
