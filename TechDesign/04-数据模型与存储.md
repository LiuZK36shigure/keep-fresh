# 04 · 数据模型与存储（V0：SQLite）

## 1. 领域模型（`packages/core/schemas`，前后端共用）

> 这份类型是**唯一真源**：服务端用它写库，前端用它渲染，API 契约用它校验（Zod）。
> **不要在前端另外定义一份 Item**。

```typescript
// ── 账户 ──
interface User {
  id: string;              // UUID
  username: string;        // 展示用原名
  createdAt: string;       // ISO
}

// ── 设置（每用户一行）──
interface Settings {
  userId: string;
  climate: {
    city?: string;         // 自填，仅用于展示（V0 不做定位）
    summerMode: boolean;   // 夏季高温
    humidMode: boolean;    // 潮湿
    plumRainMode: boolean; // 梅雨
    // 三档全 false = "不确定"档 → 走保守系数（见 §3.6）
  };
  defaultStorage: StorageLocation;  // 新增物品时的默认存储位置
  updatedAt: string;
}

type StorageLocation =
  | 'fridge' | 'freezer' | 'room' | 'shade' | 'medicine' | 'cosmetic' | 'other';

// ── 物资（核心）──
interface Item {
  // 标识与归属
  id: string;                    // 客户端生成 UUID v4 —— 幂等 & 未来离线批量补传
  userId: string;                // 归属（所有查询必带，见 03 §4.1）

  // 记录要素（表单字段）
  categoryId: string;            // 知识库品类 ID；自定义为 'custom:xxx'
  categoryName: string;          // 展示名（保存时快照，防知识库改名后历史错乱）
  categoryModel: 'date' | 'state';   // 日期驱动 / 状态驱动（PRD 04 §7）
  qty: number;                   // 数量（默认 1；V0 仅统计与展示）
  buyDate: string;               // 'YYYY-MM-DD'，不得晚于今天
  openedAt: string | null;       // 开封日期；null = 未开封
  storageLocation: StorageLocation;
  note: string;                  // 备注（可空字符串）

  // 推算结果快照（服务端写入，见 01 §4.1）
  estimate: {
    expireAt: string;            // 到期日（状态驱动 = 窗口下限）
    windowEndAt: string;         // 窗口上限（日期驱动 = expireAt）
    confidence: 'high' | 'mid' | 'low';
    reasonText: string;          // "未开封冷藏 7 天 × 高温潮湿 0.64 ≈ 4 天"
    climateFactors: string[];    // ['high_temp','humid']
    ruleVersion: string;         // 推算所用知识库版本（可追溯）
  };
  manual?: {                     // 用户手动修正（F-06 反馈回路）
    correctedAt: string;
    newExpireAt: string;
    reason: 'actual_bad' | 'still_fine' | 'other';
  };

  // 状态
  status: 'active' | 'disposed';         // 存储态（仅两种）
  disposeType: 'used' | 'discarded' | 'gifted' | null;
  disposedAt: string | null;
  deletedAt: string | null;              // 软删除（支持 5 秒撤销 + 统计不回退）

  createdAt: string;
  updatedAt: string;
}

// ⚠️ 注意：'recorded' | 'opened' | 'expiring' | 'expired'（PRD 06 §2 的状态机）
//     **不是存储态**，而是服务端在查询时按当前日期**推导**出来的展示态。
//     这样"今天到期"会随时间自动变化，不需要定时任务去刷库——**V0 没有 cron，这点很关键**。
type DerivedStatus = 'recorded' | 'opened' | 'expiring' | 'expired';
```

### 1.1 V0 保留的 V1 字段（只存不算）

> 这是"保留接口"在数据层的落地：**字段先留好，V1 加提醒时不用改表结构**。

| 字段（V1 启用） | V0 行为 | V1 用途 |
| ---- | ---- | ---- |
| `remindPolicy` | 不写（默认 NULL） | 提醒档位 |
| `windowStart` | 不写 | 提醒窗口起点 |
| `lastRemindedAt` | 不写 | 幂等去重 |
| `pushSubscriptions` 表 | **不建**（V1 迁移时新增表） | 推送订阅 |

> 设计取舍：**加字段是廉价的，加表也是廉价的**（SQLite `ALTER TABLE ADD COLUMN` / `CREATE TABLE`
> 都是向前兼容操作）。所以 V0 **不预先建空表**，只在文档里写清 V1 要加什么——
> 这比建一堆永远不写的表更容易理解。

## 2. 数据库 Schema（SQLite DDL）

```sql
-- ── 迁移版本 ──
CREATE TABLE schema_version (
  version     INTEGER PRIMARY KEY,
  applied_at  TEXT NOT NULL
);

-- ── 1. 用户 ──
CREATE TABLE users (
  id             TEXT PRIMARY KEY,           -- UUID
  username       TEXT NOT NULL,              -- 展示用，保留用户输入的大小写
  username_lower TEXT NOT NULL UNIQUE,       -- 查重与登录用（大小写不敏感）
  password_hash  TEXT NOT NULL,              -- argon2id / bcrypt，绝不存明文
  created_at     TEXT NOT NULL,
  updated_at     TEXT NOT NULL
);

-- ── 2. 会话 ──
CREATE TABLE sessions (
  token_hash  TEXT PRIMARY KEY,              -- 只存 token 的哈希，防库泄露即被盗用
  user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at  TEXT NOT NULL,
  expires_at  TEXT NOT NULL,
  last_seen_at TEXT NOT NULL
);
CREATE INDEX idx_sessions_user    ON sessions(user_id);
CREATE INDEX idx_sessions_expires ON sessions(expires_at);

-- ── 3. 登录限流 ──
CREATE TABLE login_attempts (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  username_lower TEXT NOT NULL,
  ip           TEXT,
  succeeded    INTEGER NOT NULL,             -- 0/1
  attempted_at TEXT NOT NULL
);
CREATE INDEX idx_attempts_user_time ON login_attempts(username_lower, attempted_at);

-- ── 4. 设置（每用户一行）──
CREATE TABLE settings (
  user_id         TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  city            TEXT,
  summer_mode     INTEGER NOT NULL DEFAULT 0,   -- SQLite 无 bool，用 0/1
  humid_mode      INTEGER NOT NULL DEFAULT 0,
  plum_rain_mode  INTEGER NOT NULL DEFAULT 0,
  default_storage TEXT NOT NULL DEFAULT 'fridge',
  updated_at      TEXT NOT NULL
);

-- ── 5. 物资（核心表）──
CREATE TABLE items (
  id               TEXT PRIMARY KEY,          -- 客户端生成 UUID
  user_id          TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,

  category_id      TEXT NOT NULL,
  category_name    TEXT NOT NULL,
  category_model   TEXT NOT NULL CHECK (category_model IN ('date','state')),
  qty              INTEGER NOT NULL DEFAULT 1 CHECK (qty > 0),
  buy_date         TEXT NOT NULL,             -- 'YYYY-MM-DD'
  opened_at        TEXT,                      -- NULL = 未开封
  storage_location TEXT NOT NULL,
  note             TEXT NOT NULL DEFAULT '',

  -- 推算快照
  expire_at        TEXT NOT NULL,
  window_end_at    TEXT NOT NULL,
  confidence       TEXT NOT NULL CHECK (confidence IN ('high','mid','low')),
  reason_text      TEXT NOT NULL,
  climate_factors  TEXT NOT NULL DEFAULT '[]',  -- JSON 数组字符串
  rule_version     TEXT NOT NULL,

  -- 手动修正
  manual_corrected_at TEXT,
  manual_expire_at    TEXT,
  manual_reason       TEXT,

  -- 状态
  status       TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active','disposed')),
  dispose_type TEXT CHECK (dispose_type IN ('used','discarded','gifted')),
  disposed_at  TEXT,
  deleted_at   TEXT,                          -- 软删除

  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);

-- ⚠️ 索引是 V0 性能与正确性的关键，不是可选项
CREATE INDEX idx_items_user_expire   ON items(user_id, expire_at);          -- 列表默认排序 / 临期筛选
CREATE INDEX idx_items_user_status   ON items(user_id, status, deleted_at); -- "我的未处置物资"
CREATE INDEX idx_items_user_storage  ON items(user_id, storage_location);   -- 分组视图
CREATE INDEX idx_items_user_buydate  ON items(user_id, buy_date);           -- 按购买日排序
CREATE INDEX idx_items_user_category ON items(user_id, category_id);        -- 按品类统计

-- ── 6. 校准样本（用户手动修正到期日时写入）──
CREATE TABLE calibration_samples (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id        TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  item_id        TEXT NOT NULL,
  category_id    TEXT NOT NULL,
  climate_factors TEXT NOT NULL DEFAULT '[]',
  direction      TEXT NOT NULL CHECK (direction IN ('shorter','longer')),
  reason         TEXT NOT NULL,
  rule_version   TEXT NOT NULL,
  created_at     TEXT NOT NULL
);
CREATE INDEX idx_calib_user_cat ON calibration_samples(user_id, category_id);
```

> **`knowledge_versions` / `events` / `families` / `orders` 等表在 V0 不建**：
> 知识库版本放 `settings` 的返回值里即可；埋点在 V0 只做本地日志（见 §5）；
> 家庭共享与支付属于 V2。

### 2.1 一致性约定

| 约定 | 说明 |
| ---- | ---- |
| 时间格式 | 日期用 `'YYYY-MM-DD'`；时间戳用 UTC ISO 字符串。**不要混用** |
| 布尔 | SQLite 无 bool，统一 `INTEGER 0/1`，在 `services/` 层转成 `boolean` |
| 数组 | 用 JSON 字符串存（`climate_factors`），在 `services/` 层 `JSON.parse` |
| 软删除 | `deleted_at IS NOT NULL` 的记录**一律不出现在任何查询里**（写成统一的 `WHERE deleted_at IS NULL` 片段） |
| 外键 | 建表时 `PRAGMA foreign_keys = ON`；`ON DELETE CASCADE` 只在删除**用户**时使用 |
| 事务 | 写操作（尤其是"重算 + 更新"）**必须包在事务里** |

## 3. 推算引擎的输入输出（与 `packages/core/engine` 的契约）

### 3.1 输入

```typescript
interface EstimateInput {
  rule: CategoryRule;              // 来自 shelf_rules.json
  buyDate: string;
  openedAt: string | null;
  storageLocation: StorageLocation;
  settings: Settings['climate'];
  today: Date;                     // ⚠️ 显式传入，不在 core 内读系统时钟（01 §5）
}
```

### 3.2 输出

```typescript
interface EstimateResult {
  expireAt: string;
  windowEndAt: string;
  confidence: 'high' | 'mid' | 'low';
  reasonText: string;              // 可直接展示给用户
  climateFactors: string[];
}
```

### 3.3 计算流程（PRD 04 的落地）

```
① 品类基线：T0 = rule.T0[location] ?? rule.T0[default]
② 状态修正：base = openedAt ? T1 : T0          // 开封后从开封日重新计时
            存储位置不符 → ×0.5
③ 气候修正：k = 温度系数 × 湿度系数 × 特殊季系数（按 climateSensitivity 分级生效）
④ 取整：T = roundDown(base × k)                // 保守原则：取更短期限
⑤ 到期日：expireAt = (openedAt ?? buyDate) + T
⑥ 置信度：按依据完整性打分（PRD 04 §5.1）
```

> ⚠️ **三处必须在 V0 修掉的旧问题**（上一轮文档审查发现，见审查报告 P1-3 / P1-10）：
>
> 1. **"高温潮湿 = 0.8" 是错的**。PRD 04 §4.1 规定 `k = 温度 × 湿度 × 特殊季`，
>    高温 0.8 × 潮湿 0.8 = **0.64**。0.8 只是"温度"单项。**PRD 03 GWT-11 与 PRD 06 §4.3
>    线框里的 0.8 与 "+6/+5 天" 都写错了**，实现时以本节公式为准，并回头修正那两处。
> 2. **品类级 `summerFactor` 与气候级 `temp_hot` 重复计**（同一份规则里，鲜牛奶被 0.7 与 0.8 各罚一次）。
>    V0 决定：**删除品类级 summerFactor，统一由气候因子表达**（气候档是用户可见的，更可解释）。
> 3. **"不确定"气候档必须有系数**。三档全 false 时取 **`k = 0.9`**（保守），
>    并在 `reasonText` 里写明"气候档未设置，已按保守值估算"——
>    原设计留空等于默认 1.0，**信息最少的用户反而拿到最长期限**，与保守原则相反。

### 3.4 状态驱动品类（水果等，PRD 04 §7 最小版）

- 不推算单点日期：输出 `[buyDate + window[0], buyDate + window[1]]` 作为窗口；
- `expireAt` 存窗口下限、`windowEndAt` 存上限；
- `confidence` 固定 `'mid'`，详情页明示"状态类物品不承诺精确期限"；
- 检查提醒节奏字段 `checkRhythm` **在 V0 只存不推**（V1 启用）。

### 3.5 展示态推导（服务端查询时计算，不落库）

| 展示态 | 条件 |
| ---- | ---- |
| `expired` | `today > expireAt` |
| `expiring` | 距 `expireAt` ≤ 提前提醒天数（按 PRD 05 §1.2 分档） |
| `opened` | `openedAt IS NOT NULL` 且未过期未临期 |
| `recorded` | 其他 |

> **这一条是 V0 不需要 cron 的原因**：状态是"算"出来的，不是"刷"出来的。
> V1 加提醒时才会需要定时任务去"主动发现"到点的物品。

## 5. 文案库与埋点（V0 的极简版）

### 5.1 `config/copywriting.json`

- V0 只需展示型文案：空状态引导、确认提示、正向反馈、免责声明；
- **不再需要"双模板体系"**（`banner.*` / `subscribe.*`）——那套划分的唯一原因是微信订阅消息的
  模板字段限制，**随小程序一并作废**；
- 保留"禁止词"扫描（"库存告急""请立即处理"等惊吓式表达）写进 `pnpm validate:config`。

### 5.2 埋点：V0 只写本地日志

> **V0 不做埋点上报系统**。理由：V0 的用户就是你自己，看日志比看仪表盘快。

- 服务端用 `console` + 结构化 JSON 行日志（`request_log`），记录：方法、路径、状态码、耗时、`userId`；
- **禁止**在日志里打印密码、token、备注全文（03 §4.3）；
- 前端只在开发模式打 `console`；
- 北极星指标（端侧聚合上报那套，旧 TechDesign 07）**整体推迟到 V1**——
  V0 没有"提醒驱动"这一环，那个指标本来也测不出来。

## 6. 迁移策略（R7 单人开发的生命线）

| 场景 | 策略 |
| ---- | ---- |
| Schema 升级 | `migrations/001_init.sql`、`002_add_xxx.sql`…**顺序执行、只增不改**；`schema_version` 表记录已应用版本；启动时自动补跑 |
| 破坏性变更 | **禁止**直接删列/改语义；走"加新列 → 双写 → 回填 → 停用旧列"四步 |
| 知识库升级 | 全量替换 JSON + 版本号递增；**已在库的 `estimate` 快照不回溯**（历史可追溯，靠 `ruleVersion`）；用户可手动触发"重算全部" |
| 数据备份 | **拷贝 `data/keepfresh.db` 即完成备份**（SQLite 单文件）。建议每周一次，写进周节奏 |
| V1 迁移 | SQLite → Postgres：表结构基本可直接平移；届时引入 ORM 并把 SQL 逐条复核 |
| 数据导出 | V0 不做（`sqlite3 .dump` 就是导出）；V1 提供 JSON 导出（PRD 08 §5） |

> **迁移执行器**（约 30 行代码）：读 `migrations/` 目录 → 按文件名排序 → 对比 `schema_version`
> → 在**单个事务内**依次执行未应用的脚本 → 写入新版本号。
> **不要引入 knex/prisma migrate**——6 张表的项目不值得。

## 7. 数据一致性原则

1. **单写者**：`apps/server/src/services/` 是唯一写数据库的地方，且必须带 `userId`；
2. **推算快照与规则版本绑定**：`estimate.ruleVersion` 让"这条记录当时是按哪版规则算的"永远可查；
3. **状态是推导值**：`recorded/opened/expiring/expired` **不落库**（§3.5），因此不存在"状态过期"的问题；
4. **软删除优先**：删除物品写 `deleted_at`，5 秒撤销只是把它置回 NULL；**统计因此不会回退**；
5. **撤销窗口由前端控制，但服务端永远允许 restore**——前端 5 秒后隐藏入口即可，不做服务端时间锁（避免时钟不一致的坑）。
