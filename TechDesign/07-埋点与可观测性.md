# 07 · 埋点与可观测性

> 📌 **V0 生效范围（2026-08 范围收缩）**：
> **本章约 90% 的内容属于 V1，V0 不实现。**
>
> | 节 | 内容 | V0 状态 |
> | ---- | ---- | ---- |
> | §1 事件清单 | 13 个事件 | ⏸ **V1**（V0 无提醒/语音，一半事件测不出来） |
> | §2 端侧上报链路 | 本地队列 + 批量上报 | ⏸ **V1** |
> | §3 云端接收 | analytics 云函数 | ⏸ **V1**（V0 无云端） |
> | §4 错误上报 | 极简错误日志 | 🔄 **V0 简化为服务端结构化日志**（见下） |
> | §5 指标看板 | 13 项指标 | ⏸ **V1**（**V0 的"用户"就是你，看日志比看仪表盘快**） |
>
> **V0 实际做法**：服务端用 `console` 输出**结构化 JSON 行日志**，字段为
> `方法 / 路径 / 状态码 / 耗时 / userId`，**禁止记录密码、token、备注全文**。
> 不做上报、不做仪表盘、不做北极星口径（V0 没有"提醒驱动"这一环，那个指标本来也测不出来）。
> 详见 [TechDesign 04 §5](./04-数据模型与存储.md)。
>
> ⚠️ **一条必须记住的事实**：原 §5 的"周闭环数"用**端侧聚合上报**口径——
> 那是"端侧为权威"时代的产物，**随 V0 改为服务端权威已不再适用**（服务端本来就有全量数据）。
> V1 重做埋点时，直接**服务端聚合**即可，不需要端侧上报链路。
>
> **版本号**：**V0**（=P0，当前）/ **V1**（=P1）/ **V2**（=P2）。

> 一人公司也要埋点（03 §4）：没有数据，下一版不知道做什么（08 范围原则 3）。
> 但同样重要：**埋点必须匿名、最小、可解释**（07 §1），且不做复杂用户画像系统。
> 本章定义：事件清单、端侧上报链路、云端接收、错误上报、指标看板。

## 1. 事件清单（对应 03 §4 埋点表，V1 全集）

| 事件名 | 触发 | 关键 props（白名单） | 用途 |
| ---- | ---- | ---- | ---- |
| `app_launch` | 启动 | `scene`（场景值） | 渠道/冷启动分析 |
| `record_voice_start` | 点语音按钮 | — | 语音漏斗 |
| `record_voice_success` | 识别+解析成功 | `category`（大类） | 语音漏斗、准确率 |
| `record_voice_fail` | 识别/解析失败 | `reason`（enum） | 漏斗、词典迭代 |
| `record_save` | 记录保存 | `category`、`isVoice`、`isTemplate`、`isCustom` | 北极星分子、记录结构 |
| `estimate_modified` | 修改推算日期 | `direction`（shorter/longer）、`reason` | 推算准确率（01 §3.2） |
| `remind_received` | 横幅渲染 | `type`（expiring/expired/opened/check） | 提醒有效性（横幅口径，已排除订阅重复，2026-08） |
| `remind_click` | 点击提醒卡片 | `type`、`action`（open/used/discard/gift/postpone）、`channel`（banner/subscribe/service） | 提醒有效性、处置转化 |
| `item_disposed` | 处置动作 | `type`（used/discard/gift）、`isFromRemind` | 北极星（端侧聚合原料） |
| `subscribe_granted` / `subscribe_denied` | 订阅授权结果 | `quota`（granted 时授权条数） | 提醒渠道健康度、配额账本（2026-08） |
| `weekly_closed` | 端侧周聚合上报 | `week`、`fromRemind`、`active`（聚合数字） | **北极星指标**（2026-08 新增，01 §3.2 计算口径） |
| `invite_sent` / `invite_accepted`（P1） | 家庭邀请 | — | 裂变验证（01 §3.2） |
| `knowledge_update` | 知识库版本更新 | `fromVer`、`toVer` | 配置发布监控 |

> 白名单原则：props 只能取枚举/分类值，**禁止携带物品名、日期、金额等用户内容**（07 §1 最小收集）。

## 2. 端侧上报链路（本地队列 → 批量 → 云端）

```
core/analytics.track(event, props)
  → 组装 { event, ts, props, anonId }（anonId = sha256(openid+salt)[0:16]，不可逆）
  → 入本地队列（kf_events_queue，上限 500 条，超出丢最旧并计数）
  → 满足阈值（≥20 条 或 距上次上报 ≥30 秒）→ 批量调 analytics 云函数
  → 成功清队列；失败保留（下次合并上报，避免重试风暴）
```

**设计要点**：

- **本地先聚合**：同一 session 内的 `remind_received` 等高频事件先计数再上报（如 1 条带 count=5），
  节省请求额度（V0 无此问题——事件不离开服务端）；
- **端侧聚合上报（北极星，2026-08 新增）**：`weekly_closed` 由端侧统计"记录→处置"同物品闭环数
  （本地有全量数据，无需物品级事件上云），按 `isFromRemind` 分桶，每周一聚合上报一次；
  这是匿名原则与北极星可计算之间的平衡点（01 §3.2）；
- **离线不丢**：队列持久化，联网后自动补报（弱网场景也成立）；
- **不上报用户内容**：事件白名单 schema 在端侧与云端双重校验；
- **采样**：`record_voice_*` 与 `remind_*` 在用户量 >1 万时抽样 50%（V1 内测阶段全量）。

## 3. 云端接收（analytics 云函数）—— ⏸【V1，且实现方式会变】

> ⏸ **V0 无云端、无上报**。且 **V1 重做时也不该照抄本节**：原设计是"端侧上报 → 云端接收"，
> 而 V0 起服务端已是权威数据源，**事件直接写服务端数据库即可，不需要上报链路**。
> 保留本节仅为记录原始设计意图。

```
入参校验：event ∈ 白名单 && props 键 ∈ 白名单 && 类型正确
  → 非法 → 丢弃 + 记 error_log（不返回错误给客户端，静默）
  → 合法 → 批量写 events 集合（数组式批量插入）
  → 定期清理：events 保留 90 天（脚本/定时函数），calibration 保留 180 天
```

> events 集合**不建 openid 索引、不关联 users**——物理上就不具备画像能力，这是对隐私承诺的工程保障（11 §9）。

## 5. 指标看板 —— ⏸【V1】

> ⏸ **V0 不做指标看板**。V0 的"用户"就是你自己，看日志比看仪表盘快。
> 下表保留作为 **V1 的指标清单**，但**计算方式需要重写**——见下方说明。

| 指标 | 计算方式（V1 重写） | 目标（01 §3.2） |
| ---- | ---- | ---- |
| **周闭环数（北极星）** | **服务端 SQL 聚合**（`items` 表按 `disposed_at` 周分组） | 环比增长 |
| 周记录量 | `items` 按 `created_at` 周计数 | 人均 ≥ 5 条/周 |
| 单条记录耗时 | 前端计时（`record_start` → 保存成功） | ≤ 10 秒 |
| 语音占比 | 保存记录的 `inputMethod` 比例 | ≥ 60% |
| 语音解析准确率（内部口径） | 解析成功 / 解析总数 | ≥ 80% |
| 确认页修改率（产品口径） | 发生字段修改的会话 / 语音会话 | ≤ 30% |
| 最终保存成功率 | 保存成功 / 语音会话总数 | ≥ 90% |
| 推算修改率 | 有 `manual` 的记录 / 总记录（**排除状态驱动品类**） | ≤ 20% |
| **通知授权率** | 授权成功 / 展示授权引导 | ≥ 30% |
| 提醒点击率 | 点击 / 送达 | ≥ 40% |
| 48h 处置率 | 临期提醒后 48h 内处置数 / 临期提醒数 | ≥ 50% |
| 次日/30 日留存 | 登录事件按 `user_id` 去重 | ≥ 40% / ≥ 20% |
| 提醒关闭率 | 关闭推送的用户 / 活跃用户 | ≤ 15% |

**V1 的实现方式（取代原"方案 A/B"）**：

- **直接对服务端数据库写聚合查询**（SQL 或一个 `/api/v1/stats` 端点），
  **不需要"端侧上报 → 云端接收"这条链路**——因为服务端本来就是权威数据源；
- 周报 = 一条 SQL，可写进 `tools/weekly.ts` 一键导出；
- **仍不做**：实时大屏、复杂漏斗平台、用户分群画像（与最小收集原则冲突，PRD 03 §4 明确不做）。

> ⚠️ **两处修正**（上一轮审查 P1-8 / P2 #34-35）：
> ① 原"订阅授权率 `subscribe_granted/(granted+denied)`"改为 **通知授权率**——
> Web Push 的授权是 **origin 级全局**的，没有"订阅配额"这个概念；
> ② 原"方案 A：小程序后台自定义分析（微信公众平台）"**整条作废**——Web 端没有这个后台。
>
> ⚠️ 另需注意（上一轮审查 P1-16）：**"提醒点击率""送达率"这类指标在 iOS 上可能给出虚假的好数字**——
> 推送订阅会静默失效且服务端不一定收到错误。V1 必须以
> "**用户随后是否打开了网页**"作为推送健康度的真实性校验。

## 6. 验收清单

- [ ] 断网记录 5 条 → 联网后队列自动补报，事件不丢（可对照本地计数）；
- [ ] 上报 payload 中不含任何物品名/日期/金额字段（抓包检查）；
- [ ] 伪造事件名/字段 → 云端丢弃且有日志，不返回错误；
- [ ] 周报所需的 13 项指标都能从埋点数据算出来（对照 §5 表逐项）；
- [ ] **weekly_closed 端侧聚合**：本地闭环数与上报聚合值一致（2026-08 新增）。
