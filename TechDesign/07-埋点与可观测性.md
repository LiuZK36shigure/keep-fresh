# 07 · 埋点与可观测性

> 一人公司也要埋点（03 §4）：没有数据，下一版不知道做什么（08 范围原则 3）。
> 但同样重要：**埋点必须匿名、最小、可解释**（07 §1），且不做复杂用户画像系统。
> 本章定义：事件清单、端侧上报链路、云端接收、错误上报、指标看板。

---

## 1. 事件清单（对应 03 §4 埋点表，V1 全集）

| 事件名 | 触发 | 关键 props（白名单） | 用途 |
| ---- | ---- | ---- | ---- |
| `app_launch` | 启动 | `scene`（场景值） | 渠道/冷启动分析 |
| `record_voice_start` | 点语音按钮 | — | 语音漏斗 |
| `record_voice_success` | 识别+解析成功 | `category`（大类） | 语音漏斗、准确率 |
| `record_voice_fail` | 识别/解析失败 | `reason`（enum） | 漏斗、词典迭代 |
| `record_save` | 记录保存 | `category`、`isVoice`、`isTemplate`、`isCustom` | 北极星分子、记录结构 |
| `estimate_modified` | 修改推算日期 | `direction`（shorter/longer）、`reason` | 推算准确率（01 §3.2） |
| `remind_received` | 横幅渲染 | `type`（expiring/expired/opened/check） | 提醒有效性 |
| `remind_click` | 点击提醒卡片 | `type`、`action`（open/used/discard/gift/postpone） | 提醒有效性、处置转化 |
| `item_disposed` | 处置动作 | `type`（used/discard/gift）、`isFromRemind` | 北极星、浪费金额 |
| `subscribe_granted` / `subscribe_denied` | 订阅授权结果 | — | 提醒渠道健康度 |
| `invite_sent` / `invite_accepted`（P1） | 家庭邀请 | — | 裂变验证（01 §3.2） |
| `knowledge_update` | 知识库版本更新 | `fromVer`、`toVer` | 配置发布监控 |

> 白名单原则：props 只能取枚举/分类值，**禁止携带物品名、日期、金额等用户内容**（07 §1 最小收集）。

## 2. 端侧上报链路（本地队列 → 批量 → 云端）

```
core/analytics.track(event, props)
  → 组装 { event, ts, props, anonId }（anonId = sha256(openid+salt)[0:16]，不可逆）
  → 入本地队列（kf_events_queue，上限 500 条，超出丢最旧并计数）
  → 满足阈值（≥20 条 或 距上次上报 ≥30 秒）→ 批量调 analytics 云函数
  → 成功清队列；失败保留（下次合并上报，避免重试风暴）
```

**设计要点**：

- **本地先聚合**：同一 session 内的 `remind_received` 等高频事件先计数再上报（如 1 条带 count=5），
  节省云函数调用额度（03 §6 成本控制）；
- **离线不丢**：队列持久化，联网后自动补报（弱网场景也成立）；
- **不上报用户内容**：事件白名单 schema 在端侧与云端双重校验；
- **采样**：`record_voice_*` 与 `remind_*` 在用户量 >1 万时抽样 50%（V1 内测阶段全量）。

---

## 3. 云端接收（analytics 云函数）

```
入参校验：event ∈ 白名单 && props 键 ∈ 白名单 && 类型正确
  → 非法 → 丢弃 + 记 error_log（不返回错误给客户端，静默）
  → 合法 → 批量写 events 集合（数组式批量插入）
  → 定期清理：events 保留 90 天（脚本/定时函数），calibration 保留 180 天
```

> events 集合**不建 openid 索引、不关联 users**——物理上就不具备画像能力，这是对隐私承诺的工程保障（11 §9）。

## 4. 错误上报（极简，07 §5）

| 层级 | 上报内容 | 频率 |
| ---- | ---- | ---- |
| 小程序 | `err_page`（页面名 + 错误码 enum）+ `err_core`（模块 + 错误码） | 按错误码聚合后每天 ≤10 条/用户 |
| 云函数 | 函数名 + 错误码 + 耗时（日志，云开发自带） | 全量（云端日志免费） |

- **禁止**：不上传堆栈原文中的变量值、不上传用户输入内容（07 §5"不上传用户内容"）；
- 看板：云开发控制台日志 + 自建 `error_log` 集合（聚合统计，按错误码 Top N）。

## 5. 指标看板（周报数据源，09 §8）

| 指标 | 计算方式（埋点聚合） | 目标（01 §3.2 / 08 §2.3） |
| ---- | ---- | ---- |
| 周记录量（北极星分子） | `record_save` 按周计数 | 人均 ≥ 5 条/周 |
| 单条记录耗时 | `record_voice_start` → `record_save` 时间差（P50） | ≤ 10 秒 |
| 语音占比 | `record_save.isVoice` 比例 | ≥ 60% |
| 语音解析准确率 | `record_voice_success / (success+fail)` | ≥ 85% |
| 推算修改率 | `estimate_modified / record_save`（排除状态驱动品类） | ≤ 20% |
| 提醒点击率 | `remind_click / remind_received` | ≥ 40% |
| 48h 处置率 | 临期提醒后 48h 内 `item_disposed` / 临期提醒数 | ≥ 50% |
| 次日/30 日留存 | `app_launch` 按用户去重 | ≥ 40% / ≥ 20% |
| 提醒关闭率 | 设置页推送关闭事件 / 活跃用户 | ≤ 15% |

**实现方式（V1 极简）**：

- 方案 A（首选）：小程序后台"自定义分析"（微信公众平台，事件量小够用）+ 每周手工导出；
- 方案 B（补充）：events 集合用云函数定时聚合出日汇总表（`daily_metrics`），
  查询一张表即可出周报——**建议 V1.1 落地，避免每周手算**；
- 不做：实时大屏、复杂漏斗平台、用户分群画像（与最小收集原则冲突，03 §4 明确不做）。

## 6. 验收清单

- [ ] 断网记录 5 条 → 联网后队列自动补报，事件不丢（可对照本地计数）；
- [ ] 上报 payload 中不含任何物品名/日期/金额字段（抓包检查）；
- [ ] 伪造事件名/字段 → 云端丢弃且有日志，不返回错误；
- [ ] 周报所需的 9 项指标都能从埋点数据算出来（对照 §5 表逐项）。
