# 03 · 服务端技术栈（微信云开发 Serverless）

> 本章给出服务端（云端）的完整选型：为什么用微信云开发、云函数如何拆分、
> 定时触发器如何设计（提醒计算 ≤ 1 分钟）、数据库安全规则、成本预算与限额应对。
> PRD 依据：09 §3.4 数据与后端、07 §2 性能、07 §5 可维护性。

---

## 1. 选型：微信云开发（TCB）vs 自建后端

| 维度 | 微信云开发（Serverless） | 自建（Node + 服务器） | 结论 |
| ---- | ---- | ---- | ---- |
| 运维 | 零运维（云函数/数据库/存储全托管） | 服务器、环境、备份、扩容全自己扛 | 云开发 ✅ |
| 身份 | 免鉴权：云函数内直接拿 openid | 需自建登录/token 体系 | 云开发 ✅ |
| 定时任务 | 云函数定时触发器（cron） | 需 cron 服务 + 常驻进程 | 云开发 ✅ |
| 订阅消息 | 云开发有配套发送链路（openapi） | 需自持 access_token 管理 | 云开发 ✅ |
| 成本 | 免费额度内 ≈ 0 元（09 §5） | 最低 ~50 元/月 | 云开发 ✅ |
| 迁移风险 | 绑定微信生态 | 任意后端 | 云开发 ⚠️（备选见 10 §4） |

> **结论（T-04）**：V1~V1.2 全部使用微信云开发。同时约定：**云函数只做"薄逻辑"**
> （消息发送、数据读写、配置管理），业务算法一律在端侧 `core/`——
> 这样即使未来迁出微信生态，核心资产（逻辑层 + 知识库 JSON）不受影响（10 §4）。

## 2. 云函数清单（V1）

| 云函数 | 触发方式 | 职责 | 对应 PRD |
| ---- | ---- | ---- | ---- |
| `reminder` | 定时触发器（cron，见 §4） | 分桶扫描 remind_plans → 按配额/合并/限频生成待发消息 → 调 subscribe；批完成链式触发下一批 | 05 |
| `subscribe` | 云函数调用（reminder 内部） | 调用 `subscribeMessage.send`（模板 ID、touser、page、data）；**配额扣减；43101 拒收错误映射为取消该物品计划**（2026-08 新增） | 05 §2 |
| `analytics` | 客户端批量上报 | 校验事件结构（白名单 schema）→ 批量写 events 集合 → 定期清理；接收**端侧聚合周报数据** | 03 §4 |
| `knowledge` | 客户端查询 / 管理员更新 | 返回最新版本号与 JSON；管理员发布新版本（校验 schema） | 07 §5 |
| `user` | 客户端调用 | 读/写 users 设置（气候档案、提醒窗、开关）；删除账号（级联清理） | 07 §1.2 |
| `family`（P1） | 客户端调用 | 创建家庭空间、邀请码、加入、成员物品库读写（安全规则配合） | F-12 |
| `service_msg`（V1.2） | 定时触发器 | 服务号订阅通知发送（需企业/个体户主体，PRD 09 §5） | 05 §2 |
| `pay`（V1.2） | 客户端调用 + 支付回调 | 下单、验签、更新订阅状态、回调处理（⚠️ 个人主体不可开通微信支付，主体决策见 PRD 10 §1.1） | 10 §1.1 |

> 数据导出（P1）**改端侧本地实现**（2026-08 修订）：数据本来就在端侧，本地打包 JSON/CSV 即可，
> 不再经云端（原 `export` 云函数废弃），避免数据绕道违背本地优先（PRD 07 §1.2）。
> 每个云函数保持**单一职责 + 无状态**；公共逻辑（时间工具、消息模板配置）抽到
> `cloudfunctions/common/`（npm 本地包方式共享，或复制粘贴——V1 允许复制，控制抽象成本）。

## 3. 云数据库集合（V1 设计，schema 详见 04）

| 集合 | 读写方 | 安全规则要点 |
| ---- | ---- | ---- |
| `users` | 本人 + reminder | 仅本人可读写自己的文档；reminder 通过云函数（管理员权限）读 |
| `remind_plans` | 本人写 + reminder 读 | 仅本人可增删；云端定时任务只读 |
| `events` | analytics 云函数写 | **客户端不可直接写**（防伪造），只能经云函数 |
| `configs` | knowledge 云函数 | 客户端只读经云函数返回（版本+内容） |
| `families`/`memberships`（P1） | family 云函数 | 云函数校验成员关系后读写 |
| `orders`/`subscriptions`（V1.2） | pay 云函数 | 仅云函数读写 |
| `calibration`（P1） | analytics 云函数 | 匿名校准样本（不含物品名） |

> **安全规则原则**：客户端直读云数据库一律关闭（除用户自己的 users 文档）；
> 所有写操作经云函数校验（openid 白名单校验 + 字段白名单），从根上防注入/越权。
> 云函数内使用 `cloud.getWXContext().OPENID` 获取身份，**禁止信任客户端传入的 openid**。

## 4. 定时触发器：提醒计算的性能设计（07 §2：每批 ≤ 1 分钟，2026-08 修订）

> **为什么改**：云函数单次执行超时上限 60 秒，而"扫描 + 组装 + 逐用户发送"（网络 IO）在
> 1000+ 用户时必然超时。"全部用户 ≤ 1 分钟"的旧指标在架构上不成立，改为**分桶 + 链式分批**：

```
触发：每日 08:00（早餐档）+ 18:30（晚间档）——两档覆盖 05 §3 推荐时刻
     另：每小时轻量扫描（补发"开封计时 50% 时点"等短窗口提醒，可选）

reminder 云函数执行流程（每批一个实例）：
  0. 入参 batchNo → 按 openid 哈希分桶（如 16 桶，桶号 = hash(openid) % 16）
  1. 查询本桶 remind_plans 中「今天处于提醒窗口」的计划
     （索引：remindAt + status=active，按到期日范围扫描）
  2. 按用户分组 → 应用防轰炸合并（同用户 ≥3 条 → 1 条汇总，05 §1.3）
  3. **配额分配**（2026-08 新增）：按用户剩余订阅配额（remind_plans.quota - 已消耗）排序，
     配额不足时优先保"临期/过期"类型，检查提醒本就走横幅不占配额
  4. 应用限频（每用户每日 ≤3 单发 + 1 汇总，05 §3）→ 过滤已发记录（去重表）
  5. 组装模板数据（品类名/天数/文案键，订阅消息模板字段受限见 04 §4）→ 批内并发调用 subscribe
  6. 发送结果写回 plan 状态（sent/next_node）；43101 拒收 → 标记该计划 canceled（不再重试）
  7. 本批完成 → 链式触发下一批（batchNo+1）；全部完成 → 写 batch 完成标记（幂等）
```

**性能与可靠性要点**：

- **分桶链式**：单批容量 ≈ 200 用户（每用户 ≤ 4 条计划），批内并发发送；性能目标 = **每批 ≤ 1 分钟**，
  总时长 = 批数 × 1 分钟，可扩展到万级用户（V1 内测 1 批即可跑完）；
- **索引优先**：`remind_plans` 建 `{remindAt: 1, status: 1}` 复合索引，避免全表扫描；
- **幂等设计**：每条计划带 `sentDates[]`（日期+类型），重复触发不重复发送；批次标记防重复消费；
- **短窗口提醒**（开封计时 50% 时点、6 小时前）由"小时级扫描"兜底，允许 ±1 小时误差；
- **配额账本**（2026-08 新增）：一次性订阅 = 授权一次得 1 条配额——授权回调（subscribe_granted）
  时端侧上报配额数，云端在 remind_plans 记 `quota/quotaUsed`；发送消耗 1；配额不足的条目不发送、
  顺延或并入次日汇总，**绝不超发**（超发 = 43101 报错 + 用户信任损失）；
- **降级**：云函数超时/失败 → 端侧横幅兜底（用户打开必见），不丢用户体验；
- **夏令时/时区**：V1 全部按北京时间（国内用户），不引入时区复杂度（i18n 远期，07 §8）。

| 路径 | 内容 | 访问 |
| ---- | ---- | ---- |
| `configs/shelf_rules.json` | 品类基线知识库（04 schema） | 客户端经 knowledge 云函数读取 |

## 6. 成本预算与限额应对（09 §5 联动）

| 资源 | 免费额度（参考） | V1 用量预估 | 超限对策 |
| ---- | ---- | ---- | ---- |
| 云函数调用 | 50 万次/月 | 埋点上报为主，预估 5~15 万次 | 埋点本地聚合降频（07） |
| 云数据库 | 读 5 万/天、写 3 万/天 | 足够（明细不上云） | remind_plans 及时清理（处置后删除） |
| 云存储 | 5GB | < 100MB | 导出文件 7 天自动清理 |
| 定时触发器 | 免费 | 3 次/天 | — |
| 订阅消息 | 按模板计费（个人主体有免费额度） | 与提醒量挂钩 | 合并策略天然降量（05 §1.3） |
| WechatSI 语音 | 免费额度 | 语音使用量 | 降级手动（已设计） |

> 月度复盘时把"云资源用量"列入周报（09 §8 模板可加一行），提前 2 个月预警超限。

## 7. 数据查看与运维（一个人怎么看数据）

> 回答"服务器是什么、用户信息存哪、我以什么方式查看"。**再次强调**：物品明细默认不上云
> （07 §1），云端只是"配置 + 消息 + 匿名统计 + 最小影子数据"——所以"看用户数据"看到的是
> **设置与订阅关系**，看不到物品明细，这是隐私设计使然，不是功能缺失。

| 方式 | 入口 | 能看什么 | 适合场景 |
| ---- | ---- | ---- | ---- |
| 云开发控制台（工具内） | 微信开发者工具 → 云开发 → 数据库/云函数/存储 | 集合数据浏览与编辑、云函数日志/调用量/耗时、云存储文件、定时触发器执行记录 | 日常开发与排查（推荐） |
| 腾讯云 CloudBase 控制台（网页） | cloud.tencent.com → 云开发 CloudBase | 同上 + 用量统计、费用账单、告警配置 | 用量监控与预算管理 |
| CLI / SDK 脚本 | `@cloudbase/cli`、`@cloudbase/node-sdk`（本机 Node） | 批量导出集合（JSON/CSV）、定时巡检脚本（如"抽查云端无未授权物品明细"） | 审计与数据备份 |
| 控制台"导出" | 云开发控制台 → 数据库 → 导出 | 全量集合导出文件 | 备份/迁移 |

**用户信息长什么样（users 集合示例）**：

```jsonc
{
  "_id": "xxxx",
  "_openid": "oXXXX...",        // 微信身份，云开发自动注入，不可伪造
  "settings": { "climate": {...}, "remind": {...}, "privacy": {...} },
  "subStatus": { "subscribeMsg": true, "pay": "none" },
  "createdAt": "2025-07-01T00:00:00+08:00",
  "lastActiveAt": "..."
}
```

**查看时的注意事项**：

- `_openid` 即用户唯一标识；V1 无密码体系（07 §6），用户身份完全依赖微信；
- 埋点 events 集合**匿名**（无 openid 关联，07 §3），控制台里看不到"哪个用户干了什么"——这是刻意的；
- 删除账号（09 §4）会清空该 openid 的 users/remind_plans/云存储文件，控制台可核验。

## 8. 服务端验收清单

- [ ] 断网/弱网时客户端功能不依赖任何云函数（架构层验证）；
- [ ] 定时触发器在指定时间执行，**每批 ≤ 1 分钟**（07 §2 指标，可观察日志耗时）；批次链式触发完整跑完；
- [ ] 同一物品的提醒不会重复发送（幂等验证：手动触发两次同一天任务）；
- [ ] **配额不超发**：构造"授权 1 条但有 3 条待发"场景 → 仅发 1 条且优先临期/过期（2026-08 新增）；
- [ ] 任意云函数不可读取他人数据（越权测试用例：伪造 openid 参数被拒）；
- [ ] 埋点事件仅接受白名单 schema（非法字段直接丢弃并记错误日志）。
