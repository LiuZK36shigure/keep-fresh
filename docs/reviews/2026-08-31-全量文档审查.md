## 一、总体结论

**产品判断是扎实的，工程落地是松散且矛盾的。**

三句话概括：

1. **产品层（PRD 01–05）经得起推敲**：双模型推算、保守原则、可解释性、"提醒而不指责"的基调、北极星指标的选择，
   都是有质量的决策，且迁移后仍有 80% 以上有效。这部分不要动。
2. **迁移只做了"打补丁"，没做"换骨架"**：新增的 [TechDesign 12](../TechDesign/12-Web优先方案（平台迁移决策）.md)
   是合格的新权威文档，但它与 12 份旧文档**并列存在**。旧文档里加了 ⚠️ 作废声明，声明之下的正文却仍是"活"的小程序内容。
   结果是：**读者（包括三个月后的你自己）无法判断哪一份是有效的**。
3. **三个"地基级"缺口会让 V1 无法开工**：Web 端的**账号与身份体系**没有设计、面向中国大陆公网发布的**合规路径**没有设计、
   **V0 的工期与范围严重不匹配**。这三项都不在"改几个字"的范畴，需要补写。

严重度分布：**P0 = 3 项**（阻塞开工/触发返工）、**P1 = 16 项**（一致性硬伤，会导致两人做出两种实现）、**P2 = 53 项**（残留与笔误）。

> **P1-14（ASR 音频格式）、P1-15（Cloudflare 免费版硬墙）、P1-16（iOS 推送订阅静默失效）**
> 是本次审查通过外部核实**新发现**的三项，原文档完全没有涉及。
> 其中 P1-14 与 P1-15 **不是"待优化"，而是"按现方案实现会 100% 失败"**——建议优先处理。

### P0-3 面向中国大陆公网发布的合规路径缺失（影响 V1 托管选型）

**位置**：`PRD/09-一人公司工作流.md` §5（成本）；`TechDesign/12` §5.1（托管三选一）、§9；`PRD/11` 全章

文档的 V1 是：**公网 HTTPS 网站 + 小红书/豆瓣内容引流 + 面向中国大陆个人用户**。
同时托管选型推荐 **Cloudflare Pages + Workers 免费额度**（`*.pages.dev` / `*.workers.dev`）。

但是**全部 27 份文档中，"备案"两个字一次都没有出现**。这是缺失，不是遗漏细节：

- 面向中国大陆用户的公网站点，实践中通常需要 **ICP 备案**（以及后续的公安联网备案）；
  备案要求**境内主体 + 境内接入服务商**，Cloudflare 不提供备案通道。
- 这直接决定 §5.1 的三选一哪个能用来**发布**：如果 V1 需要备案，
  "Cloudflare 免费额度（0 元）"就只能是 V0 自用阶段的答案，V1 必须落到"轻量云服务器 + 域名"这条线上。
  文档目前把这两条并列成"看心情选"，会让 V1 临时换托管重做部署（CI、证书、Cron、静态分发全要动）。
- 与之相关、同样未提的还有：**国内用户访问 Cloudflare 免费版 IP 的稳定性**（这关系到"提醒服务端必须常开"这条生命线）、
  **个性化推荐/算法备案**（本案不涉及，但要在风险章里明确排除）、**收款合规**（PRD 10 §1.1 已诚实标注为"V1 重估项"，✓ 做得好）。

**⚠️ 技术核实后的补充（这让问题从"未决策"升级为"技术路线直接冲突"）**：

外部核实确认了 Cloudflare 的两条硬性事实，它们与备案**正面冲突**：

1. **Cloudflare 的 Custom Domain 要求域名处于你自己的 Cloudflare zone**，即**必须把 NS 迁到 Cloudflare**
   （免费/Pro 计划只支持 Full setup，Full setup 的定义就是"改 nameserver"）。
2. 官方的 `*.workers.dev` **自带有效 HTTPS 证书、无需任何自定义域名**——但官方明确**不推荐用于生产**：
   workers.dev 子域被视为 "Free website"，定位是 "personal or hobby projects that aren't business-critical"。

于是形成一个两难：
**用 `*.workers.dev` → 官方不建议生产、且该域名在国内常被污染/不可直连；
用自定义域名 → 必须迁 NS 到 Cloudflare → 丢掉境内 CDN 与备案接入资格。**

而 PWA 的三件事（安装到主屏、Service Worker、Web Push）**全都必须走 HTTPS 且域名可达**——
**这正好打在产品生命线（提醒通道）上**。**这已经不是"细节风险"，而是 V1 架构路线的前置约束。**

**建议**：不要求你现在就下结论，要求的是**把它变成一个显式决策点，并前置到 V0 阶段**：

1. 在 PRD 11 新增一条风险（如 R13「公网发布合规、备案与域名可达性」），写明"V1 发布前必须完成备案路径确认"；
2. 在 PRD 09 §5 成本表加两行：`域名（含备案，约 60 元/年）`、`境内轻量服务器（备案必需，约 24~60 元/月）`；
3. 在 TechDesign 12 §5.1 明确标注：**Cloudflare（含 workers.dev）= V0/V0.5 开发自用；
   V1 公网发布另行决策**，并写明上面那个 NS 两难；
4. **决策建议（供参考，不代替你的判断）**：V0/V0.5 用 Cloudflare 跑通链路（此时不需要域名、不需要备案），
   V1 发布前再决定——若走境内备案，则前端与服务端一起迁到境内（架构上 **`core/` 纯 TS + 静态 JSON 配置
   这条解耦做得对，迁移成本可控** ✓）；若确定以境外访问为主，则留在 Cloudflare 并接受可达性风险。

## 三、P1 级问题（口径冲突，会导致实现分歧）

### P1-1 V0 的工期与范围严重不匹配（最现实的风险）

**位置**：`PRD/08` §1/§2/§3；`PRD/09` §6；`TechDesign/12` §9 与附录

先看约束：PRD 09 §6 明确"固定'**晚上 2 小时 + 周末半天**'开发窗口" ≈ **14 小时/周**。

再看要交付的东西（PRD 08 §3 + TechDesign 12 §9 + 附录 第一周/第二周目标）：

> Web 前端（PWA）、远程服务端（定时任务 + ASR 代理 + 配置分发 + 埋点接收）、推送通道打通、
> 语音记录闭环（MediaRecorder + 云 ASR 对接 + 规则解析器）、三层推算引擎（双模型）、
> 四类提醒（临期/过期/开封计时/检查）+ 合并 + 限频 + 沉默策略、
> 处置闭环 + 5 秒撤销、极简物品列表页、设置页（气候/提醒窗/推送/隐私）、
> 埋点体系 + 端侧聚合上报、**50+ 类基线知识库**、"改规则不发版"的远程配置链路

口径还有歧义：PRD 08 §3 写 V0 = "（本人 dogfooding，**2~4 周**）"，退出标准是"**自己连续使用 ≥ 2 周**"。
按字面读，**2~4 周里包含 2 周 dogfooding，留给开发的是 0~2 周 = 0~28 小时**。
按宽松读（dogfooding 额外算），也只有 4 周 ≈ 56 小时。

**结论：以 14 h/周 的投入，上面这张清单在 2~4 周内不可能完成。**
这不是"有点紧"，是差 3~5 倍。而 PRD 08 §2.3 又把"未达标先回炉"设为硬门禁——
真实结果大概率是**第一次就撞门禁，然后产生挫败感**（正好命中风险 R7「倦怠」）。

**建议**（三选一，都要写进文档）：

- **A（推荐）**：把 V0 拆成 V0a（第一周：手动表单闭环 + 服务端 + 一条 Bark 推送，**不做语音**）
  与 V0b（第二~三周：语音 + 50 类知识库 + 四类提醒），把"50 类知识库"后移到 V0b 末甚至 V1 前；
  PRD 08 §3 的 V0 工期改为"**3~6 周**"并显式写出"⚠️ 以每周 14 小时计"。
- **B**：知识库先做 **15~20 类高频品**（覆盖 80% 场景），把"50 类"降级为 V1 的交付项。
  这与 PRD 12 §5 阶段三"先整理 **30 类**"也更一致（目前 12 章写 30、04 §2 与 08 写 50+，本身就是不一致）。
- **C**：明确 V0 **允许范围缩水**：V0 的唯一目的是验证"推算准不准 + 提醒有没有用"，
  因此知识库和提醒类型都可以砍到最小。

### P1-3 气候系数的算术链自相矛盾（同一个例子，三份文档算出三个结果）

以"鲜牛奶 7 天 + 夏季高温潮湿"为例：

| 出处 | 说法 | 算术 |
| ---- | ---- | ---- |
| `PRD/06` §4.3 线框 | 购买日 7/12 → **预计到期 7/19**；依据 "未开封冷藏 7 天 × **高温潮湿季 0.8 ≈ 6 天**" | 7×0.8=5.6，**6 天应为 7/18，与"7/19"自相矛盾** |
| `PRD/03` GWT-11 | "到期日 = 今天 + 7（夏季为 **+6 或 +5**）" | 假设四舍五入（5.6→6、4.9→5） |
| `TechDesign/05` §2.1 | reasonText 例："未开封冷藏 7 天 × 夏季高温潮湿 **0.64 ≈ 4 天**"，且明确 `T = roundDown(...)` | 0.64 来自 `PRD/04` §4.1（高温 0.8 × 潮湿 0.8），roundDown(4.48)=4 |

**根因有三层**：

1. **"高温潮湿 = 0.8" 是错的**。`PRD/04` §4.1 明确规定组合方式为 `k = 温度系数 × 湿度系数 × 特殊季系数`，
   高温 0.8 × 潮湿 0.8 = **0.64**。0.8 只是"温度"单项。PRD 03 与 PRD 06 把单项当成了组合值。
2. **品类级 summerFactor 与气候级 temp_hot 重复计**。`PRD/04` §2 表给鲜牛奶备注"夏季系数 0.7"，
   `TechDesign/04` §3 把它落成 `specialRules.summerFactor: 0.7`；而气候表里已有高温 0.8。
   两者**相乘**就是 0.56，再乘潮湿 0.8 = 0.448，一路撞到保底 0.5 → 7 天变 3 天。
   **这是设计缺陷：同一个"夏天"被罚了两次。** 要么删掉品类级 summerFactor，要么明确它是"替代"而非"叠加"。
3. **取整规则未统一**：GWT-11 暗示四舍五入，TechDesign 05 写死 roundDown。而 roundDown 是"保守原则"的应有之义，
   GWT 的 "+6/+5" 反而更宽松——**验收标准比安全原则更激进**，方向反了。

**建议**：把 04 章定为唯一算术权威，其余章节的例子改成引用；删除或改义 `summerFactor`；
在 04 §4.1 加一句"任何展示示例必须与本节公式逐位对齐，CI 校验 reasonText 与 expireAt 的一致性"。

### P1-4 合并策略与限频规则互斥（PRD 05 与 TechDesign 05 的验收标准打架）

- `PRD/05` §1.3：**同一天 ≥3 条提醒时，合并为一条"今日临期汇总"**
- `PRD/05` §3：每用户每天最多 **3 条单发 + 1 条汇总**
- `TechDesign/05` §5 验收清单：「构造"**一天 5 条临期**"场景 → 输出 **3 单发 + 1 汇总**（GWT-17）」

**如果 5 ≥ 3 就触发合并，那结果应该是 0 单发 + 1 汇总**，不可能出现 "3 单发 + 1 汇总"。
两条规则在同一份文档集里给出了互斥的期望输出，测试写完必然红。

**建议**：明确合并是"**对超过 3 条的部分合并**"还是"**全部合并**"。
推荐表述：`≤3 条各自单发；>3 条时，保留最近到期的 3 条单发，其余合并为 1 条汇总`——
这样 "5 条 → 3 单发 + 1 汇总" 才成立，且与 §3 的频率上限自洽。

### P1-5 推送通知"内联处置按钮"在 V0 通道上不成立（已独立核实）

- `PRD/03` F-08：「提醒卡片/通知提供动作按钮：【已用完】【已丢弃】【转赠】【延后 3 天】，
  **点击后无需进入 App 即可完成处置**」；GWT-20 据此编写验收标准。
- `TechDesign/12` §3 与附录：V0 通道选用 **Bark**（"手机装 Bark → 复制 key → 一条 HTTP 请求推到通知栏"）。

**核实结论：Bark 不支持自定义交互按钮。** 它只提供"点击打开 URL"与"自动复制"类行为。
且这**不只是 Bark 的实现问题，而是 iOS 平台层的硬约束**——iOS 通知上的按钮来自 App 预先注册的
`UNNotificationCategory`，**推送载荷无法在运行时定义新按钮**。也就是说：第三方（我们）**没有办法**
通过推送内容让 Bark 渲染出【已用完】【已丢弃】，只能等 Bark 自己实现对应 category。
飞书机器人发的是聊天消息卡片，同样不满足"无需进入 App"。
三者中只有 **ntfy** 的 `http` action 能真正做到"不打开 App 即回传动作"，
但**在 iOS 上它不是通知上可见的按钮，而是长按通知后的上下文菜单**（ntfy 官方维护了 iOS 功能差异表
`FEATURE_PARITY.md`，实施前需逐项核对）。

**后果**：F-08 是 P0 功能，GWT-20 是 P0 验收标准，而它在 V0 的选定通道上无法通过。

**建议**：二选一——
（a）V0 把 F-08 降级为"点击通知 → 打开网页 → 落地页预置该物品的处置卡片（一次点击完成）"，
并据此改写 GWT-20（诚实描述 V0 能力）；
（b）V0 通道改用 ntfy 并把 `http` action 写进技术方案（接受"长按"的交互损耗）。
无论选哪个，`PRD/05` §5 的示意图（`[提醒卡片] 牛奶还有 2 天到期 [已用完][已丢弃]...`）都要加上"V1 起可用"的标注。

> 附带发现（信任假设）：**Bark 公共服务器 `api.day.app` 会看到你的通知内容**。
> 对一个以"你的冰箱只有你知道"为卖点的产品，这是一条必须写进文档的信任假设。
> Bark 可自建（`Finb/bark-server`），若 V0 使用公共服务器，应在 TechDesign 12 §3 显式记录这个取舍。

### P1-9 "3 秒出确认页"的验收标准按字面不可达

`PRD/03` F-01 性能项：「从**按下按钮**到确认页出现 ≤ 3 秒（**含识别**）」。
GWT-01 同样是「When 说出"牛奶，今天买的"且网络正常，Then **3 秒内**展示确认页」。

**按下按钮之后用户还要说话。** 说一句"牛奶今天买的"通常 2~4 秒，
再加上 MediaRecorder 停止、音频上传、云端 ASR 往返、解析、渲染——**3 秒在物理上做不到**。

**建议**：改为分段的、可测量的口径：
`① 松手（录音结束）→ 识别文本返回 ≤ 2 秒（P50，4G）；② 识别文本 → 确认页渲染 ≤ 0.5 秒；
③ 端到端（含说话）中位数 ≤ 10 秒`（后者与 01 §3.2、08 §2.3 的"单条记录 ≤ 10 秒"一致）。

### P1-10 气候"不确定"档没有定义系数，且方向与保守原则相反

- `PRD/04` §4.2：气候档案"**可跳过，默认'不确定'档**"；`PRD/06` §3.4 同。
- `PRD/04` §5.2 保守原则："规则存在不确定性时**一律取更短期限**"。
- `PRD/04` §4.1 系数表只有：常温 1.0 / 高温 0.8 / 酷热 0.7；干燥 1.0 / 潮湿 0.8。**没有"不确定"档。**

于是默认行为只有两种可能，**两种都错**：

- 若"不确定" = 1.0（常温干燥）→ **信息最少的用户反而拿到最长期限**，与保守原则直接冲突；
- 若"不确定" = 某个 <1 的猜想值 → 文档没写，实现者自己拍。

同时注意：`PRD/04` §5.1 置信度打分里，一个"品类命中 40 + 开封明确 20 + 存储明确 15 + 日期明确 15"的默认记录
= **90 分 → 高置信 → 展示单一日期**，恰恰是最不该给单一日期的那种记录。

**建议**：定义 `climate_unknown` 系数（建议 0.9，并在推算详情页写明"气候档未设置，已按保守值估算"），
并把"气候档位明确 +10"是否命中，真实反映到置信度里。

### P1-11 端侧离线处置与服务端提醒计划的一致性策略缺失

新架构下服务端持有 `remind_plans` 才能推送（`TechDesign/12` §7）。但：

- 用户在**地库/超市离线**时标记"已用完" → 端侧状态变了，**服务端不知道** → 到点照推。
  用户收到"牛奶还有 2 天到期"而牛奶昨天就喝完了——**这是最伤信任的一类 bug**。
- 文档只有"失败静默重试（≤3 次）"（`TechDesign/05` §3.2）与"**下次用户授权订阅时重新上报**"
  （`TechDesign/04` §7 第 2 条）。前者没有时限（离线 2 天怎么办？后者在 Web Push 下"授权"是 origin 级一次性的，
  不会反复发生）。
- 也没有定义客户端"心跳/定期全量对账"的机制与频率。

**建议**：在 TechDesign 12 新增一节"提醒计划的端云一致性"，明确：
① 端侧每次启动/回前台做一次**全量对账**（本地未处置集合 → 覆盖云端）；
② 离线队列 + 网络恢复后立即重放；
③ 服务端推送前**二次校验**（若超过 N 小时未收到端侧心跳，降级为"通用提醒"，不点名具体物品）；
④ 反例测试用例写进验收清单（离线处置 → 恢复网络 → 云端不再推送）。

### P1-14 语音音频格式未考虑 —— **已核实为架构级阻塞项**（不是"缺口"，是"会 100% 失败"）

`TechDesign/12` §6 只写了「采集：浏览器 `MediaRecorder` 录音（iOS Safari / Chrome 均支持）」→
「识别：服务端代理调用云 ASR（腾讯云一句话识别 / 讯飞）」。**中间少了一个决定成败的环节。**

**事实（已逐条核对两家官方文档）**：

| 浏览器产物 | 讯飞语音听写（仅支持 `pcm` / `wav` / `speex-wb`，16k/8k、16bit、单声道） | 腾讯云一句话识别（支持 `wav`/`pcm`/`ogg-opus`/`speex`/`silk`/`mp3`/`m4a`/`aac`/`amr`） |
| ---- | ---- | ---- |
| Chrome / Edge / Firefox：`audio/webm;codecs=opus`（48 kHz） | ❌ **完全不支持**（opus 不在列） | ❌ **不支持 WebM 容器**——列表里的 `ogg-opus` 指 **Ogg 封装**的 Opus，**"webm" 在该文档中零命中** |
| Safari（iOS/macOS）：`audio/mp4`（AAC） | ❌ 不支持 | ⚠️ 列表含 `m4a`/`aac`，**可试但文档未保证** `audio/mp4` 这个 MIME 被接受 |

**结论：你在 Windows Chrome 上录的音，两家主流国内 ASR 都吃不下。**
这已有同类故障记录（例如 `desktop webm (Opus 48k) fails Tencent 16k_zh`）。

**而且"在服务端转码"这条路在 Workers 上是堵死的**（文档没有考虑过这点）：

- Workers 是 **V8 isolate，不是容器**——**没有子进程、没有文件系统、没有 shell**，
  `child_process` / `ffmpeg` 连解析都过不去；
- **`ffmpeg.wasm` 也不行**：Workers 的 WebAssembly 运行时**只支持预编译模块**，
  **禁止运行时动态编译**，无法从 R2 拉 wasm 再编译；即便塞进 bundle，
  ffmpeg.wasm core 未压缩约 25 MB，叠加 **10 ms CPU** 与 128 MB 内存，音频重采样必然超限。

**建议（按优先级）**：

1. **✅ 把转码挪到前端，让云端零转码**（唯一可行且成本最低的解）：
   浏览器里 `decodeAudioData()` 解码 MediaRecorder 的 Blob → 重采样到 **16 kHz 单声道** →
   自己打 **44 字节 WAV 头** → 上传 WAV。Worker 只做纯透传（只保管 API key，不做任何编解码）。
   15 秒 @16k/16bit/mono ≈ **480 KB**，远低于腾讯云 **3 MB / 60 秒**上限。
   （备选：用 `AudioWorklet` 直接采 16 kHz PCM 跳过解码，但 iOS Safari 支持度需自测。）

### P1-15 Cloudflare 免费版有"双重硬墙"，现方案跑不通（已核实，取代原"待实测"）

原报告把这一项标为"待实测"。核实结果是：**不是"性能可能不够"，而是"设计必然失败"。**

**免费版的两道墙（官方限额，非推测）**：

| 项 | Workers Free | Workers Paid |
| ---- | ---- | ---- |
| CPU 时间（**含 Cron Trigger**） | **10 ms** | 30 s（间隔 <1h）/ **15 min**（间隔 ≥1h） |
| **子请求 / 次调用** | **50** | 10,000 |
| 请求数 | 100,000/日 | 无限制 |
| Cron Trigger 数量 | **5 个/账户** | 250 |

**算术很残酷**：

- CPU：50 条推送 × (VAPID ES256 JWT 签名 + AES-GCM 载荷加密 + HKDF 派生)，
  预算 = `10 ms ÷ 50 = 每条 0.2 ms`——**连一次 ECDSA P-256 签名都不够**。
  而且这些是**纯 CPU**，无法用并发 IO 掩盖（CPU 时间不含网络等待，这点对我们有利，但救不了加密）。
- **子请求：50 条 `fetch()` 就把配额用尽**，此后连"写回发送结果""读 D1 游标""重试失败推送"都做不了。
  **即使 CPU 达标，设计也必然失败。**
- 超限后果：返回 **Error 1102 `Worker exceeded resource limits`**，日志标记 `exceededCpu`，
  **调用被硬杀、无重试、已发/未发状态丢失**——必须按这个前提设计（幂等 + 可续跑）。

**还有一处选型错误**：`TechDesign/12` §5 写的是"Cloudflare Workers + **D1/KV**"（二选一），
但 **KV 免费写额度只有 1,000/日，且同一 key 每秒只能写 1 次**。
50~200 用户 × 每人每天新增/编辑/删除若干提醒计划 + 订阅续期 + 已发送标记，
很容易到每天数千次写；更糟的是**用户在前端连点保存就会撞 429**。**KV 不适用于提醒计划。**

**建议**：

1. **必须把"一轮发 N 条推送"改成分片 cron**：用 `*/1 * * * *` 每分钟跑、每次只处理一小批
   （建议 **≤10 条推送**，为写回结果留足子请求余量），游标存 D1，幂等键保证可续跑。
   免费版只有 5 个 Cron Trigger，够用但要规划好。
2. **提醒计划、推送订阅、发送日志全部放 D1**，KV 只放"几乎不改"的东西
   （JSON 配置、feature flag、ASR 每日配额计数）。**D1 免费额度是 KV 写的 100 倍，且强一致**——
   "用户刚存完计划立刻能读到"这点对体验很关键。
3. **D1 自身的三个坑要写进文档**：① 按**扫描行数**计费（不是返回行数），过滤列必须建索引；
   ② 索引会让**写翻倍**（命中索引列算 2 行写），测算额度按 2 倍估；
   ③ **单库单线程**，并发过高先排队、队列满返回 `overloaded`，不是高并发存储。
4. **性价比结论要反过来写**：文档在"0 元 Cloudflare vs 60 元 VPS"之间二选一，
   但 **Workers Paid $5/月（≈36 元）** 就把子请求提到 10,000、cron CPU 提到 30 s~15 min，
   且免运维、免 TLS 续期、免 Push 库维护。**"60 元 VPS" 的性价比论证是错的**——
   如果不想受免费版限制，最便宜的正解是 $5 Workers Paid，而不是 VPS。
5. **补一个备选**：**Deno Deploy Free**（1M 请求/月、10 小时活跃 CPU、`Deno.cron` 抖动 up to 1 分钟）
   没有 10 ms CPU 墙，比 Workers Free 更适合本项目。注意其请求额度是**月**级。

**另外，`TechDesign/12` §5 把 GitHub Actions schedule 列为定时任务选项，这是不可靠的**：
官方承认高负载时**延迟**（"每小时整点"最严重）、**负载过高时排队任务会被直接丢弃（dropped）**、
**公开仓库 60 天无活动自动禁用**。**它不能作为提醒投递通道**，只能用于博客/构建类任务。
（顺带确认：Vercel Cron Hobby **每天 1 次且精度 ±59 分钟**、Render Free **15 分钟无流量即休眠**、
Fly.io **已无 free allowance**——这三个都不适用于"必须常开"的提醒服务端。）

### P1-16 iOS Web Push 订阅"静默失效"缺应对（已独立核实的高频真实问题）

这是本次外部核实中**最重要的一个新发现**，文档里完全空白。

在 iOS 上，Web Push 的 subscription 会**静默失效**——用户没有做任何操作，推送就是不再到达。已知成因包括：
系统更新、PWA 长期未打开、Safari 存储被回收、用户清理网站数据、设备迁移。
WebKit 上有多条长期未收敛的相关 issue（273063 / 284111），Firebase 等平台也有对应的公开报告。

**对本案的影响**：`TechDesign/12` 的整个提醒链路建立在"服务端持有 `pushTarget` → 到点发送"之上，
而"用户是否还能收到"被默认成恒真的。实际上：

- 订阅失效时，推送服务通常返回 **404 / 410 Gone**——**服务端必须据此清理死订阅**，否则会永久重试一个死地址；
- 但更麻烦的是**不一定返回错误**：有些失效表现为静默丢弃，服务端会以为"发送成功"，
  于是在 PRD 08 §2.3 的"**推送到达率 ≥ 95%**"这个指标上看到的是一个**虚假的好数字**——
  而这恰恰是 08 章用来替代"订阅授权率"的生死指标；
- **`pushsubscriptionchange` 事件在 iOS/Safari 上不可靠**，也就是说：**你不能依赖浏览器主动通知你"订阅变了"**，
  只能自己兜底。（这一条决定了下面的对策 1 不是"优化"，而是**唯一手段**。）
- 需要如实写进文档的表述是：「**无官方 TTL 承诺，实测存在静默失效**」——
  Apple 从未公布 Web Push 订阅的过期策略，所有公开信息都是开发者实测与 bug 报告。

**建议**：在 TechDesign 12 的提醒调度一节（见 P1-12）中明确写进四条：

1. **每次打开/回前台重新 `pushManager.subscribe()` 并 upsert 服务端订阅**（不是只在首次授权时写一次）——
   这是唯一可靠的兜底，因为 `pushsubscriptionchange` 不可信；
2. 服务端对 **404 / 410 立即删除**该订阅（Push 协议标准语义），并在同一用户的其他订阅上重试，**不要无限重试**；
3. 存 `subscription + last_seen_at`，把"连续 N 次发送失败"作为订阅失效的**代理信号**；
4. 增加一个**真实性校验指标**：不能只看"服务端发送成功"，要看"**用户随后打开了网页**"
   （即 `remind_received` 横幅渲染事件）——把它作为推送健康度的兜底观测。

> 这一条与 P1-11（端云一致性）是同一条链路上的两个断点，建议合并成一节一起写。
>
> **产品层面的推论（重要）**：以上全部成立意味着——**"推送是网页端提醒的生命线"这个前提是脆弱的**。
> 建议把产品定位从"一定准时响"下调为"**打开时一定会看到**"（这正是 GWT-19 页内横幅的价值所在），
> 并在 PRD 05 §2 显式承认"提醒可能漏发"。**这不是妥协，而是把 GWT-19 从"兜底"提升为"主承诺"。**

### 5.2 技术可行性 —— 逐项评估

| 方案 | 评估 | 说明 |
| ---- | ---- | ---- |
| Vite + React + TS + Dexie | ✅ 可行 | 成熟组合，AI 辅助友好 |
| IndexedDB 存 500 条物品 | ✅ 可行 | 数据量无压力 |
| **第三方推送通道（Bark）** | ✅ 可行，⚠️ 三点未写 | ① 通知内容经过 `api.day.app` **第三方服务器**（可自建 `Finb/bark-server`），与"隐私优先"定位有张力；② **不支持内联动作按钮**（P1-5，且是 iOS 平台限制而非 Bark 的锅）；③ 见下条 |
| **Web Push on iOS** | ⚠️ 可行但前置条件苛刻 | 四前提已核实，但**"添加到主屏幕"严格说是"接收"推送的前提，"订阅"在 Safari 标签页内也可能完成**——文档措辞应精确化（否则引导文案会写错）。**实操建议**：把"添加主屏幕"与"请求通知权限"放在**同一个用户手势链**里一次完成（添加主屏幕本身就是手势）。另：**权限一旦拒绝无法程序化重新请求**（WebKit Bug 248463），只能用户手动清站点数据；macOS Safari 另需"添加到程序坞"（本案用 Windows + Chrome/Edge，**免安装即可用，且浏览器关闭后仍能送达**——这是桌面端与 iOS 端最大的体验差异） |
| **iOS 推送订阅的长期可靠性** | ⚠️ **真实且高频的风险** | 订阅会静默失效（系统更新 / 长期未开 PWA / 存储回收 / 清理网站数据），且 `pushsubscriptionchange` 在 iOS 上不可靠。服务端必须处理 404/410 并每次打开重新 upsert（详见 P1-16）。**这条直接威胁"推送是网页端提醒的生命线"这个核心假设** |
| **Cloudflare Workers 免费额度** | ❌ **现方案跑不通** | 已核实：免费版 **CPU 10 ms（含 Cron）+ 子请求 50/次调用**。50 条推送的加密预算只有每条 0.2 ms，且 50 个 `fetch()` 就把子请求用尽。**必须改成分片 cron（≤10 条/批）+ D1 存游标**（详见 P1-15）。另：`web-push` 是 Node 库不能直接用，但"**必须自研**"是错的——Cloudflare Agents 官方有 push 通道，也有 Workers 兼容的 Web Crypto 系库（见 §4.2 #45） |
| **Cloudflare 承载 V1 公网** | ❌ **与备案技术路线正面冲突** | 自定义域名**要求把 NS 迁到 Cloudflare**（免费/Pro 仅支持 Full setup），这会丢掉境内 CDN 与备案接入资格；`*.workers.dev` 虽自带 HTTPS，但**官方明确不推荐用于生产**，且该域名在国内常不可直连。详见 P0-3 |
| **云 ASR 代理（腾讯云/讯飞）** | ❌ **前端不改就 100% 失败** | 已核实：Chrome 产出 `audio/webm;codecs=opus`，**讯飞只收 pcm/wav/speex（全不收）**，腾讯云**不收 WebM 容器**（文档里的 `ogg-opus` 是 Ogg 封装，不是 WebM）。**必须在浏览器端归一化为 16k 单声道 WAV**；且 Workers 上 ffmpeg 与 ffmpeg.wasm **都不可行**（V8 isolate 无子进程；WASM 只支持预编译模块）。详见 P1-14 |
| **和风天气免费版** | ⚠️ 待验证 | 个人开发者免费额度与实名要求需在 V1.2 前确认；文档已设计"失败回退手动档"的降级 ✓ |

| **"浏览器没有本地定时通知"** | ✅ 基本成立 | 已核实：Notification Triggers API 已被 Chrome 停摆，Periodic Background Sync 在 Safari 从未支持。文档的结论方向正确，只是措辞可以更精确（P2 #11） |

### 5.3 成本可行性 —— ⚠️ 结论方向对，但论证是错的

`PRD/09` §5 的"≈ 0 ~ 300 元/月"在**自用阶段**成立（Bark、Let's Encrypt、ASR 按量都接近 0）。
但**"0 元 Cloudflare vs 60 元 VPS"这个二选一的论证方向是错的**：

| 文档主张 | 核实后的裁定 |
| ---- | ---- |
| "0 元（Cloudflare 免费版）" | **部分成立但不完整**。Cron + D1 能在免费额度内跑，但 **10 ms CPU / 50 子请求**使"一轮发 50 条推送"必然失败（P1-15），必须改成分片 cron。**这是"有工程代价的 0 元"**，不是配置一下就完事 |
| "D1/KV"（二选一） | **D1 ✅ 正确，KV ❌ 不适用**。KV 免费写额度仅 1,000/日、同 key 1 次/秒，几十个活跃用户就会爆（P1-15） |
| "60 元轻量服务器" | **性价比论证反了**。**Workers Paid $5/月（≈36 元）** 就把子请求提到 10,000、cron CPU 提到 30 s~15 min，且免运维、免 TLS 续期、免 Push 库维护。**若不想受免费版限制，最便宜的正解是 $5 Workers Paid，而不是 VPS** |
| "和风天气免费版" | **该表述已过时**。和风天气现在**全量按量计费**，"免费开发者订阅"已不存在；实际免费额度是"天气和基础服务"分组**每月前 50,000 次 = 0 元**。本项目用量（50~200 用户 × 每日 1 次 ≈ 月 1,500~6,000 次）**确实仍在 0 元内 ✓**，但措辞必须改，并注意：① 免费档只覆盖"天气和基础服务"分组，用台风/海洋/太阳辐照则从第一笔计费；② 最小计费 0.01 元，**超出后哪怕 1 次也会产生账单**，建议 80% 时告警；③ 开发者类型选定后**不支持更改** |

**漏掉的成本项**（V1 产品化之后）：

| 漏项 | 量级 | 出处 |
| ---- | ---- | ---- |
| 域名 + **ICP 备案** | ~60 元/年 + 时间成本 | 全文档未提（P0-3） |
| **境内轻量服务器**（若需备案） | 24~100 元/月 | 09 §5 只把服务器列为"或"选项 |
| **云 ASR 实际单价**（已核实） | 腾讯云一句话识别：**5,000 次/月免费**，之后 **3.20 元/千次**（≈0.0032 元/次），**≤60 秒 / ≤3 MB**；讯飞语音听写：默认 **500 次/日**免费 + 可领 5 万次/90 天礼包，之后 **0.005 元/次**。两家**均需实名认证**（腾讯云明确要求；讯飞公开文档未明确，需实测） | `TechDesign/12` §6 只写"按量计费、月几十元内"——量级对，但缺具体单价与**接口限额** |
