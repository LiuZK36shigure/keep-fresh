# 04 · 保质期推算规则（推算引擎设计）

> 这是产品**最核心的技术卖点**：不是"记录到期日"，而是"帮你算出到期日"。
> 本章定义三层规则引擎：**品类基线 → 开封/存储状态修正 → 气候因子修正**，以及置信度表达与维护机制。
>
> ⚠️ **食品安全红线**：本产品是"提醒工具"而非"质检机构"。推算结果一律标注"估算"，
> 采用**保守原则**（拿不准就取更短期限），并在明显位置提示"以包装标注与个人判断为准"。

---

## 1. 规则引擎总览

```
用户记录（品类 + 数量 + 购买日 + 开封状态 + 存储位置 + 城市）
        │
        ▼
┌─────────────────────────────┐
│ ① 品类基线表                │  → 未开封标准期限 T0（按存储位置分档）
└─────────────────────────────┘
        │
        ▼
┌─────────────────────────────┐
│ ② 状态修正                  │  → 已开封 → 用"开封后期限" T1（重新计时）
│    （开封状态 / 存储位置）    │  → 存储位置不符 → 修正（如"应冷藏却放室温"）
└─────────────────────────────┘
        │
        ▼
┌─────────────────────────────┐
│ ③ 气候因子修正              │  → 温度档 × 湿度档 × 特殊季（梅雨）→ 系数 k（0.5~1.0）
└─────────────────────────────┘
        │
        ▼
   预计可用期限 T = T1 × k
   到期日 = 购买日（或开封日） + T
   置信度 = 依据完整性打分 → 展示"估算区间"
```

**规则即数据**：以上全部规则存放在**可远程更新的 JSON 知识库**中（`shelf_rules.json`），
App 启动时拉取最新版本（离线时用本地缓存），不随发版才能改规则（见 07 非功能需求）。

> **双模型架构**：上述三层引擎只适用于**日期驱动品类**（有明确到期日：乳品、肉蛋、酱料、
> 药品、化妆品、冷冻品等）。生鲜果蔬（水果等）属于**状态驱动品类**，没有可靠到期日，逻辑模型不同——
> 见 §7。状态驱动品类在 V1 以**最小版**纳入（典型窗口 + 检查提醒，与其他品类同等级），复杂增强后置。

> 未开封期限 T0、开封后期限 T1、特殊说明、单价参考（用于"避免浪费金额"统计）。
> **状态驱动条目**（水果等）：T0/T1 位置填"典型窗口区间"，另含字段 `model: state` 与 `check_rhythm`（检查节奏），见 §7。

> **数据来源策略（一人公司）**：
> 1. V1：创始人人工整理 50 类（依据：包装标注通用规律 + 公开的食品安全常识 + 权威机构建议）；
> 2. V1.1：用户"修正反馈"自动沉淀为校准样本（见 03 F-06），人工审核后并入基线表；
> 3. 远期：接入包装标注数据库/商品库做自动匹配（P2，见 F-14）。
> 每一类基线都必须写"依据来源"，防止拍脑袋。

## 3. 状态修正规则

### 3.1 开封状态（最重要）

- **未开封**：用 T0（未开封标准期限）。
- **已开封**：从**开封日期**重新计时，用 T1（开封后期限）；若开封日期未知，默认开封日 = 购买日 + T0×0.5（提示用户补充）。
- **开封提醒语义**：用户说"XX 开封了"时，系统创建"开封计时器"，并按 T1 生成倒计时提醒。

### 3.2 存储位置

- 用户选择存储位置（冷藏/冷冻/室温/阴凉处/药箱/化妆台），与基线表要求的存储方式不一致时：
  - 例：鲜牛奶放在室温 → 系数 ×0.5，并提示"牛奶建议冷藏，室温下请尽快饮用"。
  - 例：蚝油开封后放室温 → 系数 ×0.6，提示"蚝油开封后请冷藏"。

### 3.3 数量与"多件"处理

- 数量 >1 时默认**逐件使用**：总期限不变，但提醒按"预计消耗节奏"分件（V1 简化：按单件期限提醒，件数仅用于统计与"还有几件"展示）。

## 4. 气候因子修正

### 4.1 气候档位模型（V1：手动档；V1.2：天气 API 自动）

| 维度 | 档位 | 系数 k（默认） | 适用 |
| ---- | ---- | ---- | ---- |
| 温度 | 常温（< 28℃） | 1.0 | 春秋、北方夏季阴凉 |
| 温度 | 高温（≥ 28℃ 持续） | 0.8 | 夏季南方城市 |
| 温度 | 酷热（≥ 33℃ 持续） | 0.7 | 极端高温天 |
| 湿度 | 干燥 | 1.0 | 北方秋冬 |
| 湿度 | 潮湿 | 0.8 | 南方回南天、沿海 |
| 特殊季 | 梅雨季 | 0.7（叠加） | 长江中下游 6-7 月 |
| 存储修正 | 应冷藏未冷藏 | 0.5 | 见 §3.2 |

**组合方式**：k = 温度系数 × 湿度系数 × 特殊季系数（叠加上限 0.5，不低于 0.5）。
例：上海 7 月（高温 0.8 × 潮湿 0.8）= 0.64；若同时梅雨（×0.7）= 0.448 → 取保底 0.5。

### 4.2 V1 用户操作方式（冷启动无 API）

- 首次使用时引导用户选择：所在城市（用于季节判断）+ 确认"夏天你家是否闷热/是否潮湿"两个问题，
  生成用户的【气候档案】；之后用户可在设置中一键切换"夏季模式/梅雨模式/日常模式"。
- 推算详情页展示：*"当前气候档：高温 + 潮湿 → 期限缩短约 40%"*，让用户理解并信任规则。

### 4.3 V1.2 自动模式（P1）

- 接入免费天气 API（如和风天气免费版/高德天气），按城市每日温湿度自动切换气候档；
- 天气 API 不可用时自动回退到手动档，**绝不因 API 故障影响记录功能**。

### 4.4 品类 × 气候的敏感性分级

- **高敏感**（乳制品、生鲜、面包、坚果、药品）：气候系数全量生效；
- **中敏感**（酱料、零食、大米）：仅湿度与特殊季生效；
- **低敏感**（罐头、冷冻品、化妆品、洗护）：气候因子基本不生效（冷冻品本身不受室温影响，化妆品只受高温暴晒影响——高温系数 0.9）。

> 敏感度也写入基线表字段 `climate_sensitivity: high|mid|low`。

## 5. 置信度与表达

### 5.1 置信度打分（规则依据完整性）

| 依据项 | 得分 |
| ---- | ---- |
| 品类命中基线表 | +40 |
| 开封状态明确 | +20 |
| 存储位置明确且符合要求 | +15 |
| 购买/开封日期明确 | +15 |
| 气候档位明确 | +10 |

- ≥ 90：高置信 → 展示单一日期（仍标注"估算"）；
- 60~89：中置信 → 展示区间："预计还有 4~6 天，按 4 天提醒"；
- < 60：低置信 → 展示区间 + 强提示"信息不足，建议核对包装标注"。

### 5.2 保守原则（Safety）

- 规则存在不确定性时**一律取更短期限**；
- 生鲜/乳品/婴幼儿用品：区间展示时提醒按**区间下限**触发；
- 任何推算都不替代包装标注：物品详情页常驻一行小字
  *"估算仅供参考，请以包装标注与实际状态（气味/外观）为准。"*

### 5.3 校准机制（让规则越用越准）

- 用户修正到期日/提前变质时，记录一条校准样本（品类、气候档、修正方向、原因）；
- 后台（V1 手工、V1.1 半自动）统计：某品类在"高温潮湿档"下被频繁提前修正 → 调低该档系数；
- 校准结果定期合并入知识库版本（版本号递增，App 内可查"知识库更新日志"）。

## 6. 边界情况处理

| 情况 | 处理 |
| ---- | ---- |
| 品类不在知识库 | 降级为"自定义物品"：用户填"期望期限"并选模板分类；系统学习该模板（P2 全自动） |
| 无网络 | 用本地缓存的最近版知识库推算，规则版本号展示"离线版" |
| 识别为"药品" | 强制提示"药品请以包装与医嘱为准"，推算仅作参考 |
| 冷冻→解冻 | 用户标记"解冻"后，按"解冻后 24h"生成倒计时提醒 |
| 日期在未来（用户口误） | 确认页校验：购买日 > 今天则拦截并提示修改 |
| 推算到期日已过（补录） | 不阻断保存，标记为"可能已过期"，提醒用户检查实物 |

## 7. 状态驱动品类：生鲜果蔬怎么办（V1 最小版）

> **版本决策（2025-07 最终确定）**：水果等生鲜果蔬在 **V1 以"最小版"纳入，与其他品类同等级**——
> 即"典型窗口 + 检查提醒"，不做成熟度判断。状态档、多模态估计、切开重算等复杂增强全部后置 P2（§7.6）。
> 理由：水果是目标用户最高频购买品类之一，最小版仅约 2 天工作量，不值得让最高频场景在 V1 缺席；
> 复杂增强则复杂度无底洞、本质不可精确预测，留给数据校准后的版本。

### 7.1 为什么水果不能用日期驱动模型

| 复杂度来源 | 例子 | 能否结构化？ |
| ---- | ---- | ---- |
| ① 品类粒度 | "水果"不是品类，是几百个品种：草莓 1~2 天，冷藏苹果几周 | ✅ 能（品种级条目） |
| ② 购入状态 | 成熟度（生/正好/过熟）、完整度（完整 vs 切开）、存储方式（香蕉/芒果放冰箱反而坏更快——冷害） | ✅ 能（做成可选字段） |
| ③ 动态变化 | 呼吸跃变型水果（香蕉、牛油果、番茄）买回来还在继续熟，状态每天在变 | ❌ 本质不可精确预测 |
| ④ 个体差异 | 同一批草莓，品质不同，坏的时间完全不同 | ❌ 本质不可精确预测 |

**结论**：①②可以结构化（是"复杂"），③④不可精确预测（是"不确定性"）。
对不可预测的东西越假装精确，用户越不信任——"说好 3 天，结果 2 天就坏了"，用户不会怪草莓，会怪你。

### 7.2 双模型对比

| | 日期驱动模型（§1~6） | 状态驱动模型（本章） |
| ---- | ---- | ---- |
| 适用 | 包装食品、药品、化妆品、冷冻品 | 果蔬、面包、剩菜、鲜切 |
| 输出 | 一个到期日（估算） | 一个建议窗口（区间） |
| 提醒 | 到期前 N 天提醒 | **检查提醒**（"草莓第 2 天啦，看一眼有没有发霉～"） |
| 失败模式 | 推算不准 | 不承诺精确，所以不存在"不准" |

### 7.3 成熟度（状态档）与"我不知道"默认态

- **关键设计：状态档不是必答问卷，用户不输入 = 默认"不知道"** = 走保守典型窗口。
  "我不知道"不是第四个选项，而是**默认值**——任何用户都不必回答自己答不出的问题（这正是目标用户的常见处境）。
- 可选增强（V1.1+）：确认页折叠区可选手动三档：**还很生（3~5 天）/ 正好吃（1~2 天）/ 有点过（今天内）**。
- 用户主动补充：可用**语音描述**（"有点软了"）或**拍照**触发多模态成熟度估计（P2，见 §7.6）。

### 7.4 情境化科普窗口（不是教学弹窗）

- 触发条件：仅当该品类存在**反直觉规则**时（例：香蕉/芒果/木瓜"别放冰箱，会冻伤"）；
- 形式：记录确认页一行小字 + 可展开的"为什么"，**绝不弹全屏教学**；
- 定位：科普是"帮用户做对选择"的轻提示，不是课程；
- 副产品：科普内容 = 内容营销资产（小红书冷启动素材，见 10 章 §2——"梅雨季食物保存指南"）。

### 7.5 最小版（已纳入 V1，约 2 天工作量）

- 知识库新增"状态驱动"品类条目：**典型窗口（区间）+ 检查节奏**，不承诺精确期限；
- 新增**检查提醒**类型（05 §1.1 预留）：按检查节奏触发，帮用户"看一眼"；
- 语音照常："草莓，今天买的" → 窗口 1~2 天 + 检查提醒；
- 特殊存储规则直接内置（香蕉/芒果提示勿冷藏）。

### 7.6 复杂增强（全部 P2）

| 增强 | 说明 | 依赖 |
| ---- | ---- | ---- |
| 成熟度三档 + "我不知道"默认 | §7.3 | 最小版 |
| 多模态成熟度估计 | 拍水果照片 → 估计"大约还能放 2~3 天"；**只做成熟度估计，不做"能不能吃"判定**（安全红线 R1 不破，低风险、高感知、可分享，是理想付费卖点） | 拍照记录 F-04 |
| 切开重算 | 西瓜切开后按"切开后窗口"重算（约 1 天） | 状态档 |
| 校准收敛 | 按品种统计"提前变坏"修正，窗口系数自动下调 | 修正反馈数据量 |

### 7.7 版本决策记录（2025-07 最终确定）

1. **V1 纳入最小版**：水果是最高频购买品类，最小版成本约 2 天（知识库条目 + 检查提醒类型），
   与其他品类同等级支持——用户日常购买场景在 V1 即"接得住"；
2. **复杂增强全部后置 P2**：成熟度状态档、多模态估计、切开重算（§7.6）复杂度无底洞、
   本质不可精确预测，且需真实数据校准，留给 V1.2+；
3. **检查提醒因此升为 P0**：作为 V1 第四种提醒类型（05 §1.1）；
4. **V1 内测统计注意**："用户手动修改推算日期的比例 ≤ 20%"（08 §2.3）指标对水果条目不适用
   （窗口不承诺精确），统计时应排除状态驱动品类或单独统计。
