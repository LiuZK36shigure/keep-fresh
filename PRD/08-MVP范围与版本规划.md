# 08 · MVP 范围与版本规划

> 一人公司最忌"功能堆砌"。本章给出范围取舍原则、**V0 的完整边界**、版本路线图与**每版的验证目标**。
>
> **本章是"这一版做什么"的唯一权威**。其他章节与本表冲突时，以本章为准。
>
> **版本号约定（2026-08 收敛，替代此前的 V0/V0.5/V1/V1.1/V1.2/V2/V2.0/P1.1 混用）**：
> 全文档集**只使用三个版本号**，`P0 / P1 / P2` 与之一一映射：
>
> | 版本 | 名称 | P 级 | 状态 |
> | ---- | ---- | ---- | ---- |
> | **V0** | 物资总管（PC 辅助端） | P0 | **当前开发** |
> | **V1** | 提醒闭环（公网 + 移动端） | P1 | 待 V0 验证后启动 |
> | **V2** | 产品化（多用户公网 / 家庭共享 / 付费） | P2 | 远期 |

---

## 1. 范围取舍原则

1. **闭环优先**：先跑通"登记 → 推算 → 管理 → 处置"这条**数据闭环**，提醒闭环（主动触达）后置；
2. **零外部依赖优先**：任何需要注册第三方账号、实名认证、付费、或部署到公网的环节，一律后置；
3. **服务端为权威**：V0 就有账户与同步，数据只有一份，不存在"端云合并"这类复杂度；
4. **接口先于实现**：V0 不做的能力（提醒 / 语音 / 推送），**接口与字段先留好**，移动端接入时不改协议；
5. **可配置优先**：品类规则必须是 JSON，改一条规则不发版；
6. **"会被用户夸"优先**：每版至少有一个"值得截图分享"的点（V0 = 推算依据的可解释性）。

## 2. V0 范围：物资总管（PC 辅助端）

> **一句话**：一个跑在你自己电脑上的「物资总管」Web 应用——
> 注册账号 → 手动录入买回来的东西 → 自动推算到期日 → 分组/筛选/搜索管理 → 标记用完或丢弃。
> 后端与前端同仓，**一条命令同时起**。

### 2.1 形态

| 项 | V0 决策 | 说明 |
| ---- | ---- | ---- |
| 前端 | **Vite + React + TypeScript**，**桌面浏览器**（Chrome / Edge） | 不做 PWA、不做移动端适配、不做「添加到主屏幕」 |
| 后端 | **Node + Hono + SQLite**，本地运行 | 与前端同仓，`pnpm dev` 一起起；**不部署、不买服务器、不需要域名与备案** |
| 数据 | **服务端 SQLite 为唯一权威** | "账户下的物资通过服务端同步"——前端不做本地权威副本 |
| 定位 | 未来移动端的**客户辅助端** | 电脑上"总管物资"；手机端的记录/提醒能力留到 V1 |

### 2.2 P0 功能（必做）

| 模块 | 内容 | 对应 |
| ---- | ---- | ---- |
| **账户** | 注册 / 登录 / 登出；用户名 + 密码（argon2id 哈希）；会话 token；**数据按账户隔离** | 新增（原"无账号体系"作废） |
| **记录** | 手动表单：品类（搜索/热门）→ 数量 → 购买日 → 开封状态 → 存储位置 → 备注 | F-02（由兜底升为主入口） |
| **推算** | 品类基线 × 开封状态 × 气候档（手动档）三层引擎；展示依据文案与置信度 | F-05 / F-06 |
| **管理** | **完整版列表**：分组视图（冷藏/冷冻/储物柜/药箱/化妆台/其他）+ 排序（到期日/购买日）+ 筛选（临期/过期/已开封）+ 搜索 | F-09 完整版（由 P1 升为 P0） |
| **详情** | 全字段 + 推算依据 + 手动修改（校准样本本地记录） | F-10（由 P1 升为 P0） |
| **处置** | 已用完 / 已丢弃 / 转赠；5 秒内可撤销 | F-08（去按钮化，改为详情/列表内操作） |
| **统计** | 极简三项：在库件数 / 本月处置件数 / 避免浪费件数（**不做图表**） | F-11 极简版 |
| **知识库** | 50 类 `shelf_rules.json` + `copywriting.json`，服务端持有，启动时校验 | 07 §5 |
| **设置** | 气候档位 / 默认存储位置 / 修改密码 | F-13（子集） |
| **工程** | monorepo + typecheck + vitest（core 覆盖率 ≥ 80%）+ 一条命令启动 | TechDesign 08 |

### 2.3 V0 明确不做（**这一节同等重要**）

> ⚠️ 以下不是"以后再说"，而是**明确排除在 V0 之外**。相关设计文档保留，但标注「V1 起实现」。

| 不做 | 原因 | 设计文档去向 |
| ---- | ---- | ---- |
| ❌ **一切提醒**（临期/过期/开封计时/检查）与页内横幅 | V0 是"总管"不是"提醒"，且提醒必须常开服务端才有意义 | `PRD/05` 整章标注「V1 起」 |
| ❌ **一切推送通道**（Web Push / Bark / ntfy / 飞书机器人） | 同上；且 iOS Web Push 前置条件苛刻、订阅会静默失效 | `TechDesign/12` §3 标注「V1」 |
| ❌ **语音录入与 ASR** | 依赖第三方云服务（实名 + 计费）且音频格式需前端归一化，属"涉及服务器"的复杂度 | `PRD/03` F-01、`TechDesign/05` §1 标注「V1」 |
| ❌ **PWA / 移动端适配 / 添加到主屏幕** | V0 只在 PC 用；但**前端仍按响应式写**，避免 V1 重写 | — |
| ❌ **公网部署 / 域名 / 备案 / HTTPS 证书** | V0 跑 `localhost`，这些全部后置 | `PRD/11` 新增 R13，**V1 发布前必须决策** |
| ❌ **定时任务 / Cron / 常开服务端** | 没有提醒就不需要常开 | `TechDesign/03` 新章不涉及 |
| ❌ **天气 API 自动气候** | 手动气候档足够 V0 验证推算引擎 | `PRD/04` §4.3 标注「V1」 |
| ❌ **拍照记录 / OCR** | 与"总管"闭环无关 | F-04 / F-14 |
| ❌ **家庭共享 / 多设备同步冲突** | V0 单用户单设备，冲突合并是纯增复杂度 | F-12 |
| ❌ **金额统计** | qty 单位体系未校准前金额不可信 | F-11（金额版） |

### 2.4 V0 保留的接口（为 V1 / 移动端预留）

> 这是"简化前期"的**关键**：不是删功能，而是**把接口先定下来**。

| 预留项 | 形式 | V1 怎么用 |
| ---- | ---- | ---- |
| **REST API 版本前缀** | 全部接口挂 `/api/v1/*`，JSON + `Authorization: Bearer <token>` | 移动端（RN/Expo 或 PWA）**直接复用同一套接口**，无需改后端协议 |
| **提醒字段** | `Item` 模型保留 `remindPolicy` / `windowStart` / `windowEndAt`，**V0 只算不推** | V1 加一个 cron + 推送发送即可，不必改表 |
| **`Notifier` 接口** | `notify(userId, payload): Promise<void>`，V0 提供 `NoopNotifier` | V1 换成 `WebPushNotifier` / `BarkNotifier` |
| **`VoiceInput` 接口** | `recognize(audio): Promise<string>`，V0 不实现 | V1 换成云 ASR adapter（注意音频格式归一化，见 TechDesign 12 §6） |
| **领域逻辑层 `packages/core`** | 纯 TS：parser（V0 留空）/ engine / 规则加载，**前后端共用** | 移动端直接复用；这也是"以后做移动端"最大的资产 |
| **知识库 JSON** | 服务端持有 + 版本号，前端可拉取 | V1 改为静态托管分发，机制不变 |
| **数据库迁移机制** | `schema_version` 表 + 顺序迁移脚本 | V0 SQLite → V1 迁 Postgres/云 DB 时有据可依 |

### 2.5 V0 完成定义（做到什么程度算"成了"）

| # | 验收项 | 判定方式 |
| ---- | ---- | ---- |
| 1 | **一条命令起前后端** | `pnpm dev` → 前端 `:5173` + 后端 `:3000` 同时可用 |
| 2 | **账户隔离** | 注册 A、B 两个账号各录 3 件；用 A 的 token 请求 B 的物资 → **403**；数据库直查确认数据分属不同 user_id |
| 3 | **数据不丢** | 录入 30 件 → 刷新 / 换浏览器 / 重装前端 → 数据仍在（服务端权威） |
| 4 | **推算正确** | 04 章 §2 示例品类 × 各气候档的用例全部通过，`reasonText` 与 `expireAt` 逐位一致 |
| 5 | **管理可用** | 500 条数据下列表渲染 ≤ 1 秒；分组/排序/筛选/搜索组合可用 |
| 6 | **闭环完整** | 登录 → 录入 → 查看推算依据 → 修改 → 标记用完 → 统计数字变化 → 5 秒内可撤销 |
| 7 | **质量底线** | `pnpm typecheck` 与 `pnpm test` 全绿；`core/` 覆盖率 ≥ 80%；`core/` 内无任何 `fetch` / Node API |

> **V0 的验证目标是"数据与推算是否可信"**，不是留存、不是提醒效果。
> 那两项属于 V1（见 §3），**不要在 V0 阶段用留存量判断成败**——V0 没有提醒，留存必然不好看。

## 3. 版本路线图

```
V0 · 物资总管（PC 辅助端）        V1 · 提醒闭环（公网 + 移动端）      V2 · 产品化
─────────────────────────       ────────────────────────────      ──────────────────
账户 + 同步（服务端权威）          部署公网 HTTPS（含备案决策）        家庭共享（2~4 人）
手动表单录入                      PWA「添加到主屏幕」                 深度统计与月度报告
三层推算引擎 + 依据展示            语音录入（浏览器归一化 + 云 ASR）    数据导出 / 账号删除
完整管理视图（分组/排序/筛选/搜索）  四类提醒（临期/过期/开封/检查）      付费与主体资质
处置闭环 + 极简统计                推送通道（Web Push；V0 期可先用 Bark） 原生 App（RN/Expo，复用 core/）
50 类知识库（JSON，可热更新）      天气 API 自动气候                   知识库扩到 200 类
localhost + SQLite               知识库扩到 100 类                   多设备同步与冲突合并
```

| 版本 | 核心业务问题 | 关键交付 | 退出标准 |
| ---- | ---- | ---- | ---- |
| **V0**（物资总管） | **东西记得住吗？算得准吗？** | 账户 + 本地后端 + PC 网页 + 推算引擎 + 完整管理视图 | §2.5 的 7 条全部通过；**自己真实使用 ≥ 2 周**，库存在 30 件以上且保持更新 |
| **V1**（提醒闭环） | **提醒有没有用？** | 公网部署 + 移动端可用 + 语音录入 + 四类提醒 + 推送通道 | 提醒点击率 ≥ 40%；48h 处置率 ≥ 50%；30 日留存 ≥ 20% |
| **V2**（产品化） | **别人愿意付费吗？** | 家庭共享 + 深度统计 + 付费 + 主体资质 | 家庭空间周活 ≥ 30%；付费转化 ≥ 3% |

> **版本之间的硬门禁**：V0 的 §2.5 未全绿，**不进入 V1 开发**。
> 但注意——**"没达标"指的是功能没做完或推算不准，不是留存量不好看**（V0 没有提醒，留存天然低）。

## 4. 迭代节奏（一人公司的"周"）

| 周几 | 工作内容 |
| ---- | ---- |
| 周一 | 看数据/看进度 → 定本周 1 个主题 |
| 周二~周四 | 开发 + 自测（AI 辅助，见 09 §4） |
| 周五 | 自用验证 + 修 bug |
| 周六 | **录入手上的真实物资** / 写 1 篇内容 |
| 周日 | 复盘：哪里卡住了 + 更新 PRD 假设 → 休息 |

> 原则：**每周只做一件事**。一周做 3 个功能 = 3 个功能都没做完。
>
> **工期口径（2026-08 修订）**：按 09 §6 的"晚 2 小时 + 周末半天"≈ **14 小时/周**计，
> V0 的 §2.2 清单（少了语音/ASR/推送/定时/部署，多了账户与同步）**预计 3~4 周**。
> 此前"2~4 周含 2 周 dogfooding"的口径已被证明不现实，**不再使用**。
