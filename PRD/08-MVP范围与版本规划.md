# 08 · MVP 范围与版本规划

> 一人公司最忌"功能堆砌"。本章给出范围取舍原则、MVP 边界、版本路线图与**每版的验证目标**——
> 每个版本都要回答一个业务问题，而不是"又加了几个功能"。

---

## 1. 范围取舍原则

1. **闭环优先**：MVP 必须跑通"记录 → 推算 → 提醒 → 处置"完整闭环，哪怕每个环节都简陋；
2. **黄金时刻优先**：一切设计围绕"购买瞬间 10 秒内完成记录"展开，砍掉任何拖慢它的东西；
3. **数据优先于功能**：宁可少做功能，也要把埋点（03 §4）做对——没有数据，下一版不知道做什么；
4. **可配置优先**：规则、文案必须可远程更新，因为一个人来不及发版救火；
5. **"会被用户夸"优先**：每个版本至少有一个"值得截图分享"的点（生活化文案/成就卡片），这是冷启动的燃料。

## 2. MVP（V1.0）范围

### 2.1 P0 功能（必做）

| 模块 | 内容 | 对应 |
| ---- | ---- | ---- |
| 记录 | 语音录入 + 确认页纠错 + 手动表单兜底 + 快捷模板 | F-01/02/03 |
| 推算 | 品类基线（50+ 类，含生鲜果蔬最小版）+ 开封状态 + 手动气候档 + 估算区间与依据展示 | F-05/06 |
| 提醒 | 临期/过期/开封计时（订阅消息，三类高价值）+ 检查提醒（水果，横幅）+ 订阅授权引导与管理 + App 内横幅兜底（双端去重） + 防轰炸合并 | F-07 |
| 处置 | 提醒卡片一键处置（用完/丢弃/转赠/延后）+ 5 秒撤销 | F-08 |
| 管理 | 极简"全部物品"页（只读列表 + 处置按钮，闭环完整性，2026-08 新增） | F-09 极简版 |
| 设置 | 气候档案（首记后引导）、提醒时间窗、推送开关、订阅授权管理、隐私开关 | F-13 |
| 数据 | 全部埋点事件 + 本地优先存储 | 03 §4 / 07 §1 |
| 知识库 | shelf_rules.json + copywriting.json 远程可更新 | 07 §5 |

### 2.2 MVP 明确不做（与 01 §4.2 呼应）

- ❌ 不做拍照记录（P1）；❌ 不做家庭共享（P1）；❌ 不做统计页（P1）；
- ❌ 不做天气 API 自动气候（P1）；❌ 不做 OCR/扫码（P2）；
- ❌ **不做服务号通知渠道**（V1.2，需企业/个体户主体，见 09 §5 / 10 §1.1）；
- ❌ **不做金额统计**（V1 只统计件数，金额版待单价体系校准后于 P1.1 上线，见 03 F-11）；
- ❌ 不做社交/内容；❌ 不做原生 App；
- ❌ **V1 不做状态驱动的复杂增强**：成熟度状态档、多模态成熟度估计、切开重算全部后置（见 04 §7）；
  水果等生鲜在 V1 仅以"最小版"（典型窗口 + 检查提醒）支持，**与其他品类同等级**。

### 2.3 MVP 验证目标（做到什么程度算"成了"）

| 问题 | 通过标准（内测 20~50 人，4~6 周） |
| ---- | ---- |
| 用户愿意记录吗？ | 人均周记录 ≥ 5 条；单条记录 ≤ 10 秒 |
| 语音真的更好用吗？ | 语音录入占比 ≥ 60%；解析准确率 ≥ 80% + 确认页修改率 ≤ 30%（双口径，2026-08 修订）；语音用户留存趋势（同用户对比，见 10 §4 H1） |
| 推算准吗？ | 用户手动修改推算日期的比例 ≤ 20% |
| 提醒有效吗？ | 提醒点击率 ≥ 40%；48h 处置率 ≥ 50%；**订阅授权率 ≥ 30%**（2026-08 新增，低于则重设计授权时机） |
| 值得继续做吗？ | 30 日留存 ≥ 20%；≥ 3 位用户主动说"愿意付费/推荐给家人" |

> 任一标准未达标，先回炉（改记录流程/改提醒策略），**不进入 V1.1 的功能开发**。
>
> 注："用户手动修改推算日期的比例 ≤ 20%"仅统计**日期驱动品类**；状态驱动品类（水果窗口）不承诺精确，
> 单独观察处置率与"提前变坏"修正（见 04 §7.7）。

## 3. 版本路线图

```
V1.0 MVP（第 1~12 周）          V1.1 增强（第 13~20 周）        V1.2 智能化（第 21~28 周）
─────────────────────          ──────────────────────          ──────────────────────
语音记录闭环                    拍照记录 + 照片归档              天气 API 自动气候档
50+ 类基线知识库(含水果最小版)   物品列表/详情页完善              校准数据半自动调优
手动气候档 + 估算区间            统计页 + 徽章 + 分享卡片          OCR 识别包装日期(试点)
临期/过期/开封/检查提醒          家庭共享(2~4 人)                成熟度状态档 + 多模态估计(试点)
极简全部物品页(闭环完整性)       数据导出(端侧) + 知识库扩 200 类  菜谱/处置建议(轻量)
处置闭环 + 埋点(端侧聚合上报)    主体资质决策(服务号/支付前置)    服务号订阅通知渠道
内测 20 人 → 小范围发布          用户访谈 10 人                  文案 A/B 测试
                                                               商业化功能试点(订阅)
```

| 版本 | 核心业务问题 | 关键交付 | 退出标准 |
| ---- | ---- | ---- | ---- |
| V1.0 | 有人愿意持续用它吗？ | 记录闭环 + 提醒闭环（含生鲜果蔬最小版 + 极简全部物品页） | 30 日留存 ≥ 20% |
| V1.1 | 它能进家庭吗？（付费信号） | 共享 + 统计 + 拍照 + 端侧数据导出 + **主体资质决策**（服务号/支付共同依赖，2026-08 修订） | 家庭空间周活 ≥ 30% |
| V1.2 | 推算够聪明吗？（差异化加固） | 自动气候 + 校准 + 状态档/多模态试点 + **服务号订阅通知渠道**（2026-08 新增） | 修改推算比例 ≤ 15% |
| V2.0（候选） | 要不要做原生 App？ | 依据：小程序推送限制是否成为流失主因 | 流失原因访谈结论 |

## 4. 迭代节奏（一人公司的"周"）

| 周几 | 工作内容 |
| ---- | ---- |
| 周一 | 看数据（上周指标）→ 定本周 1 个主题 |
| 周二~周四 | 开发 + 自测（AI 辅助，见 09 §4） |
| 周五 | 内测群发布 + 收集反馈 + 修复 |
| 周六 | 用户访谈 2~3 人 / 内容运营（小红书 1~2 篇） |
| 周日 | 复盘：指标变化 + 更新 PRD 假设 → 休息 |

> 原则：**每周只做一件事**。一周做 3 个功能 = 3 个功能都没做完。
