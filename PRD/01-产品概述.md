## 1. 背景与问题

### 1.1 一个每天都在发生的浪费

食物浪费是一个巨大的、但每个家庭或许都"感觉不到"的问题：

- 据媒体报道，我国每年食物**损耗与浪费总量约 4.6 亿吨**（含生产、储运、加工、消费全链条）；
  仅消费端被丢弃的食物也达到**亿吨级**（有报道称中国一年丢弃约 1.08 亿吨食物）。
  （参考：[尺素金声｜一年损耗浪费食物4.6亿吨](https://news.ifeng.com/c/8fDk9aPB1Ut)、
  [最浪费食物的国家 中国去年丢弃1.08亿吨食物](https://news.seehua.com/post/1378198)）
- 家庭场景中，浪费的主因往往不是"买太多"，而是 **"忘了它存在"和"不知道它还能不能吃"**：
  - 冰箱深处的酸奶过期一周才发现；
  - 买了很贵的化妆品，开封后放着放着就过了 6 个月保质期；
  - 药品、保健品过期后只能整盒扔掉。

### 1.2 用户的三个具体痛点

| 痛点         | 描述                                                      | 现有解决方案的不足                                  |
| ------------ | --------------------------------------------------------- | --------------------------------------------------- |
| **记不住**   | 买的时候没记，用的时候想不起来还有，放在冰箱里被忘记      | 备忘录要手动打字，坚持不下去；冰箱贴手写麻烦        |
| **算不准**   | "保质期"≠"能吃的期限"：开封后、夏天、潮湿天气都会显著缩短 | 包装上只有未开封保质期；没人帮你换算"开封 + 梅雨季" |
| **提醒粗暴** | 要么没提醒，要么到期当天才弹一个冷冰冰的"已过期"          | 制造焦虑，用户反而产生回避心理                      |

### 1.3 为什么是"现在"做这件事

1. **语音交互成熟**：语音识别准确率已很高且免费，语音记录的门槛被抹平，输入便捷性得到提升，AI也可更轻松的解析所有的输入；
2. **气候数据可获取**：天气/气候 API 廉价甚至免费，"环境修正保质期"在技术上可行；
3. **AI 降低单人开发成本**：一人公司可以借助 AI 完成原型、代码、文案，冷启动成本前所未有地低；
4. **生活方式升级**：年轻人越来越重视"好好生活"，冰箱收纳、断舍离、极简生活是热门话题，天然有传播场景。

## 2. 产品定位

### 2.1 一句话定位

> **一款生活化的个人物品保质期管家：用语音/拍照 3 秒记录你买的东西，结合本地气候与物品特性推算"可用期限"，并在合适的时间温柔提醒你。**

### 2.2 定位拆解

| 要素     | 内容                                  | 含义                               |
| -------- | ------------------------------------- | ---------------------------------- |
| 服务对象 | **个人 / 家庭**（不是仓库、不是企业） | 不做库存管理、不做扫码出入库       |
| 核心动作 | **记录 → 推算 → 提醒 → 处置**         | 四步闭环，缺一不可                 |
| 录入方式 | **语音优先**，打字、拍照为辅          | 把记录成本降到"说一句话"           |
| 推算逻辑 | 品类基线 × 开封状态 × **气候因子**    | 这是与所有"记事本"类工具的本质差异 |
| 体验风格 | **生活化**：温暖、拟人、不焦虑        | 差异化，见 2.4                     |

### 2.3 竞品差异（为什么用户选我们不选别的）

| 竞品类型          | 代表                   | 不足                                          | 我们的差异                       |
| ----------------- | ---------------------- | --------------------------------------------- | -------------------------------- |
| 普通提醒/日历 App | 手机自带提醒、滴答清单 | 需要手动计算日期；没有"保质期"心智            | 说一句话就能记，自动算到期日     |
| 冰箱收纳/库存 App | 各类"冰箱管理"App      | 录入繁琐（拍照+手动分类）；提醒生硬；用完即弃 | 语音优先 + 气候修正 + 生活化文案 |
| 记事本/Excel      | 备忘录、表格           | 没有推算、没有提醒                            | 全自动闭环                       |
| 超市会员 App      | 各商超 App             | 只覆盖本超市商品                              | 全渠道通用                       |

### 2.4 风格基调：生活化（Design Language 摘要）

- **视觉**：暖色调（奶油白、橘、浅绿），圆角卡片，手绘风插画；拒绝"工业感表格风"。
- **文案**：拟人化、有温度。示例：
  - 临期提醒：_"冰箱里的牛奶还有 2 天就到保鲜期啦，记得喝掉它～"_（V1 起才有提醒）
  - 过期提醒：_"这瓶酸奶已经悄悄过期了，是时候说再见啦。"_（V1 起）
  - 正向反馈：_"这个月你成功避免了 12 件浪费，冰箱终于清空啦！"_——**V0 就有**（极简统计的"避免浪费件数"，08 §2.2 统计模块）
    （金额版"避免了 36 元"待单价体系校准后启用，即 **V2**，V0/V1 只统计件数，见 03 F-11）
- **态度**：**提醒而不指责，管理而不囤积**。产品存在的意义是帮你"用完它"，而不是让你为浪费愧疚。

## 3. 产品目标与成功指标

### 3.1 产品目标（按优先级）

1. **减少浪费**：让用户"买的东西被用完"，而非堆到过期。
2. **降低管理成本**：记录一条物品 ≤ 3 步、≤ 10 秒。
3. **建立信任**：推算结果可解释、可纠正，绝不制造"过期焦虑"。
4. **形成习惯**：让"买完说一句"成为用户的下意识动作。

### 3.2 指标体系（北极星 + 过程指标）

**北极星指标（North Star）**：

> **每周完成"记录 → 处置"闭环的物品数** = 用户记录的物品中，被标记为"用完/处理"的数量（V1 起可再区分"提醒驱动"与"主动处置"）。
>
> 为什么是它：它同时度量了"记录习惯"（分子有人用）与"产品价值"（真帮用户处理掉了东西）。只记录不处置 = 产品没价值；不记录只处置 = 不可能发生。
>
> **V0 怎么用这个指标（2026-08 范围收缩）**：V0 没有提醒，"提醒驱动"那一桶**恒为 0**，因此**本周闭环数在 V0 不是留存指标**。
> 但配方本身成立：服务端 SQLite 为唯一权威，"在库件数 / 本月处置件数"两个数字就能当**自用验收**的标准
> （对应 08 §2.5 第 6 条"闭环完整"，且要求自己真实使用 ≥ 2 周）。
> ⚠️ **V0 阶段不要用留存量判断成败**——没有提醒，留存必然不好看（08 §3）。
>
> **计算口径（V0/V1 修订，2026-08）**：**服务端聚合**——
> V0 改为"服务端 SQLite 为唯一权威"之后，服务端本来就持有全量数据，
> **"记录→处置"的同物品关联可以直接在 SQL 里算**，不需要任何端侧上报链路。
> ⚠️ 原设计"端侧本地聚合上报（`weekly_closed` 事件）"是**"端侧为权威"时代的产物，已作废**；
> V1 重做埋点时直接用服务端聚合即可（TechDesign 07 顶部已标注）。
> 隐私面因此更小：**埋点根本不需要离开服务端**。

**过程指标（Process Metrics）**：

> ⚠️ **指标按可度量时机拆成两组（2026-08 范围收缩）**：**V0 没有提醒、没有语音、没有公网产品**，
> 因此原表中「提醒」分类的全部指标与「留存 / 病毒」分类在 V0 **无法度量**，它们自 **V1** 起才有意义。
> **V0 的验证目标是"数据与推算是否可信"，不是留存**（08 §2.5 / §3）。

**A. V0 可度量（V0 过程中自用观测即可，阈值仅供参考）**

| 分类 | 指标                             | V0 目标（自用观测参考）                 |
| ---- | -------------------------------- | --------------------------------------- |
| 记录 | 单条记录耗时中位数（手动表单）   | ≤ 60 秒（PC 端表单，替代 V1 的 10 秒口径） |
| 记录 | 确认/提交前修改率                | ≤ 30%                                   |
| 记录 | 录入成功率（表单提交无报错）     | ≥ 95%                                   |
| 管理 | 500 条数据下列表渲染耗时         | ≤ 1 秒（08 §2.5 第 5 条）               |
| 管理 | 分组 / 排序 / 筛选 / 搜索 组合可用 | 全部可用（V0 核心交付）                 |
| 推算 | 用户手动修改推算日期的比例       | ≤ 20%（超过则说明推算不准）             |
| 闭环 | 在库件数 / 本月处置件数          | 供自用判断"记得住、算得准"（不做目标值） |

**B. V1 起可度量（V1 内测参考）**

| 分类 | 指标                             | 版本 | 目标（V1 内测参考）                   |
| ---- | -------------------------------- | ---- | ------------------------------------- |
| 记录 | 语音解析准确率（内部迭代口径）   | V1   | ≥ 80%                                 |
| 记录 | 最终保存成功率（解析+纠错整体）  | V1   | ≥ 90%                                 |
| 提醒 | 提醒点击率（打开 App/卡片）      | V1   | ≥ 40%                                 |
| 记录 | **通知授权率**（记录成功页授权转化） | V1 | ≥ 30%                             |
| 处置 | 临期提醒后 48h 内处置率          | V1   | ≥ 50%                                 |
| 留存 | 新用户次日 / 30 日留存           | V1   | 次日 ≥ 40%，30 日 ≥ 20%（内测参考值） |
| 病毒 | 邀请家人共用的转化率             | V2   | ≥ 15%（家庭场景是天然裂变点）         |

> 说明：原表头的"目标（V1 内测参考）"仅适用于 B 组；A 组阈值是"自用观测参考"，
> **V0 不以此判断生死**（08 §2.5 只要求流程跑通 + 自己真实使用 ≥ 2 周）。

### 3.3 关键假设（需验证，见 10-商业模式与增长）

> ⚠️ **V0 只能验证 H4 的一半**：V0 不部署公网、没有真实用户，**H1~H3 都要等到 V1/V2 才可验证**（10 §4 清单已同步标注）。

- **H1（V1 起）**：语音记录能把"坚持记录"的留存率拉到可用水平（假设语音比手动输入留存高 20%+）。
  ⚠️ **V0 无语音录入**（属 V1，见 08 §2.3），**此假设在 V0 无法验证、也无需验证**；
  V0 的手动表单正是后续对比的基线。
  验证方法（2026-08 修订）：埋点记录用户首次入口（语音/手动），对比"先语音后手动"与"一直手动"用户的留存变化
  （同用户对比，避免自选择偏差），结论表述为相关性，3 周后补深度访谈定性佐证（见 10 §4）。
- **H2（V1 起，验证推算引擎本身可在 V0 先做）**：气候修正保质期对用户有感知价值（假设至少 30% 用户会注意到并认同"夏天牛奶坏得快"的提醒）。
  V0 用**手动气候档**就能自查推算结果是否符合常识（08 §2.2 推算模块），但"用户是否有感知"要等 V1。
- **H3（V1/V2 起）**："省到钱/避免浪费"的正向反馈能驱动分享（家人、小红书）。
  V0 只有**件数统计**（08 §2.2 统计模块），分享卡片属 V2。
- **H4（V1 起，V0 已有前置事实）**：**数据与推算的可信度**是用户选择本产品的理由之一。
  ⚠️ 原表述为"本地优先、不上传数据的隐私承诺"——**该表述已随 V0 的"服务端 SQLite 为唯一权威"失效**（08 §2.1），
  此处按 V0 架构改正；V0 阶段可先自己验证"推算依据是否说得清"，隐私承诺的具体形态（本地优先 or 服务端可信）
  留待 V1 结合公网部署重新设计。

## 4. 产品边界（做什么 & 不做什么）

### 4.1 做

- 食品、饮料、乳品、冷冻品、药品保健品、化妆品护肤品的**保质期与开封后期限**管理。
- 语音/拍照记录、推算、临期提醒、处置闭环、轻量统计。
- 家庭共享（多个成员一起维护一个"冰箱"）——**V2**（原 V1.1，编号废弃）。

> 📌 **V0 实际做的（2026-08 范围收缩）**：账户（用户名+密码+会话隔离）、**手动表单录入**、三层保质期推算引擎、
> **完整管理视图（分组/排序/筛选/搜索）**、物品详情、处置 + 5 秒撤销、**极简统计（3 个数字，不做图表）**、
> 50 类知识库 JSON、设置子集（气候档/默认存储位置/改密码）。
> 上式中的"语音/拍照记录"→ **V1/V2**，"临期提醒"→ **V1**，"轻量统计的金额版"→ **V2**。
> 详见 [08-MVP范围与版本规划](./08-MVP范围与版本规划.md) §2.2 / §2.3。

### 4.2 不做（Non-Goals，各版本均不做；V0 的排除清单见 08 §2.3）

- ❌ 不做购物清单/比价/电商导购（先把"管好已有的"做透）。
- ❌ 不做库存管理/出入库/条码批量扫描（那是企业场景）。
- ❌ 不做社交动态、社区内容（V2 再议）。
- ❌ 不做"健康饮食建议/营养计算"（知识库太深，单人做不动）。
- ❌ 不做 B 端/商家版本。
